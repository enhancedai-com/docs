O servidor MCP do FluxPrompt é um **Authorization Server OAuth 2.0** compatível com a especificação (RFC 8414). Esses endpoints são usados automaticamente por clientes de IA que suportam Dynamic Client Registration — você não os chama manualmente.

URL base: `https://mcp.fluxprompt.ai`

---

## Descoberta

### Metadados do Authorization Server OAuth

```http
GET /.well-known/oauth-authorization-server
GET /mcp/.well-known/oauth-authorization-server
GET /.well-known/oauth-authorization-server/mcp
```

Os três caminhos retornam o mesmo documento de metadados (com suporte a path, conforme a especificação MCP).

### Resposta

```json
{
  "issuer": "https://mcp.fluxprompt.ai",
  "authorization_endpoint": "https://mcp.fluxprompt.ai/oauth/authorize",
  "token_endpoint": "https://mcp.fluxprompt.ai/oauth/token",
  "registration_endpoint": "https://mcp.fluxprompt.ai/oauth/register",
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code"],
  "code_challenge_methods_supported": ["S256"],
  "token_endpoint_auth_methods_supported": ["none"],
  "scopes_supported": ["read", "write", "execute"],
  "client_id_metadata_document_supported": true
}
```

Apenas o grant `authorization_code` é suportado (sem refresh tokens), e os clientes são públicos: `token_endpoint_auth_methods_supported` é `["none"]`, então o PKCE (`S256`) substitui um client secret. `issuer` é o `MCP_PUBLIC_URL` do servidor. `client_id_metadata_document_supported: true` significa que um `client_id` que seja uma URL `https://` é buscado como um Client ID Metadata Document, em vez de ser procurado entre os clientes registrados.

### Metadados do Protected Resource OAuth

```http
GET /.well-known/oauth-protected-resource
GET /mcp/.well-known/oauth-protected-resource
GET /.well-known/oauth-protected-resource/mcp
```

Os três caminhos retornam o mesmo documento de metadados.

```json
{
  "resource": "https://mcp.fluxprompt.ai/mcp",
  "authorization_servers": ["https://mcp.fluxprompt.ai"],
  "scopes_supported": ["read", "write", "execute"],
  "bearer_methods_supported": ["header"]
}
```

`resource` é o próprio endpoint MCP (`{issuer}/mcp`), e não o host puro. Requisições MCP sem autenticação recebem `401` com `WWW-Authenticate: Bearer resource_metadata="{issuer}/.well-known/oauth-protected-resource"`, que é como os clientes encontram este documento.

## Dynamic Client Registration

Clientes de IA que suportam DCR se registram automaticamente na primeira conexão.

```http
POST /oauth/register
Content-Type: application/json
```

### Corpo da requisição

```json
{
  "redirect_uris": ["https://claude.ai/callback"],
  "client_name": "Claude Desktop"
}
```

`redirect_uris` é obrigatório e não pode ser vazio — caso contrário retorna 400.

### Resposta `201 Created`

```json
{
  "client_id": "dcr_3f9a1c…",
  "redirect_uris": ["https://claude.ai/callback"],
  "client_name": "Claude Desktop",
  "token_endpoint_auth_method": "none"
}
```

Os `client_id` gerados têm o prefixo `dcr_`. `client_name` é opcional e é retornado como `null` quando omitido. O registro é armazenado por 90 dias por padrão (`MCP_DCR_CLIENT_TTL`).

Os clientes DCR são **persistidos no Postgres** via `back/` e sobrevivem a reinicializações do mcp-server.

## Autorização

```http
GET /oauth/authorize
  ?response_type=code
  &client_id=dcr_3f9a1c…
  &redirect_uri=https://claude.ai/callback
  &code_challenge=BASE64URL(SHA256(verifier))
  &code_challenge_method=S256
  &state=random-state
  &scope=read
```

| Parâmetro | Obrigatório | Descrição |
|-----------|-------------|-----------|
| `response_type` | Sim | Deve ser `code`. |
| `client_id` | Sim | Um `client_id` DCR, ou uma URL `https://` de Client ID Metadata Document. |
| `redirect_uri` | Sim | Deve corresponder a uma redirect URI registrada. URIs de loopback (`localhost`, `127.0.0.1`, `::1`) são comparadas por esquema, host e path, independentemente da porta. |
| `code_challenge` | Sim | Challenge PKCE. |
| `code_challenge_method` | Sim | Deve ser `S256`. |
| `state` | Não | Devolvido em todos os redirecionamentos. |
| `scope` | Não | Escopos separados por espaço. O padrão é `read` quando omitido. |

Redireciona o navegador do usuário para a página de consentimento do FluxPrompt (configurada por `MCP_FRONT_CONSENT_URL`) com `request_id`, `client_id`, `client_name` e `scope`. Depois que o usuário aprova, a página de consentimento envia a assertion assinada de volta para `/oauth/consent-callback`.

### Erros

| Resposta | Motivo |
|----------|--------|
| `400 { "error": "invalid_request" }` | `client_id` ou `redirect_uri` ausente. |
| `400 { "error": "invalid_client" }` | Cliente desconhecido ou expirado, ou `redirect_uri` não corresponde. Esses dois casos retornam JSON porque a `redirect_uri` não é confiável. |
| Redirecionamento para `redirect_uri?error=invalid_request&state=…` | `response_type` não é `code`, ou `code_challenge` está ausente, ou `code_challenge_method` não é `S256`. |

## Callback de consentimento (interno)

```http
GET /oauth/consent-callback?request_id={id}&assertion={jwt}&decision=approve
```

Chamado pela página de consentimento do FluxPrompt depois que o usuário aprova ou nega. A `assertion` é um JWT HS256 de curta duração assinado pelo `back/` com o `MCP_OAUTH_CONSENT_SECRET` compartilhado.

### Query params

| Parâmetro | Obrigatório | Descrição |
|-----------|-------------|-----------|
| `request_id` | Sim | O `request_id` original de `/oauth/authorize`. `400 { "error": "invalid_request" }` se ausente, ou com `"reason": "expired"` se for desconhecido, expirado ou já usado. |
| `decision` | Sim | Deve ser exatamente `approve` para continuar o fluxo. Qualquer outro valor (ou `assertion` ausente) redireciona de volta para `redirect_uri` com `error=access_denied`. |
| `assertion` | Sim, quando `decision=approve` | O JWT HS256 de `POST /mcp/v1/oauth/consent`. |

Em caso de sucesso, redireciona para `redirect_uri?code=<auth-code>&state=<state>`.

Falhas redirecionam para `redirect_uri` com um parâmetro `error` e o `state` original:

| `error` | Motivo |
|---------|--------|
| `access_denied` | `decision` não é `approve`, ou `assertion` está ausente. |
| `access_denied` (com `reason=invalid_consent`) | A assinatura, o emissor, a audiência ou a expiração da assertion são inválidos, ou seu `nonce`/`clientId` não corresponde à solicitação pendente. |
| `invalid_scope` | Nenhum dos escopos concedidos estava entre os escopos solicitados em `/oauth/authorize`. Os escopos concedidos são a interseção dos dois. |

## Troca de token

```http
POST /oauth/token
Content-Type: application/x-www-form-urlencoded
```

```
grant_type=authorization_code
&code=<auth-code>
&redirect_uri=https://claude.ai/callback
&client_id=dcr_3f9a1c…
&code_verifier=<pkce-verifier>
```

### Resposta

```json
{
  "access_token": "mcp_oauth_abc123...",
  "token_type": "Bearer",
  "scope": "read"
}
```

`code`, `code_verifier` e `client_id` são obrigatórios. Os códigos de autorização são de uso único. O `access_token` é um token opaco `mcp_oauth_…` cujo hash é persistido no Postgres. Ele é usado como `Bearer` token em todas as requisições MCP seguintes.

### Erros

Todos os erros são `400` com corpo JSON.

| `error` | Motivo |
|---------|--------|
| `unsupported_grant_type` | `grant_type` não é `authorization_code`. |
| `invalid_request` | `code`, `code_verifier` ou `client_id` ausente. |
| `invalid_grant` | Código desconhecido, expirado ou já usado; `client_id` não corresponde ao código; ou `redirect_uri` foi enviado e não corresponde. |
| `invalid_grant` (com `reason: "pkce_mismatch"`) | O hash de `code_verifier` não corresponde ao `code_challenge`. |

<Note>
Os tokens de acesso OAuth **não expiram por padrão** (`expires_in` é omitido por completo da resposta, conforme a RFC 6749). Defina `MCP_OAUTH_TOKEN_TTL` (segundos) no servidor MCP para optar por uma expiração — com ele configurado, a resposta inclui `expires_in` com esse valor.
</Note>

## Endpoints de transporte

### Requisições MCP

```http
POST /mcp
POST /
Authorization: Bearer <token>
Content-Type: application/json
```

JSON-RPC 2.0 sobre Streamable HTTP. Todas as chamadas de ferramentas vão aqui.

### Encerramento de sessão

```http
DELETE /mcp
DELETE /
```

Retorna `204 No Content`. Nenhum header `Authorization` é necessário e nada é armazenado no servidor: o endpoint existe para que clientes que enviam uma requisição de encerramento de sessão recebam uma resposta limpa.

### Health check

```http
GET /healthz
GET /readyz
```

Ambos retornam `200 OK` com `{ "status": "ok" }`. Sem autenticação. Usados pelos health/readiness checks do ECS e por smoke tests pós-deploy.

## CORS

O servidor MCP habilita CORS para clientes OAuth baseados em navegador, refletindo o header `Origin` da requisição em vez de enviar um curinga literal, e não permite requisições com credenciais:

```
Access-Control-Allow-Origin: <o Origin da requisição>
Access-Control-Allow-Credentials: (não enviado — credentials: false)
Access-Control-Expose-Headers: Mcp-Session-Id, WWW-Authenticate
```

Os métodos permitidos são `GET`, `POST`, `OPTIONS` e `DELETE`. Os headers de requisição permitidos são `Authorization`, `Content-Type`, `Mcp-Session-Id`, `mcp-protocol-version` e `Accept`. O preflight CORS (`OPTIONS /mcp`) retorna `204` com os headers `Access-Control-Allow-*` apropriados.
