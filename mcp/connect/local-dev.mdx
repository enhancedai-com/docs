## Overview

The MCP server uses Streamable HTTP, which runs fine on `localhost`. You don't need a separate transport for local work — the same endpoint you'll deploy to staging and production works during development.

<Note>
**OAuth is the recommended way to authenticate, for developers too, in every environment** (local, dev, staging and production). Use an MCP key only for clients that can send nothing but a header (n8n, CI, scripts).
</Note>

The recommended tools are:

| Tool | Reaches `localhost`? | Best for |
|------|----------------------|----------|
| **MCP Inspector** | Yes (runs on your machine) | Exploring tools, inspecting raw JSON-RPC, quick iteration |
| **Claude Code (CLI)** | Yes (runs on your machine) | Testing as a developer with OAuth, no tunnel |
| **Claude Desktop** | No, needs a public HTTPS tunnel | End-to-end testing exactly as a real user would experience it (OAuth) |

## Prerequisites

- Node.js ≥ 22.13 and pnpm ≥ 11 **or** Docker Desktop (see option A below)
- `mcp-server/` cloned
- A local `back/` instance running (or a dev tunnel to the dev environment)
- The local front (`front/`, on `http://localhost:3000`) running, so you can generate an **MCP key** (see [Get a client credential](#get-a-client-credential)) or complete the OAuth consent screen. For OAuth it must be started with `VITE_MCP_SERVER_URL=http://localhost:3100/mcp` set — see [Client environment variables](/client/environment-variables)

## Step 1 — Start the server

Choose one approach. Docker Compose is recommended for new contributors — no Node/pnpm setup required on the host.

<Tabs>
  <Tab title="Option A — Docker Compose (recommended)">
    Starts `mcp-server` alone — no Node/pnpm setup required on the host.

    ```bash
    cp .env.example .env
    # Fill BACK_BASE_URL and MCP_INTERNAL_SECRET (see below)
    docker compose up
    ```

    The server listens on **http://localhost:3100** (published from the container).

    <Note>
    **arm64 image on an x86 host.** The compose image is built for `linux/arm64` to mirror production (AWS Fargate Graviton). On an x86 machine it runs under QEMU emulation — install the emulator once:

    ```bash
    docker run --privileged --rm tonistiigi/binfmt --install arm64
    ```
    </Note>

    <Note>
    **MCP Inspector does not run in Docker Compose.** The `inspector:` service in `docker-compose.yml`
    is defined but commented out — inside Docker its OAuth issuer (`http://mcp-server:3100`) would not
    match the `localhost` the browser and redirects use, so it doesn't work there. Run the Inspector on
    the host instead, whether `mcp-server` runs in Docker (this option) or standalone (Option B) — see
    [Step 2](#step-2-test-with-mcp-inspector).
    </Note>

    <Note>
    In Docker, set `BACK_BASE_URL` to `http://host.docker.internal:<port your back/ listens on>` — compose already maps `host.docker.internal` to the host on every OS.
    </Note>
  </Tab>
  <Tab title="Option B — Standalone (pnpm start:dev)">
    Requires pnpm and Node ≥ 22.13 installed on the host.

    ```bash
    cp .env.example .env
    # Set BACK_BASE_URL=http://localhost:<back-port>
    pnpm install
    pnpm start:dev        # watch mode — reloads on save
    ```

    The server listens on `http://localhost:3100` by default.
  </Tab>
</Tabs>

### Minimal `.env` for local work

```env
PORT=3100
NODE_ENV=development

BACK_BASE_URL=http://host.docker.internal:3001   # Docker; use http://localhost:3001 for pnpm
MCP_INTERNAL_SECRET=<same value as in back/.env>

# Local OAuth (Claude Desktop, Claude Code, the Inspector's OAuth flow)
MCP_PUBLIC_URL=http://localhost:3100
MCP_OAUTH_CONSENT_SECRET=<same value as in back/.env>
MCP_FRONT_CONSENT_URL=http://localhost:3000/mcp-authorize.html

MCP_KILL_SWITCH=off

# Leave blank to skip Datadog writes locally
DATADOG_API_KEY=
```

`MCP_INTERNAL_SECRET` must match the value set in `back/`'s `.env`. It is the secret `mcp-server` uses to call `back/` — it is **not** a client token, and sending it as `Authorization: Bearer ...` returns `401 invalid_token`.

See [Environment variables](/mcp/environment-variables) for the full list.

### Check that the server is up

```bash
curl -s http://localhost:3100/healthz
curl -s http://localhost:3100/readyz
```

The health endpoints are `/healthz` and `/readyz` (there is no `/health`).

### Get a client credential

Local `mcp-server` resolves every client token through `back/`, so use one of these supported paths:

<Steps>
  <Step title="Use OAuth (recommended)">
    Clients that support OAuth (Claude Desktop, Claude Code, the MCP Inspector's OAuth flow) need no key. Set the [Local OAuth](#local-oauth) values and let the client run the consent screen. The local server supports client ID metadata documents (CIMD), dynamic client registration (DCR) and PKCE `S256`.
  </Step>
  <Step title="Or generate an MCP key in the local front">
    Open `http://localhost:3000`, go to **Settings → MCP Keys** (or open `http://localhost:3000/dashboard-beta?settings=mcpTokens`), and click **Generate key**. Copy the key that starts with `mcp_` and use it as `Authorization: Bearer <key>`.
  </Step>
  <Step title="Or create a key from the command line">
    For header-only clients, from `back/` (after `pnpm build`, because the command runs the compiled output):

    ```bash
    pnpm mcp:dev-token --email <your user email> [--workspace <id>] [--scopes read,write,execute] [--name <name>]
    ```

    It creates the key through the app's own token service, so the membership check, role clamp, workspace binding and audit all apply. The workspace defaults to your first admin membership. It prints a random `mcp_…` key **once** — copy it then.
  </Step>
</Steps>

<Note>
Keys are created against the database your local `back/` uses, so the key only works with a local `mcp-server` that points at that same `back/`.
</Note>

## Step 2 — Test with MCP Inspector

<Tabs>
  <Tab title="Docker Compose (Option A)">
    The Inspector is not part of the Docker Compose stack (see the note in [Step 1](#step-1-start-the-server)) — run it on the host the same way as Option B, connecting to the port Docker published:

    | Field | Value |
    |-------|-------|
    | Transport | Streamable HTTP |
    | URL | `http://localhost:3100/mcp` |
    | Header | `Authorization: Bearer <your MCP key>` |

    Follow the **Standalone (Option B)** tab for the exact steps — switch to Streamable HTTP, set the URL above, add the header, then **Connect**.
  </Tab>
  <Tab title="Standalone (Option B)">
    [MCP Inspector](https://github.com/modelcontextprotocol/inspector) runs directly on the host. From `mcp-server/`, `pnpm inspect` starts the Inspector on port `5173` (local use only):

    ```bash
    pnpm inspect
    ```

    Or run the Inspector yourself. Run it **without arguments** — passing a URL directly makes it treat the URL as a stdio process to spawn, which fails for HTTP servers:

    ```bash
    npx @modelcontextprotocol/inspector
    ```

    The `npx` command opens the web UI at `http://localhost:6274`.

    <Steps>
      <Step title="Switch to Streamable HTTP transport">
        In the **Transport Type** dropdown, change `STDIO` to `Streamable HTTP`.
      </Step>
      <Step title="Set the server URL">
        Enter `http://localhost:3100/mcp` in the URL field.
      </Step>
      <Step title="Add the Authorization header">
        In the **Headers** panel, add:

        ```
        Authorization: Bearer <your MCP key>
        ```
      </Step>
      <Step title="Connect and explore">
        Click **Connect**, then **Tools → List**. The tool list is non-empty — see the [tools pages](/mcp/tools/agents-and-folders) for what each one does. Select any tool and click **Call** to see the raw JSON-RPC request and response.
      </Step>
    </Steps>
  </Tab>
</Tabs>

## Step 3 — Test with Claude Desktop (via a tunnel)

Claude Desktop adds remote MCP servers as **connectors**, by an **HTTPS URL**, and the request is made from Anthropic's backend, not from your machine. `localhost` is therefore unreachable: you need a public HTTPS tunnel. There is no local config file to edit for this.

<Steps>
  <Step title="Start a tunnel">
    Expose port `3100` with cloudflared or ngrok and align the three URL values, as described in [Tunnels](#tunnels). Restart the front and `mcp-server` afterwards.
  </Step>
  <Step title="Add a custom connector">
    In Claude Desktop, go to **Customize → Connectors → Add custom connector**, and enter `https://<your-tunnel>/mcp`.
  </Step>
  <Step title="Sign in with OAuth">
    Under authentication choose **Sign in**, then either **Use Claude's published identity** (recommended) or **Register automatically**. Complete the FluxPrompt consent screen served by your local front.
  </Step>
  <Step title="Ask Claude to use a tool">
    Try: *"List my FluxPrompt agents"* or *"What node types are available in FluxPrompt?"*
  </Step>
</Steps>

<Warning>
Do not add a FluxPrompt `url` or a header to `claude_desktop_config.json`. Claude Desktop does not connect to remote servers through that file.
</Warning>

## Step 4 — Test with Claude Code (CLI)

Claude Code runs on your machine, so it reaches `localhost` directly and needs no tunnel. See [Connect Claude Code](/mcp/connect/claude-code) for the full guide.

<Steps>
  <Step title="Add the local server">
    ```bash
    claude mcp add --transport http fluxprompt http://localhost:3100/mcp
    ```
  </Step>
  <Step title="Authenticate with OAuth">
    Inside Claude Code run `/mcp`, select **fluxprompt**, choose **Authenticate**, and finish the consent screen in your browser. Claude Code receives the result on a loopback redirect to an ephemeral port.
  </Step>
</Steps>

To use a key instead (header alternative), pass it with `--header`:

```bash
claude mcp add --transport http fluxprompt http://localhost:3100/mcp \
  --header "Authorization: Bearer mcp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
```

Keep the key out of `--scope project`, which writes a shared `.mcp.json`.

## Local OAuth

The `mcp-server` side of local OAuth (`MCP_PUBLIC_URL`, `MCP_OAUTH_CONSENT_SECRET`, `MCP_FRONT_CONSENT_URL`) is in the Step 1 `.env`. The rest:

| Where | Variable | Local value |
|-------|----------|-------------|
| `back` | `MCP_OAUTH_CONSENT_SECRET` | The **same** value as on `mcp-server` — otherwise the consent signature fails |
| `front` | `VITE_MCP_SERVER_URL` | `http://localhost:3100/mcp` (build-time — restart the Vite dev server after changing it; see [Client environment variables](/client/environment-variables)) |

`back/` also needs `MCP_SERVER_INTERNAL_URL` and `MCP_RESOURCE_METADATA_URL` — see [Main API environment variables](/main-api/environment-variables). Restart `mcp-server` after editing its `.env`.

## Tunnels

Claude Desktop, Claude.ai and any remote client can't reach `localhost`, because their requests come from the vendor's servers. Claude Code and the Inspector run on your machine and don't need a tunnel. Expose the server through a tunnel — both **ngrok** and **cloudflared** (`trycloudflare.com` quick tunnels) work.

Quick tunnels get a **new URL every time you start them**. When the public URL changes, update three values together:

| Value | Where | Format |
|-------|-------|--------|
| Client URL | The Claude Desktop connector URL, or e.g. the `fluxprompt-mcp-local` entry in `~/.claude.json` | Origin **plus** `/mcp` |
| `VITE_MCP_SERVER_URL` | `front/.env` (build-time) | Origin **plus** `/mcp` |
| `MCP_PUBLIC_URL` | `mcp-server/.env` | Bare origin, **no** `/mcp` |

Then restart the front and `mcp-server`, and reconnect the client. If they disagree, OAuth discovery returns an issuer that doesn't match the URL the client used and the sign-in fails.

<Tip>
The workspace's `mcp-tunnel-url` skill updates all three files in one step. It edits files only — you restart the services yourself.
</Tip>

For ngrok's free tier, send the `ngrok-skip-browser-warning: 1` header on every request — see [Troubleshooting](#troubleshooting). cloudflared needs no extra header.

## Quick curl smoke test

```bash
curl -s -X POST http://localhost:3100/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer <your MCP key>" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

A working setup returns a JSON-RPC `result.tools` array with the tool catalog. `tools/list` isn't filtered by scope, so an empty list is not a permissions problem.

## Run the test suite

```bash
pnpm test              # unit tests — fast, no network
pnpm test:e2e          # e2e tests — Supertest, in-process server
npx tsc --noEmit       # type check
```

All three must pass before any commit.

## Troubleshooting

<AccordionGroup>
  <Accordion title="401 Unauthorized">
    The response body has a `reason`:

    - `missing_token` — no `Authorization: Bearer ...` header.
    - `invalid_token` — the token isn't accepted: it's unknown, revoked, expired, or has no active workspace binding. Locally, `MCP_INTERNAL_SECRET` is not a client token either.

    Generate a new key under **MCP Keys** in the local front or with `pnpm mcp:dev-token` (see [Get a client credential](#get-a-client-credential)), or use OAuth instead. For the generic 401 reasons, see [Troubleshooting](/mcp/troubleshooting).
  </Accordion>
  <Accordion title='"Service disabled" error (-32005)'>
    `MCP_KILL_SWITCH=on` is set in your `.env`. Change it to `off` and restart.
  </Accordion>
  <Accordion title="503 upstream_unavailable / cannot reach back/ (ECONNREFUSED)">
    `mcp-server` couldn't reach `back/`, so it answers `503` with `reason: "upstream_unavailable"`. Check `BACK_BASE_URL` (see [Step 1](#minimal-env-for-local-work)) and that `back/` is running.
  </Accordion>
  <Accordion title="502 upstream_auth_rejected">
    `MCP_INTERNAL_SECRET` differs between `mcp-server` and `back/`. Set the same value on both and restart `mcp-server`.
  </Accordion>
  <Accordion title="Inspector shows ECONNREFUSED or won't connect">
    The Inspector runs on the host (see [Step 2](#step-2-test-with-mcp-inspector)), not inside Docker
    Compose — the `inspector:` service in `docker-compose.yml` is commented out. Make sure you started
    it on the host, and that the URL you gave it is `http://localhost:3100/mcp` (the port Docker
    publishes `mcp-server` on).
  </Accordion>
  <Accordion title="OAuth consent page doesn't load or the sign-in fails">
    Check the [Local OAuth](#local-oauth) values and the Step 1 `.env`: `MCP_OAUTH_CONSENT_SECRET` must be identical on `mcp-server` and `back`, and `MCP_PUBLIC_URL` / `VITE_MCP_SERVER_URL` must point at the same origin the client uses (see [Tunnels](#tunnels)).
  </Accordion>
  <Accordion title='Exposing the server via ngrok — responses come back as HTML ("Unexpected content type: text/html")'>
    When you tunnel the local server through **ngrok** (free tier), ngrok serves its browser-warning interstitial page (HTTP 200, `Content-Type: text/html`) instead of proxying to the MCP server. The MCP client then fails with `Unexpected content type: text/html`.

    Send the skip header on every request — and note the value must be **`1`**, not `true` (ngrok only honors `1`):

    ```
    ngrok-skip-browser-warning: 1
    ```

    In a config that supports headers (for example a Claude Code entry in `~/.claude.json`), add it alongside `Authorization`:

    ```json
    "headers": {
      "Authorization": "Bearer <token>",
      "ngrok-skip-browser-warning": "1"
    }
    ```

    For a client that can't send headers, use cloudflared, or let ngrok inject the header for you (`ngrok http 3100 --request-header-add "ngrok-skip-browser-warning: 1"`).

    Verify with curl (note the value `1`):

    ```bash
    curl -s -X POST https://<your-subdomain>.ngrok-free.dev/mcp \
      -H "Authorization: Bearer <token>" \
      -H "ngrok-skip-browser-warning: 1" \
      -H "Content-Type: application/json" \
      -H "Accept: application/json, text/event-stream" \
      -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
    ```

    A correct response has `Content-Type: text/event-stream`. If you still get `text/html`, the header value is wrong (`true` instead of `1`) or missing.
  </Accordion>
</AccordionGroup>
