## Overview

The MCP server uses Streamable HTTP, which runs fine on `localhost`. You don't need a separate transport for local work — the same endpoint you'll deploy to staging and production works during development.

The two recommended tools are:

| Tool | Best for |
|------|----------|
| **MCP Inspector** | Exploring tools, inspecting raw JSON-RPC, quick iteration |
| **Claude Desktop** | End-to-end testing exactly as a real user would experience it (OAuth) |

## Prerequisites

- Node.js ≥ 22.13 and pnpm ≥ 11 **or** Docker Desktop (see option A below)
- `mcp-server/` cloned
- A local `back/` instance running (or a dev tunnel to the dev environment)
- The local front (`front/`, on `http://localhost:3000`) running, so you can generate an **MCP key** (see [Get a client credential](#get-a-client-credential)) or complete the OAuth consent screen

## Step 1 — Start the server

Choose one approach. Docker Compose is recommended for new contributors — no Node/pnpm setup required on the host.

<Tabs>
  <Tab title="Option A — Docker Compose (recommended)">
    Starts `mcp-server` alone — no Node/pnpm setup required on the host.

    ```bash
    cp .env.example .env
    # Fill BACK_BASE_URL and MCP_INTERNAL_SECRET (see below)
    docker compose up
    ```

    The server listens on **http://localhost:3100** (published from the container).

    <Note>
    **arm64 image on an x86 host.** The compose image is built for `linux/arm64` to mirror production (AWS Fargate Graviton). On an x86 machine it runs under QEMU emulation — install the emulator once:

    ```bash
    docker run --privileged --rm tonistiigi/binfmt --install arm64
    ```
    </Note>

    <Note>
    **MCP Inspector does not run in Docker Compose.** The `inspector:` service in `docker-compose.yml`
    is defined but commented out — inside Docker its OAuth issuer (`http://mcp-server:3100`) would not
    match the `localhost` the browser and redirects use, so it doesn't work there. Run the Inspector on
    the host instead, whether `mcp-server` runs in Docker (this option) or standalone (Option B) — see
    [Step 2](#step-2-test-with-mcp-inspector).
    </Note>

    <Note>
    **`BACK_BASE_URL` in Docker** — the container can't use `localhost` to reach your machine, because inside a container `localhost` is the container itself. The compose file already adds `extra_hosts: ["host.docker.internal:host-gateway"]`, so `host.docker.internal` resolves to the host on every OS, including Linux and WSL:

    | Where `back/` runs | `BACK_BASE_URL` value |
    |--------------------|----------------------|
    | On the host (pnpm start:dev, or a container that publishes its port) | `http://host.docker.internal:<port>` |

    The compose file joins only the `default` network, not `back_default`, so a `back/` service name isn't resolvable from `mcp-server` — publish `back/`'s port to the host and use `host.docker.internal`.

    Set `<port>` to the port your `back/` actually listens on. `.env.example` ships `http://host.docker.internal:3000`, but the workspace stack runs `back/` on **3001** — change it if that's your setup, or every call fails with `503 upstream_unavailable`.
    </Note>
  </Tab>
  <Tab title="Option B — Standalone (pnpm start:dev)">
    Requires pnpm and Node ≥ 22.13 installed on the host.

    ```bash
    cp .env.example .env
    # Set BACK_BASE_URL=http://localhost:<back-port>
    pnpm install
    pnpm start:dev        # watch mode — reloads on save
    ```

    The server listens on `http://localhost:3100` by default.
  </Tab>
</Tabs>

### Minimal `.env` for local work

```env
PORT=3100
NODE_ENV=development

BACK_BASE_URL=http://host.docker.internal:3001   # Docker; use http://localhost:3001 for pnpm
MCP_INTERNAL_SECRET=<same value as in back/.env>

MCP_KILL_SWITCH=off

# Leave blank to skip Datadog writes locally
DATADOG_API_KEY=
```

`MCP_INTERNAL_SECRET` must match the value set in `back/`'s `.env`. It is the secret `mcp-server` uses to call `back/` — it is **not** a client token, and sending it as `Authorization: Bearer ...` returns `401 invalid_token`.

See [Environment variables](/mcp/environment-variables) for the full list.

### Check that the server is up

```bash
curl -s http://localhost:3100/healthz
curl -s http://localhost:3100/readyz
```

The health endpoints are `/healthz` and `/readyz` (there is no `/health`).

### Get a client credential

Local `mcp-server` resolves every client token through `back/`, and `back/` only accepts a token that has an **active workspace binding**. The old helper script `back/scripts/create-dev-mcp-token.mjs` inserts a row into `mcp_tokens` without that binding, so its `mcp_dev_local` token is rejected with `401 invalid_token`. Don't use it.

Use one of these instead:

<Steps>
  <Step title="Generate an MCP key in the local front">
    Open `http://localhost:3000`, go to **Settings → MCP Keys** (or open `http://localhost:3000/dashboard-beta?settings=mcpTokens`), and click **Generate key**. Copy the key that starts with `mcp_` and use it as `Authorization: Bearer <key>`.
  </Step>
  <Step title="Or use OAuth">
    Clients that support OAuth (Claude Desktop, Claude Code, MCP Inspector's OAuth flow) need no key. Set up [Local OAuth](#local-oauth) and let the client run the consent screen.
  </Step>
</Steps>

<Note>
Keys are created against the database your local `back/` uses, so the key only works with a local `mcp-server` that points at that same `back/`.
</Note>

## Step 2 — Test with MCP Inspector

<Tabs>
  <Tab title="Docker Compose (Option A)">
    The Inspector is not part of the Docker Compose stack (see the note in [Step 1](#step-1-start-the-server)) — run it on the host the same way as Option B, connecting to the port Docker published:

    | Field | Value |
    |-------|-------|
    | Transport | Streamable HTTP |
    | URL | `http://localhost:3100/mcp` |
    | Header | `Authorization: Bearer <your MCP key>` |

    Follow the **Standalone (Option B)** tab for the exact steps — switch to Streamable HTTP, set the URL above, add the header, then **Connect**.
  </Tab>
  <Tab title="Standalone (Option B)">
    [MCP Inspector](https://github.com/modelcontextprotocol/inspector) runs directly on the host. From `mcp-server/`, the repo script starts a pinned version bound to `127.0.0.1` with the browser auto-open disabled and the Inspector proxy's own auth turned off (`DANGEROUSLY_OMIT_AUTH=true`, local use only) — its UI is on port `5173`:

    ```bash
    pnpm inspect
    ```

    Or run the Inspector yourself. Run it **without arguments** — passing a URL directly makes it treat the URL as a stdio process to spawn, which fails for HTTP servers:

    ```bash
    npx @modelcontextprotocol/inspector
    ```

    The `npx` command opens the web UI at `http://localhost:6274`.

    <Steps>
      <Step title="Switch to Streamable HTTP transport">
        In the **Transport Type** dropdown, change `STDIO` to `Streamable HTTP`.
      </Step>
      <Step title="Set the server URL">
        Enter `http://localhost:3100/mcp` in the URL field.
      </Step>
      <Step title="Add the Authorization header">
        In the **Headers** panel, add:

        ```
        Authorization: Bearer <your MCP key>
        ```
      </Step>
      <Step title="Connect and explore">
        Click **Connect**, then **Tools → List**. You see the full tool catalog (about 30 tools) — see the [tools pages](/mcp/tools/agents-and-folders) for what each one does. Select any tool and click **Call** to see the raw JSON-RPC request and response.
      </Step>
    </Steps>
  </Tab>
</Tabs>

## Step 3 — Test with Claude Desktop

Claude Desktop authenticates with **OAuth only** — it does not support custom headers in its config file, so there is nowhere to put a token. Complete [Local OAuth](#local-oauth) first, then register the server. See also [Authentication](/mcp/authentication).

### Option A — Register with one command

From the `mcp-server/` directory (server must already be running):

```bash
pnpm claude:register
```

This script reads `PORT` from `.env` (used only when you don't pass `--url`) and writes the
`fluxprompt-mcp` entry — `{ "url": "<target>" }`, with no `Authorization` header, since Claude Desktop's
config doesn't support one — into `claude_desktop_config.json`. It is idempotent — running it again
with the same URL prints the current state and exits without changes.

After running, **fully restart Claude Desktop**. The `fluxprompt-mcp` entry appears in the tools panel (hammer icon), and Claude Desktop starts the OAuth flow on first use.

### Option B — Edit the config file manually

<Steps>
  <Step title="Open the Claude Desktop config file">
    | OS | Path |
    |----|------|
    | **macOS** | `~/Library/Application Support/Claude/claude_desktop_config.json` |
    | **Windows** | `%APPDATA%\Claude\claude_desktop_config.json` |
    | **Linux** | `~/.config/Claude/claude_desktop_config.json` |

    Create the file if it doesn't exist.
  </Step>
  <Step title="Add the local server entry">
    ```json
    {
      "mcpServers": {
        "fluxprompt-local": {
          "url": "http://localhost:3100/mcp"
        }
      }
    }
    ```

    Don't add a `headers` block — Claude Desktop ignores custom headers and signs in through OAuth.

    <Warning>
    If the file already has an `mcpServers` key, add `"fluxprompt-local": { ... }` inside it — do not create a second `mcpServers` block.
    </Warning>
  </Step>
  <Step title="Restart Claude Desktop">
    Fully quit Claude Desktop and reopen it. The **fluxprompt-local** entry appears in the tools panel (hammer icon).
  </Step>
  <Step title="Ask Claude to use a tool">
    Try: *"List my FluxPrompt agents"* or *"What node types are available in FluxPrompt?"*
  </Step>
</Steps>

<Note>
Clients that do accept headers (Claude Code, Cursor, the Inspector, `curl`) can send `Authorization: Bearer <your MCP key>` instead of using OAuth.
</Note>

## Local OAuth

To run the OAuth consent flow against your local stack, configure these values:

| Where | Variable | Local value |
|-------|----------|-------------|
| `mcp-server` | `MCP_PUBLIC_URL` | The origin clients reach the server on, without `/mcp` — `http://localhost:3100`, or your tunnel origin |
| `mcp-server` and `back` | `MCP_OAUTH_CONSENT_SECRET` | The **same** value on both — otherwise the consent signature fails |
| `mcp-server` | `MCP_FRONT_CONSENT_URL` | `http://localhost:3000/mcp-authorize.html` |
| `front` | `VITE_MCP_SERVER_URL` | `http://localhost:3100/mcp` (build-time — restart the Vite dev server after changing it) |

<Warning>
`MCP_FRONT_CONSENT_URL` defaults to `http://localhost:5173/mcp/authorize` in the code and in `.env.example`, but the front doesn't serve that path. The front serves the consent page as `mcp-authorize.html` on port `3000`, so set the value above or the consent redirect lands on a page that doesn't exist.
</Warning>

Restart `mcp-server` after editing its `.env`. `back/` also needs `MCP_SERVER_INTERNAL_URL` and `MCP_RESOURCE_METADATA_URL` — see [Main API environment variables](/main-api/environment-variables).

## Tunnels

Claude Desktop, Claude.ai and any remote client can't reach `localhost`. Expose the server through a tunnel — both **ngrok** and **cloudflared** (`trycloudflare.com` quick tunnels) work.

Quick tunnels get a **new URL every time you start them**. When the public URL changes, update three values together:

| Value | Where | Format |
|-------|-------|--------|
| Client config URL | e.g. the `fluxprompt-mcp-local` entry in `~/.claude.json` | Origin **plus** `/mcp` |
| `VITE_MCP_SERVER_URL` | `front/.env` (build-time) | Origin **plus** `/mcp` |
| `MCP_PUBLIC_URL` | `mcp-server/.env` | Bare origin, **no** `/mcp` |

Then restart the front and `mcp-server`, and reconnect the client. If they disagree, OAuth discovery returns an issuer that doesn't match the URL the client used and the sign-in fails.

<Tip>
The workspace has a `mcp-tunnel-url` skill that updates all three files in one step (`.claude/skills/mcp-tunnel-url/switch.sh --tunnel "<url>"`, or `--local` to go back to localhost). It edits files only — you restart the services yourself.
</Tip>

For ngrok's free tier, send the `ngrok-skip-browser-warning: 1` header on every request — see [Troubleshooting](#troubleshooting). cloudflared needs no extra header.

## Quick curl smoke test

```bash
curl -s -X POST http://localhost:3100/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer <your MCP key>" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

A working setup returns a JSON-RPC `result.tools` array with the full tool catalog (about 30 tools). `tools/list` isn't filtered by scope, so an empty list is not a permissions problem.

## Run the test suite

```bash
pnpm test              # unit tests — fast, no network
pnpm test:e2e          # e2e tests — Supertest, in-process server
npx tsc --noEmit       # type check
```

All three must pass before any commit.

## Troubleshooting

<AccordionGroup>
  <Accordion title="401 Unauthorized">
    The response body has a `reason`:

    - `missing_token` — no `Authorization: Bearer ...` header.
    - `invalid_token` — the token isn't accepted: it's unknown, revoked, expired, or has no **active workspace binding**. A row inserted by hand into `mcp_tokens` (including the old `mcp_dev_local` script) has no binding and always fails. `MCP_INTERNAL_SECRET` is not a client token either.

    Generate a new key under **MCP Keys** in the local front (see [Get a client credential](#get-a-client-credential)). Note that `mcp-server` caches token lookups for `MCP_TOKEN_CACHE_TTL` seconds.
  </Accordion>
  <Accordion title='"Service disabled" error (-32005)'>
    `MCP_KILL_SWITCH=on` is set in your `.env`. Change it to `off` and restart.
  </Accordion>
  <Accordion title="503 upstream_unavailable / cannot reach back/ (ECONNREFUSED)">
    `mcp-server` couldn't reach `back/`, so it answers `503` with `reason: "upstream_unavailable"`. `BACK_BASE_URL` points to a host or port that isn't running. If `mcp-server` runs in Docker, use `http://host.docker.internal:<port>` (not `http://localhost:...`) and make sure `<port>` is the one your `back/` listens on (`.env.example` says `3000`; the workspace stack uses `3001`). If running standalone, start your local `back/` instance.
  </Accordion>
  <Accordion title="502 upstream_auth_rejected">
    `MCP_INTERNAL_SECRET` differs between `mcp-server` and `back/`. Set the same value on both and restart `mcp-server`.
  </Accordion>
  <Accordion title="Inspector shows ECONNREFUSED or won't connect">
    The Inspector runs on the host (see [Step 2](#step-2-test-with-mcp-inspector)), not inside Docker
    Compose — the `inspector:` service in `docker-compose.yml` is commented out. Make sure you started
    it on the host, and that the URL you gave it is `http://localhost:3100/mcp` (the port Docker
    publishes `mcp-server` on).
  </Accordion>
  <Accordion title="OAuth consent page doesn't load or the sign-in fails">
    Check [Local OAuth](#local-oauth): `MCP_FRONT_CONSENT_URL` must be `http://localhost:3000/mcp-authorize.html`, `MCP_OAUTH_CONSENT_SECRET` must be identical on `mcp-server` and `back`, and `MCP_PUBLIC_URL` / `VITE_MCP_SERVER_URL` must point at the same origin the client uses (see [Tunnels](#tunnels)).
  </Accordion>
  <Accordion title='Exposing the server via ngrok — responses come back as HTML ("Unexpected content type: text/html")'>
    When you tunnel the local server through **ngrok** (free tier), ngrok serves its browser-warning interstitial page (HTTP 200, `Content-Type: text/html`) instead of proxying to the MCP server. The MCP client then fails with `Unexpected content type: text/html`.

    Send the skip header on every request — and note the value must be **`1`**, not `true` (ngrok only honors `1`):

    ```
    ngrok-skip-browser-warning: 1
    ```

    In a config that supports headers (for example a Claude Code entry in `~/.claude.json`), add it alongside `Authorization`:

    ```json
    "headers": {
      "Authorization": "Bearer <token>",
      "ngrok-skip-browser-warning": "1"
    }
    ```

    Claude Desktop can't send custom headers, so use cloudflared, or let ngrok inject the header for you (`ngrok http 3100 --request-header-add "ngrok-skip-browser-warning: 1"`).

    Verify with curl (note the value `1`):

    ```bash
    curl -s -X POST https://<your-subdomain>.ngrok-free.dev/mcp \
      -H "Authorization: Bearer <token>" \
      -H "ngrok-skip-browser-warning: 1" \
      -H "Content-Type: application/json" \
      -H "Accept: application/json, text/event-stream" \
      -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
    ```

    A correct response has `Content-Type: text/event-stream`. If you still get `text/html`, the header value is wrong (`true` instead of `1`) or missing.
  </Accordion>
</AccordionGroup>
