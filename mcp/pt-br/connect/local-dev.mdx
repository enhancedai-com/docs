## Visão geral

O servidor MCP usa Streamable HTTP, que funciona normalmente no `localhost`. Você não precisa de um transport separado para desenvolvimento local — o mesmo endpoint que vai para staging e produção funciona durante o desenvolvimento.

As duas ferramentas recomendadas são:

| Ferramenta | Melhor para |
|------------|-------------|
| **MCP Inspector** | Explorar tools, inspecionar JSON-RPC bruto, iteração rápida |
| **Claude Desktop** | Teste end-to-end exatamente como um usuário real experimenta (OAuth) |

## Pré-requisitos

- Node.js ≥ 22.13 e pnpm ≥ 11 **ou** Docker Desktop (veja a opção A abaixo)
- `mcp-server/` clonado
- Uma instância local do `back/` rodando (ou túnel para o ambiente dev)
- O front local (`front/`, em `http://localhost:3000`) rodando, para você gerar uma **chave MCP** (veja [Obter uma credencial de cliente](#obter-uma-credencial-de-cliente)) ou concluir a tela de consentimento OAuth

## Passo 1 — Iniciar o servidor

Escolha uma das opções. Docker Compose é recomendado para novos colaboradores — sem necessidade de instalar Node/pnpm no host.

<Tabs>
  <Tab title="Opção A — Docker Compose (recomendado)">
    Inicia apenas o `mcp-server` — sem necessidade de instalar Node/pnpm no host.

    ```bash
    cp .env.example .env
    # Preencha BACK_BASE_URL e MCP_INTERNAL_SECRET (veja abaixo)
    docker compose up
    ```

    O servidor escuta em **http://localhost:3100** (porta publicada pelo container).

    <Note>
    **Imagem arm64 em host x86.** A imagem do compose é construída para `linux/arm64` para espelhar a produção (AWS Fargate Graviton). Em uma máquina x86 ela roda sob emulação QEMU — instale o emulador uma única vez:

    ```bash
    docker run --privileged --rm tonistiigi/binfmt --install arm64
    ```
    </Note>

    <Note>
    **O MCP Inspector não roda no Docker Compose.** O serviço `inspector:` no `docker-compose.yml`
    está definido mas comentado — dentro do Docker o issuer OAuth dele (`http://mcp-server:3100`) não
    bateria com o `localhost` que o navegador e os redirects usam, então ele não funciona ali. Rode o
    Inspector no host, tanto com o `mcp-server` no Docker (esta opção) quanto standalone (Opção B) — veja
    o [Passo 2](#passo-2-testar-com-o-mcp-inspector).
    </Note>

    <Note>
    **`BACK_BASE_URL` no Docker** — o container não consegue usar `localhost` para alcançar a sua máquina, porque dentro de um container `localhost` é o próprio container. O arquivo compose já adiciona `extra_hosts: ["host.docker.internal:host-gateway"]`, então `host.docker.internal` resolve para o host em qualquer SO, inclusive Linux e WSL:

    | Onde o `back/` roda | Valor de `BACK_BASE_URL` |
    |---------------------|--------------------------|
    | No host (pnpm start:dev, ou um container que publica a porta) | `http://host.docker.internal:<porta>` |

    O compose entra apenas na rede `default`, não na `back_default`, então o nome de serviço do `back/` não é resolvível a partir do `mcp-server` — publique a porta do `back/` no host e use `host.docker.internal`.

    Defina `<porta>` como a porta em que o seu `back/` realmente escuta. O `.env.example` vem com `http://host.docker.internal:3000`, mas a stack do workspace roda o `back/` na **3001** — troque se for o seu caso, senão toda chamada falha com `503 upstream_unavailable`.
    </Note>
  </Tab>
  <Tab title="Opção B — Standalone (pnpm start:dev)">
    Requer pnpm e Node ≥ 22.13 instalados no host.

    ```bash
    cp .env.example .env
    # Defina BACK_BASE_URL=http://localhost:<porta-do-back>
    pnpm install
    pnpm start:dev        # modo watch — reinicia ao salvar
    ```

    O servidor escuta em `http://localhost:3100` por padrão.
  </Tab>
</Tabs>

### `.env` mínimo para trabalho local

```env
PORT=3100
NODE_ENV=development

BACK_BASE_URL=http://host.docker.internal:3001   # Docker; use http://localhost:3001 com pnpm
MCP_INTERNAL_SECRET=<mesmo valor do back/.env>

MCP_KILL_SWITCH=off

# Deixe vazio para não escrever no Datadog localmente
DATADOG_API_KEY=
```

`MCP_INTERNAL_SECRET` precisa ser igual ao valor no `.env` do `back/`. É o segredo que o `mcp-server` usa para chamar o `back/` — **não** é um token de cliente, e enviá-lo como `Authorization: Bearer ...` retorna `401 invalid_token`.

Veja [Variáveis de ambiente](/mcp/pt-br/environment-variables) para a lista completa.

### Verifique se o servidor está no ar

```bash
curl -s http://localhost:3100/healthz
curl -s http://localhost:3100/readyz
```

Os endpoints de saúde são `/healthz` e `/readyz` (não existe `/health`).

### Obter uma credencial de cliente

O `mcp-server` local resolve todo token de cliente através do `back/`, e o `back/` só aceita um token que tenha um **vínculo ativo com um workspace**. O antigo script auxiliar `back/scripts/create-dev-mcp-token.mjs` insere uma linha em `mcp_tokens` sem esse vínculo, então o token `mcp_dev_local` dele é rejeitado com `401 invalid_token`. Não use.

Use uma destas opções:

<Steps>
  <Step title="Gere uma chave MCP no front local">
    Abra `http://localhost:3000`, vá em **Settings → MCP Keys** (ou abra `http://localhost:3000/dashboard-beta?settings=mcpTokens`) e clique em **Generate key**. Copie a chave que começa com `mcp_` e use como `Authorization: Bearer <chave>`.
  </Step>
  <Step title="Ou use OAuth">
    Clientes com suporte a OAuth (Claude Desktop, Claude Code, fluxo OAuth do MCP Inspector) não precisam de chave. Configure o [OAuth local](#oauth-local) e deixe o cliente executar a tela de consentimento.
  </Step>
</Steps>

<Note>
As chaves são criadas no banco que o seu `back/` local usa, então a chave só funciona com um `mcp-server` local apontando para esse mesmo `back/`.
</Note>

## Passo 2 — Testar com o MCP Inspector

<Tabs>
  <Tab title="Docker Compose (Opção A)">
    O Inspector não faz parte da stack do Docker Compose (veja a nota no [Passo 1](#passo-1-iniciar-o-servidor)) — rode-o no host da mesma forma que na Opção B, conectando na porta publicada pelo Docker:

    | Campo | Valor |
    |-------|-------|
    | Transport | Streamable HTTP |
    | URL | `http://localhost:3100/mcp` |
    | Header | `Authorization: Bearer <sua chave MCP>` |

    Siga a aba **Standalone (Opção B)** para os passos exatos — troque para Streamable HTTP, defina a URL acima, adicione o header e clique em **Connect**.
  </Tab>
  <Tab title="Standalone (Opção B)">
    O [MCP Inspector](https://github.com/modelcontextprotocol/inspector) roda direto no host. A partir de `mcp-server/`, o script do repositório inicia uma versão fixada, ligada a `127.0.0.1`, com a abertura automática do navegador desativada e a autenticação do proxy do próprio Inspector desligada (`DANGEROUSLY_OMIT_AUTH=true`, apenas uso local) — a UI fica na porta `5173`:

    ```bash
    pnpm inspect
    ```

    Ou rode o Inspector por conta própria. Rode **sem argumentos** — passar uma URL diretamente faz o Inspector tratá-la como um processo stdio a ser iniciado, o que falha para servidores HTTP:

    ```bash
    npx @modelcontextprotocol/inspector
    ```

    O comando `npx` abre a UI web em `http://localhost:6274`.

    <Steps>
      <Step title="Troque para o transport Streamable HTTP">
        No dropdown **Transport Type**, mude `STDIO` para `Streamable HTTP`.
      </Step>
      <Step title="Defina a URL do servidor">
        Digite `http://localhost:3100/mcp` no campo de URL.
      </Step>
      <Step title="Adicione o header Authorization">
        No painel **Headers**, adicione:

        ```
        Authorization: Bearer <sua chave MCP>
        ```
      </Step>
      <Step title="Conecte e explore">
        Clique em **Connect** e depois em **Tools → List**. Você vê o catálogo completo de tools (cerca de 30) — veja as [páginas de tools](/mcp/pt-br/tools/agents-and-folders) para o que cada uma faz. Selecione qualquer tool e clique em **Call** para ver a requisição e a resposta JSON-RPC brutas.
      </Step>
    </Steps>
  </Tab>
</Tabs>

## Passo 3 — Testar com o Claude Desktop

O Claude Desktop autentica **somente com OAuth** — ele não suporta headers personalizados no arquivo de configuração, então não há onde colocar um token. Conclua o [OAuth local](#oauth-local) primeiro e depois registre o servidor. Veja também [Autenticação](/mcp/pt-br/authentication).

### Opção A — Registrar com um comando

A partir do diretório `mcp-server/` (o servidor já precisa estar rodando):

```bash
pnpm claude:register
```

Este script lê `PORT` do `.env` (usado apenas quando você não passa `--url`) e escreve a entrada
`fluxprompt-mcp` — `{ "url": "<destino>" }`, sem header `Authorization`, já que a configuração do
Claude Desktop não suporta um — no `claude_desktop_config.json`. É idempotente — rodar de novo com a
mesma URL mostra o estado atual e sai sem alterações.

Depois de rodar, **reinicie completamente o Claude Desktop**. A entrada `fluxprompt-mcp` aparece no painel de tools (ícone de martelo), e o Claude Desktop inicia o fluxo OAuth no primeiro uso.

### Opção B — Editar o arquivo de configuração manualmente

<Steps>
  <Step title="Abra o arquivo de configuração do Claude Desktop">
    | SO | Caminho |
    |----|---------|
    | **macOS** | `~/Library/Application Support/Claude/claude_desktop_config.json` |
    | **Windows** | `%APPDATA%\Claude\claude_desktop_config.json` |
    | **Linux** | `~/.config/Claude/claude_desktop_config.json` |

    Crie o arquivo se ele não existir.
  </Step>
  <Step title="Adicione a entrada do servidor local">
    ```json
    {
      "mcpServers": {
        "fluxprompt-local": {
          "url": "http://localhost:3100/mcp"
        }
      }
    }
    ```

    Não adicione um bloco `headers` — o Claude Desktop ignora headers personalizados e faz login via OAuth.

    <Warning>
    Se o arquivo já tiver uma chave `mcpServers`, adicione `"fluxprompt-local": { ... }` dentro dela — não crie um segundo bloco `mcpServers`.
    </Warning>
  </Step>
  <Step title="Reinicie o Claude Desktop">
    Feche completamente o Claude Desktop e reabra. A entrada **fluxprompt-local** aparece no painel de tools (ícone de martelo).
  </Step>
  <Step title="Peça ao Claude para usar uma tool">
    Tente: *"Liste meus agentes do FluxPrompt"* ou *"Quais tipos de node estão disponíveis no FluxPrompt?"*
  </Step>
</Steps>

<Note>
Clientes que aceitam headers (Claude Code, Cursor, o Inspector, `curl`) podem enviar `Authorization: Bearer <sua chave MCP>` em vez de usar OAuth.
</Note>

## OAuth local

Para rodar o fluxo de consentimento OAuth contra a sua stack local, configure estes valores:

| Onde | Variável | Valor local |
|------|----------|-------------|
| `mcp-server` | `MCP_PUBLIC_URL` | A origem pela qual os clientes alcançam o servidor, sem `/mcp` — `http://localhost:3100` ou a origem do seu túnel |
| `mcp-server` e `back` | `MCP_OAUTH_CONSENT_SECRET` | O **mesmo** valor nos dois — senão a assinatura do consentimento falha |
| `mcp-server` | `MCP_FRONT_CONSENT_URL` | `http://localhost:3000/mcp-authorize.html` |
| `front` | `VITE_MCP_SERVER_URL` | `http://localhost:3100/mcp` (em tempo de build — reinicie o servidor Vite depois de mudar) |

<Warning>
`MCP_FRONT_CONSENT_URL` tem como padrão `http://localhost:5173/mcp/authorize` no código e no `.env.example`, mas o front não serve esse caminho. O front serve a página de consentimento como `mcp-authorize.html` na porta `3000`, então defina o valor acima, senão o redirect de consentimento cai em uma página que não existe.
</Warning>

Reinicie o `mcp-server` depois de editar o `.env` dele. O `back/` também precisa de `MCP_SERVER_INTERNAL_URL` e `MCP_RESOURCE_METADATA_URL` — veja [Variáveis de ambiente da API principal](/main-api/pt-br/environment-variables).

## Túneis

Claude Desktop, Claude.ai e qualquer cliente remoto não alcançam o `localhost`. Exponha o servidor por um túnel — tanto o **ngrok** quanto o **cloudflared** (quick tunnels `trycloudflare.com`) funcionam.

Quick tunnels recebem uma **URL nova a cada vez que você os inicia**. Quando a URL pública muda, atualize três valores juntos:

| Valor | Onde | Formato |
|-------|------|---------|
| URL na config do cliente | ex.: a entrada `fluxprompt-mcp-local` em `~/.claude.json` | Origem **mais** `/mcp` |
| `VITE_MCP_SERVER_URL` | `front/.env` (em tempo de build) | Origem **mais** `/mcp` |
| `MCP_PUBLIC_URL` | `mcp-server/.env` | Origem pura, **sem** `/mcp` |

Depois reinicie o front e o `mcp-server` e reconecte o cliente. Se os valores divergirem, a descoberta OAuth retorna um issuer que não bate com a URL que o cliente usou e o login falha.

<Tip>
O workspace tem uma skill `mcp-tunnel-url` que atualiza os três arquivos de uma vez (`.claude/skills/mcp-tunnel-url/switch.sh --tunnel "<url>"`, ou `--local` para voltar ao localhost). Ela só edita arquivos — você reinicia os serviços por conta própria.
</Tip>

No plano gratuito do ngrok, envie o header `ngrok-skip-browser-warning: 1` em toda requisição — veja [Solução de problemas](#solução-de-problemas). O cloudflared não precisa de header extra.

## Teste rápido com curl

```bash
curl -s -X POST http://localhost:3100/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer <sua chave MCP>" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

Uma configuração funcionando retorna um array JSON-RPC `result.tools` com o catálogo completo de tools (cerca de 30). O `tools/list` não é filtrado por escopo, então uma lista vazia não é problema de permissão.

## Rodar a suíte de testes

```bash
pnpm test              # testes unitários — rápidos, sem rede
pnpm test:e2e          # testes e2e — Supertest, servidor in-process
npx tsc --noEmit       # checagem de tipos
```

Os três precisam passar antes de qualquer commit.

## Solução de problemas

<AccordionGroup>
  <Accordion title="401 Unauthorized">
    O corpo da resposta tem um `reason`:

    - `missing_token` — não há header `Authorization: Bearer ...`.
    - `invalid_token` — o token não é aceito: é desconhecido, foi revogado, expirou ou não tem **vínculo ativo com um workspace**. Uma linha inserida à mão em `mcp_tokens` (inclusive o antigo script `mcp_dev_local`) não tem vínculo e sempre falha. `MCP_INTERNAL_SECRET` também não é um token de cliente.

    Gere uma nova chave em **MCP Keys** no front local (veja [Obter uma credencial de cliente](#obter-uma-credencial-de-cliente)). Lembre que o `mcp-server` mantém em cache a resolução de tokens por `MCP_TOKEN_CACHE_TTL` segundos.
  </Accordion>
  <Accordion title='Erro "Service disabled" (-32005)'>
    `MCP_KILL_SWITCH=on` está definido no seu `.env`. Mude para `off` e reinicie.
  </Accordion>
  <Accordion title="503 upstream_unavailable / não alcança o back/ (ECONNREFUSED)">
    O `mcp-server` não conseguiu alcançar o `back/`, então responde `503` com `reason: "upstream_unavailable"`. `BACK_BASE_URL` aponta para um host ou porta que não está rodando. Se o `mcp-server` roda no Docker, use `http://host.docker.internal:<porta>` (não `http://localhost:...`) e confirme que `<porta>` é a que o seu `back/` escuta (o `.env.example` diz `3000`; a stack do workspace usa `3001`). Se roda standalone, inicie a sua instância local do `back/`.
  </Accordion>
  <Accordion title="502 upstream_auth_rejected">
    `MCP_INTERNAL_SECRET` é diferente entre o `mcp-server` e o `back/`. Defina o mesmo valor nos dois e reinicie o `mcp-server`.
  </Accordion>
  <Accordion title="O Inspector mostra ECONNREFUSED ou não conecta">
    O Inspector roda no host (veja o [Passo 2](#passo-2-testar-com-o-mcp-inspector)), não dentro do Docker
    Compose — o serviço `inspector:` no `docker-compose.yml` está comentado. Confirme que você o iniciou
    no host e que a URL informada é `http://localhost:3100/mcp` (a porta em que o Docker publica o
    `mcp-server`).
  </Accordion>
  <Accordion title="A página de consentimento OAuth não carrega ou o login falha">
    Confira o [OAuth local](#oauth-local): `MCP_FRONT_CONSENT_URL` precisa ser `http://localhost:3000/mcp-authorize.html`, `MCP_OAUTH_CONSENT_SECRET` precisa ser idêntico no `mcp-server` e no `back`, e `MCP_PUBLIC_URL` / `VITE_MCP_SERVER_URL` precisam apontar para a mesma origem que o cliente usa (veja [Túneis](#túneis)).
  </Accordion>
  <Accordion title='Expondo o servidor via ngrok — respostas voltam como HTML ("Unexpected content type: text/html")'>
    Quando você expõe o servidor local pelo **ngrok** (plano gratuito), o ngrok serve a página intersticial de aviso do navegador (HTTP 200, `Content-Type: text/html`) em vez de repassar para o servidor MCP. O cliente MCP então falha com `Unexpected content type: text/html`.

    Envie o header de bypass em toda requisição — e note que o valor precisa ser **`1`**, não `true` (o ngrok só respeita `1`):

    ```
    ngrok-skip-browser-warning: 1
    ```

    Em uma configuração que suporta headers (por exemplo uma entrada do Claude Code em `~/.claude.json`), adicione-o junto com `Authorization`:

    ```json
    "headers": {
      "Authorization": "Bearer <token>",
      "ngrok-skip-browser-warning": "1"
    }
    ```

    O Claude Desktop não envia headers personalizados, então use o cloudflared, ou deixe o ngrok injetar o header (`ngrok http 3100 --request-header-add "ngrok-skip-browser-warning: 1"`).

    Verifique com curl (note o valor `1`):

    ```bash
    curl -s -X POST https://<seu-subdominio>.ngrok-free.dev/mcp \
      -H "Authorization: Bearer <token>" \
      -H "ngrok-skip-browser-warning: 1" \
      -H "Content-Type: application/json" \
      -H "Accept: application/json, text/event-stream" \
      -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
    ```

    Uma resposta correta tem `Content-Type: text/event-stream`. Se você ainda recebe `text/html`, o valor do header está errado (`true` em vez de `1`) ou ausente.
  </Accordion>
</AccordionGroup>
