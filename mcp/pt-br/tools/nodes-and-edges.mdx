## Descrição

Estas ferramentas constroem o agente em si. Leia [escrevendo com segurança](/mcp/pt-br/tools/writing-safely)
primeiro — tudo aqui é dry-run por padrão e aceita `expectedVersion` e `versionId`.

Antes de escrever um node, busque o schema dele com `get_node_type`. O formato de `data` é específico
por tipo, e um campo que *parece* plausível mas não existe é gravado sem erro e depois ignorado na
execução.

## `list_node_types`

Um resumo leve de cada tipo de node — `type`, `label`, `category` e `description`, e **nenhum schema e
nenhum handle**. Busque uma vez para descobrir os nomes exatos dos tipos e depois chame o
[`get_node_type`](#get_node_type) para cada tipo que você vai construir. Não escreva um node só a
partir do resumo.

### Entrada

Nenhum parâmetro necessário. Assim como o `get_node_type`, não recebe `workspaceId`.

### Saída

```json
{
  "nodeTypes": [
    {
      "type": "commandTextNode",
      "label": "Command Text Node",
      "description": "Runs a prompt against an AI text model and passes the result downstream.",
      "category": "AI"
    },
    {
      "type": "conditionNode",
      "label": "Condition Node",
      "description": "Evaluates a condition and routes flow execution along the true or false branch.",
      "category": "Logic"
    }
  ]
}
```

#### Campos da saída

| Campo | Tipo | Descrição |
|-------|------|-----------|
| `nodeTypes` | array | Lista completa de tipos de node. |
| `nodeTypes[].type` | string | Identificador legível por máquina (camelCase, ex.: `commandTextNode`). Corresponde ao campo `type` nos objetos de node do `get_agent`. |
| `nodeTypes[].label` | string | Nome legível por humanos, composto como `"Nome front (Nome técnico)"` quando o nome do canvas e o nome técnico diferem — ex.: `"Display Box (Output Controller)"` — ou publicado como apenas um dos dois quando coincidem ou o tipo não tem entrada no sidebar. Essa string exata, e o nome front isolado, também são entrada válida para o `node.type` do [`add_node`](#add_node) e para o `type` do [`get_node_type`](#get_node_type). |
| `nodeTypes[].description` | string | O que este node faz. |
| `nodeTypes[].category` | string | Agrupamento: `Input/Output`, `AI`, `Data`, `Logic`, `Utility`, `Integration`. |

<Note>
  Os schemas ficam atrás do [`get_node_type`](#get_node_type). O
  [resource](/mcp/pt-br/tools/prompts-and-resources#resources) `fluxprompt://node-types` é a exceção:
  ele retorna as entradas completas, com schemas e handles.
</Note>

## `get_node_type`

Retorna a definição completa de um tipo de node: `type`, `label`, `description`, `category`,
`inputSchema`, `outputSchema` e `handles`. Chame uma vez por tipo de node que você usa, e antes de ligar com o
[`connect_nodes`](#connect_nodes). Para buscar todos os schemas de uma vez, leia o resource
[`fluxprompt://node-types`](/mcp/pt-br/tools/prompts-and-resources#resources).

| Parâmetro | Tipo | Obrigatório | Descrição |
|-----------|------|-------------|-----------|
| `type` | string | Sim | O tipo técnico (ex.: `commandTextNode`), o nome do sidebar/frontend (ex.: "Display Box"), ou o label composto que o [`list_node_types`](#list_node_types) publica (ex.: "Display Box (Output Controller)"). A comparação ignora maiúsculas/minúsculas e colapsa espaços. Um valor que não casa com nenhum dos três retorna um erro (`isError: true`) em vez de um schema. |

### O objeto `handles`

`handles` é o registro de handles derivado para o tipo — a fonte mais confiável de nomes de handles
conectáveis, muito melhor do que chutar a partir dos nomes de campo do `inputSchema`, que descrevem
dados, não ligações.

| Campo | Tipo | Descrição |
|-------|------|-----------|
| `sourceHandles` | array | `{ handle, role }` — portas de saída. `role` é `global`, `control`, `condition` ou `data`. Handles global, control e condition continuam a cadeia de execução; handles data carregam um valor. |
| `targetHandles` | array | `{ handle, dataField? }` — portas de entrada. `dataField` é o campo base do `inputSchema` que o valor da edge de entrada alimenta, quando existe. O valor cai no array companheiro `<dataField>Data`, não no próprio `dataField`. |
| `patterned` | array | `{ direction, pattern, discriminating }` — handles gerados em tempo de renderização que não dá para listar. `discriminating: false` significa que o padrão é um coringa não seletivo: indício de que existe algum handle dinâmico, não prova de nenhuma string específica. |
| `handlesPatterned` | boolean | `true` quando o tipo tem handles de renderização além das duas listas. Trate as listas como incompletas, não erradas: um handle não listado é não comprovado, não inválido. |
| `unresolved` | boolean | `true` quando não foi possível determinar os handles deste tipo. |
| `canContinueExecutionChain` | boolean | Se o tipo expõe um handle de origem que continua a cadeia de execução. Um `globalStarter` só pode conectar direto em um tipo em que isto é `true`. |

<Warning>
  **Respeite o `enum` quando o campo declarar um.** Leia o `enum` do campo no `inputSchema` e nunca
  chute um valor que pareça plausível, como `"default"`. Um valor fora da lista é gravado mesmo
  assim, reportado em `invalidEnumValues`, e o node não faz nada — se um node ficar inerte, confira o
  nome e o valor do campo. Exemplos: `dynamicSettingsNode.selectedOption` é `"text"` ou `"voice"`;
  `fluxObject.selectedType` é uma de seis strings exatas, como `"Load All Entries"`.
</Warning>

## `list_ai_models`

Retorna os modelos de IA disponíveis para o workspace, para você preencher `aiModel`/`aiSystem` de um
node de IA com um valor que existe de fato e está habilitado naquele workspace — em vez de um nome de
modelo lembrado de outro lugar.

### Entrada

| Parâmetro | Tipo | Obrigatório | Descrição |
|-----------|------|----------|-------------|
| `workspaceId` | string | Só quando esta autorização cobre mais de um workspace | Chame [`list_workspaces`](/mcp/pt-br/tools/agents-and-folders#list_workspaces) para descobrir quais workspaces esta chave cobre. |
| `cursor` | string | Não | Cursor opaco de uma resposta anterior (`nextCursor`). |

### Saída

Cada item traz `provider`, `modelName`, `displayName`, `description`, `modelType`,
`contextWindow`, `supportsVision`, `supportsReasoning`, `supportsImageOutput`,
`supportsImageGenerationTool` e uma lista `tools` derivada (por exemplo `image_generation`,
`image_output`, `web_search`, `structured_output`, `vision_input`, `reasoning`).

`supportsImageOutput` significa que o próprio modelo devolve uma imagem (um modelo nativo de imagem,
ou um modelo de chat cuja saída inclui imagens, ex. `gemini-2.5-flash-image`). `supportsImageGenerationTool`
significa que o modelo pode chamar uma tool de geração de imagem do provider a partir de uma chat
completion (ex. `gpt-5-nano`/`gpt-5.5` da OpenAI chamando `image_generation`) — são dois mecanismos
diferentes, e um modelo pode ter um, os dois, ou nenhum. `tools` é derivado desses e dos outros campos
de capacidade, não é uma fonte separada: sempre concorda com os booleanos.

```json
{
  "models": [
    {
      "provider": "openai",
      "modelName": "gpt-5-nano",
      "displayName": "GPT-5 Nano",
      "modelType": "Text",
      "supportsVision": true,
      "supportsReasoning": true,
      "supportsImageGenerationTool": true,
      "supportsImageOutput": false,
      "tools": ["image_generation", "web_search", "structured_output", "vision_input", "reasoning"]
    },
    {
      "provider": "gemini",
      "modelName": "gemini-2.5-flash-image",
      "displayName": "Gemini 2.5 Flash Image",
      "modelType": "Image",
      "supportsVision": true,
      "supportsReasoning": true,
      "supportsImageGenerationTool": false,
      "supportsImageOutput": true,
      "tools": ["image_output", "web_search", "vision_input", "reasoning"]
    }
  ],
  "total": 87
}
```

<Warning>
  Os resultados ficam em cache por um curto período e podem atrasar alguns minutos em relação a um
  admin aprovando ou alternando um modelo. Não trate um modelo listado aqui como garantia de que ele
  ainda estará disponível no momento da execução — o `run_agent` avisa se um modelo ficar indisponível.
</Warning>

## `list_voices`

Retorna as vozes que este usuário pode escolher para um `voiceBoxNode` (AI Voice Generator) — a mesma
lista que o dropdown de voz do canvas mostra. Chame antes de definir uma voz, em vez de chutar um id.
Exige o escopo `read`.

### Entrada

| Parâmetro | Tipo | Obrigatório | Descrição |
|-----------|------|-------------|-----------|
| `workspaceId` | string | Só quando esta autorização cobre mais de um workspace | Chame [`list_workspaces`](/mcp/pt-br/tools/agents-and-folders#list_workspaces) para descobrir quais workspaces esta chave cobre. |
| `provider` | `"elevenlabs"` \| `"groq"` | Não | Restringe o resultado a um provider. Omita para listar os dois. |

### Saída

```json
{
  "voices": [
    { "provider": "elevenlabs", "id": "pNInz6obpgDQGcFmaJgB", "name": "Adam", "custom": false, "isDefault": true,
      "labels": { "accent": "american", "gender": "male" } },
    { "provider": "elevenlabs", "id": "Zk3c…", "name": "My cloned voice", "custom": true, "isDefault": false, "labels": null }
  ],
  "total": 2
}
```

| Campo | Tipo | Descrição |
|-------|------|-----------|
| `voices[].provider` | `"elevenlabs"` \| `"groq"` | A qual provider a voz pertence. |
| `voices[].id` | string | O valor a definir no node. |
| `voices[].name` | string | O que mostrar ao usuário. |
| `voices[].custom` | boolean | `true` para uma voz que o usuário clonou. |
| `voices[].isDefault` | boolean | `true` para a voz padrão. |
| `voices[].labels` | object \| null | Descritores extras, como sotaque e gênero. |
| `total` | number | `voices.length`. |

A lista é pequena e retornada por inteiro — **sem paginação** e sem `cursor`. O PlayHT não é oferecido.

### Definindo a voz em um node

| `aiSystem` do node | Campo que recebe o `id` |
|--------------------|-------------------------|
| `elevenlabs` | `voiceId` |
| `groq` | `groqVoice` |

Mostre os nomes ao usuário e deixe-o escolher. Quando um node elevenlabs é escrito sem `voiceId`, o
servidor preenche a voz marcada com `isDefault` (Adam, `pNInz6obpgDQGcFmaJgB`) e informa em
`appliedDefaults`. Um node groq não recebe padrão.

<Warning>
  **`add_node` e `update_node` recusam um id de voz que o provider não conhece**, com um
  `validation_error` mandando chamar `list_voices` e usar um dos ids retornados. Sempre pegue o id
  desta lista. Se o ElevenLabs não consegue confirmar uma voz nem para um lado nem para o outro (uma
  falha de consulta diferente de "não encontrada"), a escrita é aceita e o id volta em
  `unverifiedVoices`.
</Warning>

## `list_integrations`

Retorna as conexões de terceiros que o usuário autorizador pode usar, para você preencher o
`integrationId` de um nó de integração com uma que existe **e** que esse usuário tem permissão de
alcançar — em vez de um id copiado de outro lugar.

| Parâmetro | Tipo | Obrigatório | Descrição |
|-----------|------|-------------|-----------|
| `provider` | string | Não | Restringe a um provider, ex. `hubspot`. Omita para listar todos. Um nome desconhecido retorna lista vazia. |
| `cursor` | string | Não | Cursor opaco do `nextCursor` de uma resposta anterior. |

Cada item traz `id` (o valor que o `integrationId` recebe), `name`, `provider`, `ownerUserId`,
`ownerUserName`, `isOwn`, `isSharedWithOrg` e `createdAt`. Credenciais nunca são retornadas — uma
conexão é referenciada apenas pelo id.

A lista são as conexões **próprias** do usuário mais as que um membro ativo do workspace compartilhou
com a organização. Nada além disso aparece. O usuário é quem está por trás da chave: a pessoa que
concedeu a autorização OAuth ou o membro que criou a chave de serviço. A chamada é recusada, em vez
de ampliada para o workspace inteiro, apenas quando esse usuário não é mais membro ativo do workspace
(ou quando a chave não tem nenhum usuário por trás).

<Warning>
  Escrever um `integrationId` que não está nessa lista é recusado por `add_node` e `update_node`.
  Chame esta tool primeiro em vez de reaproveitar um id visto em outro lugar — um id da conexão de
  outro usuário não é utilizável, mesmo sendo válido.
</Warning>

## Autorando um nó de integração

`thirdPartyIntegration` fala com um serviço configurado, e `hubSpotCRM` é o mesmo nó com o provider
fixo em `hubspot` — mesmos campos, mesmo motor de execução, intercambiáveis para leitura e escrita.
Seis providers executam hoje: `hubspot`, `notion`, `slack`, `stripe`, `wordpress`, `zapier`.

A ordem que funciona:

1. Escolha o `provider`.
2. Escolha o `mode` — `pull` para ler, `push` para escrever. Ausente significa pull.
3. Para um pull defina `pullObjectType`; para um push, `pushAction`. Os dois são específicos do
   provider e decidem quais dos campos restantes se aplicam, então leia-os do
   [`get_node_type`](/mcp/pt-br/tools/nodes-and-edges#get_node_type) em vez de adivinhar.
4. Defina o `integrationId` a partir do `list_integrations`.
5. Defina os campos que aquele provider e aquele objeto ou ação nomeiam.

Duas coisas que os clientes erram:

- **`providerEntry`** — só o `zapier` oferece mais de uma configuração (`zapier_pull`,
  `zapier_push`, `zapier_poll`). Vazio, o produto resolve a entrada por heurística; defina
  explicitamente para o zapier.
- **`<campo>Data`** — todo campo que aceita uma aresta de entrada tem um array companheiro com o
  mesmo nome mais `Data`, e o array **vence** o valor digitado. Deixar a referência da aresta só no
  escalar faz o valor nunca chegar. O `connect_nodes` preenche o companheiro para você.

O `blobConfig` é a saída de emergência: um objeto JSON, como string, mesclado sobre os dados do nó em
tempo de execução. Ele precisa carregar a chave `provider` ou é ignorado por completo. Prefira os
campos nomeados quando existirem.

<Note>
  Credenciais nunca são dados do nó. A conexão vive na integração salva e é selecionada pelo
  `integrationId`; nenhum segredo, URL de site ou chave de API pertence a um nó.
</Note>

## `add_node`

Adiciona um node ao agente.

| Parâmetro | Tipo | Obrigatório | Descrição |
|-----------|------|-------------|-----------|
| `agentId` | string (UUID) | Sim | Agente de destino. |
| `node` | object | Sim | Node do React-Flow: um `id` único, mais `type` e `data` conforme necessário. |

### Nomeando o tipo do node

O `node.type` aceita qualquer uma das três formas: o tipo técnico (`outputController`), o nome do
sidebar/frontend (`"Display Box"`), ou o label composto que o [`list_node_types`](#list_node_types)
publica (`"Display Box (Output Controller)"`). A comparação ignora maiúsculas/minúsculas e colapsa
espaços, então `"display box"` resolve para o mesmo tipo que `"Display Box"`.

Um valor que não casa com nenhuma das três formas é recusado com `validation_error` — inclusive uma
string que parece plausível mas simplesmente não é um tipo real.

### Não invente coordenadas

`node.position` é **opcional e resolvido pelo servidor**. A posição que você envia é uma *dica*: vence
o primeiro slot livre nela ou à direita dela, e quando você omite, o node continua o fluxo à direita
do node mais à direita. Nodes existentes nunca são movidos.

- Leia o `position` de volta na resposta — é a posição autoritativa.
- `placementAdjusted: true` significa que o servidor desviou o node de um lugar já ocupado.
- `width`/`height` são preenchidos com o tamanho medido daquele tipo de node quando você os omite.

Clientes que inventavam coordenadas redondas (`{x:0,y:0}`, `{x:100,y:100}`) sem saber as dimensões dos
nodes empilhavam todos no mesmo ponto. Omitir `position` é mais simples e melhor.

```json
// requisição — sem position
{ "agentId": "d2c2…", "node": { "id": "textgen_1", "type": "commandTextNode",
  "data": { "prompt": "Summarise the input", "aiModel": "gpt-4o", "aiSystem": "openai" } },
  "dryRun": false, "idempotencyKey": "add-textgen-1" }

// resposta — posição resolvida
{ "dryRun": false, "applied": true, "placementAdjusted": true,
  "diff": { "added": [ { "id": "textgen_1", "type": "commandTextNode",
    "position": { "x": 435, "y": -240 }, "width": 825, "height": 789 } ], "updated": [], "removed": [] } }
```

### Referenciando a saída de outro node

Nos tipos de node cuja descrição de campo no catálogo diz que sim — por exemplo `webSearch.query`,
`commandContentNode.queryData`, `voiceBoxNode.text` e `imageGenerator.prompt` — um campo string pode
embutir `{{<nodeId>.<key>}}`, e em tempo de execução o runtime substitui isso pela saída daquele node
para a `<key>` (normalmente `text`) antes de o node executar. Nem todo campo suporta isso: leia a
descrição de cada campo no [`get_node_type`](#get_node_type) antes de contar com isso. A mesma sintaxe
funciona no `patch` do [`update_node`](#update_node).

<Warning>
  O id de um node `globalStarter` **precisa** conter a substring literal `flow-global-starter` (ex.:
  `flow-global-starter_main`). O backend resolve o ponto de entrada do fluxo casando essa substring,
  então qualquer outro id é rejeitado com `validation_error` de saída.
</Warning>

<Note>
  Um agente tem **exatamente um** `globalStarter`, e o `create_agent` já o cria. Adicionar um segundo é
  recusado com `duplicate_global_starter`, que nomeia o node existente de onde conectar. Só um agente
  que não tem nenhum pode receber um.
</Note>

## `update_node`

Mescla um patch em um node existente.

| Parâmetro | Tipo | Obrigatório | Descrição |
|-----------|------|-------------|-----------|
| `agentId` | string (UUID) | Sim | Agente de destino. |
| `nodeId` | string | Sim | Node a alterar. |
| `patch` | object | Sim | Campos parciais do node. |

- Campos de topo (`type`, `position`, …) são mesclados **superficialmente**.
- `patch.data` é mesclado **um nível de profundidade**, então chaves de data omitidas são preservadas,
  não apagadas.
- Envie o mínimo: para mudar um campo, envie só aquele campo.
- O `type` de um `globalStarter` não pode ser alterado (`global_starter_not_retypable`); edite o `data` dele.

Diferente do `add_node`, o `update_node` **respeita exatamente a posição enviada** — sem resolução
anti-sobreposição. Isso é deliberado: permite que um cliente organize o fluxo de forma determinística,
node por node, sem o servidor questionar um movimento intencional.

## `remove_node`

Remove um node **e todas as edges que o tocam**. Um `globalStarter` nunca é removido
(`global_starter_not_removable`): todo agente mantém exatamente um, como no builder. Para mudar onde a
execução começa, mova a edge dele com `disconnect_nodes` e `connect_nodes`.

| Parâmetro | Tipo | Obrigatório |
|-----------|------|-------------|
| `agentId` | string (UUID) | Sim |
| `nodeId` | string | Sim |

## `connect_nodes`

Cria uma edge de um node de origem para um node de destino. Os handles são validados contra o registro
derivado dos dois tipos de node: um par `(tipo, handle)` desconhecido é recusado com
`validation_error` nomeando os handles válidos daquele tipo — chame o
[`get_node_type`](#get_node_type) e leia `handles` em vez de chutar a partir dos nomes de campo do
`inputSchema`.

| Parâmetro | Tipo | Obrigatório | Descrição |
|-----------|------|-------------|-----------|
| `agentId` | string (UUID) | Sim | Agente de destino. |
| `source` | string | Sim | Id do node de origem. |
| `target` | string | Sim | Id do node de destino. |
| `sourceHandle` | string | Não | Porta de origem. Omita para o padrão contextual (veja abaixo). Obrigatório a partir de um `conditionNode`. |
| `targetHandle` | string | Não | Porta de destino. Omita para o padrão contextual (veja abaixo). Obrigatório para dentro de um node `nodesAdd`. |
| `edgeId` | string | Não | Id explícito da edge. |

### Ordem de execução vs dados — o modelo de duas edges

Esta é a maior causa de "eu conectei, mas nada acontece":

- Uma edge de **`outputFlow` → `input`** faz o destino **executar** depois da origem. Não carrega
  dado.
- Uma edge de **`output` → `<campo>In`** (ex.: `contentIn`, `inputText`, `text-input` — o nome muda conforme o tipo de node) carrega o **dado**.
  Não dispara execução.

Encadear dois `commandTextNode` para que B rode depois de A *e* veja o texto de A exige, portanto,
**as duas** edges, cada uma com seu `edgeId`. Qualquer uma sozinha é uma meia-conexão silenciosa.

Além da edge, o `data` do destino precisa referenciar a origem — o array companheiro `<campo>Data`,
ex.: o `data.textData` de um `outputObjectNode`.

Quando o destino tem um único handle de dado alimentando um campo de texto, uma chamada com os dois
handles omitidos escreve a edge de execução, a edge de dado **e** a entrada em `<campo>Data` — por
exemplo em um `commandTextNode`, `outputObjectNode`, `textBox` ou `webSearch`. Caso contrário, só a
edge de execução é escrita e você liga a edge de dado, com `sourceHandle: "output"` e um handle de
`handles.targetHandles`. Isso nunca é feito a partir de um `globalStarter`. Confira `diff.edgesAdded`
e `diff.updated`, ou rode o [`check_agent_integrity`](/mcp/pt-br/tools/writing-safely#check_agent_integrity),
antes de alterar `<campo>Data` você mesmo — isso acrescenta uma entrada duplicada. Uma edge criada com
sucesso não agenda o destino: não leia como "o destino agora vai executar".

### Padrões de handle

Omitindo os dois handles, o servidor escolhe conforme os tipos de node. Ele só usa `outputFlow` / `input` quando o registro confirma que o tipo realmente tem esse handle, e caso contrário recusa a chamada em vez de ligar errado.

| Situação | `sourceHandle` | `targetHandle` |
|----------|----------------|----------------|
| Origem é `globalStarter` | `a` | `input` |
| Um dos lados é `mediaBox` | `mediaOutput` | `mediaInput` |
| Origem é `dynamicSettingsNode` | `outputModelTextSettings` | `modelSettings` — inclusive para dentro de um `voiceBoxNode`; recusado se o destino não tem esse handle |
| Destino é node terminal de exibição (`outputObjectNode`, `richTextBox`) | A saída de dado da origem: o primeiro entre `output`, `textOutput`, `contentOut` que ela tiver | `input` |
| Qualquer outro caso | `outputFlow`, se o tipo de origem tiver | `input`, se o tipo de destino tiver |

Dois casos exigem um handle explícito:

- A partir de um `conditionNode`, passe `sourceHandle` — `conditionHandle-T{n}`/`conditionHandle-F{n}`
  para condições SWITCH, ou `outputHandle-0`/`outputHandle-1` para condições booleanas.
- Para dentro de um node `nodesAdd`, passe `targetHandle` — `nodesInput` (payload de lista de nodes)
  ou `edgesInput` (payload de lista de edges).

## `disconnect_nodes`

Remove uma edge. Identifique-a por `edgeId`, ou por `source` + `target`.

**Uma chamada desfaz um `connect_nodes`** — as duas edges e a referência em `<campo>Data` que ele
adicionou. Leia `diff.edgesRemoved` / `diff.updated` para saber exatamente o que mudou. Isso remove
**apenas edges**; para excluir um node use `remove_node`.
