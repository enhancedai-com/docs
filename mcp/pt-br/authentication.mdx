## Dois métodos de autenticação

O servidor MCP de entrada do FluxPrompt suporta **dois** modos de autenticação. Qual deles você usa depende do seu cliente.

<Note>
**OAuth é o método recomendado para usuários e desenvolvedores em todos os ambientes** (local, dev, staging e produção); ele foi validado de ponta a ponta em todos eles. Mantenha os service tokens estáticos para clientes que só aceitam headers e para clientes máquina-a-máquina, como n8n, CI e scripts.
</Note>

| Método | Quando usar | O que você faz |
|---|---|---|
| **OAuth 2.0** | **Recomendado para todos:** Claude Desktop e Claude.ai (login do conector), Claude Code / CLI, Codex e Cursor | Adiciona a URL do servidor como conector e faz login por uma tela de consentimento do FluxPrompt — **sem token** |
| **Service token estático** | Serviços de backend / máquina-a-máquina, scripts, OpenCode, n8n e qualquer cliente que não pode ou não deve executar um fluxo de consentimento no navegador (Claude Code, Codex e Cursor também aceitam uma chave) | Gera um token e o coloca no header `Authorization` |

<Info>
**Usuários do Claude Desktop e do Claude.ai não usam token.** Eles adicionam o FluxPrompt como conector por URL HTTPS e escolhem **Sign in** (OAuth). Se algum guia mandar você colar um token ou uma URL no `claude_desktop_config.json`, ele está desatualizado — veja [Conectar Claude Desktop](/mcp/pt-br/connect/claude-desktop). O Claude Code tem seu próprio guia: [Conectar Claude Code](/mcp/pt-br/connect/claude-code).
</Info>

## Método 1 — OAuth 2.0

OAuth é a escolha certa para qualquer cliente que consegue abrir um navegador. Você nunca vê nem manipula um token.

1. No seu cliente, adicione `https://mcp.fluxprompt.ai/mcp` como conector personalizado (ou, no Claude Code, execute `claude mcp add --transport http fluxprompt https://mcp.fluxprompt.ai/mcp` e depois `/mcp` → **Authenticate**).
2. O cliente abre uma tela de login + consentimento do FluxPrompt.
3. Você faz login e vê a lista das suas **Organizations**. Todas vêm marcadas; desmarque as que você não quer liberar e clique em **Authorize** (ou **Deny**).
4. O cliente armazena a autorização resultante automaticamente.

Este é o método **recomendado** para Claude Desktop, Claude.ai, Claude Code / CLI, Codex e Cursor, em todos os ambientes. O servidor suporta client ID metadata documents (CIMD) e dynamic client registration (DCR) com PKCE `S256`, então os clientes podem se registrar sozinhos. Veja os guias por cliente para os passos exatos.

### O que uma autorização OAuth inclui

Os access tokens OAuth **não expiram**, e **não há refresh token**: o servidor só suporta o grant `authorization_code`. O cliente continua usando o mesmo token até você revogá-lo em [**Settings → MCP Keys**](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens), onde as autorizações OAuth aparecem com o tipo **OAuth**. Depois de uma revogação, reconecte o cliente para autorizar de novo.

O que a autorização pode fazer é calculado por workspace — veja [Os escopos são reduzidos pelo seu papel](#os-escopos-são-reduzidos-pelo-seu-papel) e [Uma autorização pode cobrir vários workspaces](#uma-autorização-pode-cobrir-vários-workspaces).

## Método 2 — Service token estático

Para clientes máquina-a-máquina (serviços de backend), a CLI, o Cursor e o n8n, você usa um **service token** em vez de um fluxo no navegador.

### Gerar um service token

Qualquer membro ativo de um workspace pode gerar um na interface do FluxPrompt:

1. Abra [**Settings → MCP Keys**](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens).
2. Clique em **Generate key**. No diálogo **Generate MCP key**, informe um **Key name** (por exemplo `n8n`). Se você pertence a outras organizações, também pode marcá-las em **Also grant this key access to**.
3. Escolha os escopos. Admins do workspace veem as caixas de escopo, com `read` pré-selecionado. Os demais membros recebem uma chave somente de leitura por este diálogo (veja [Os escopos são reduzidos pelo seu papel](#os-escopos-são-reduzidos-pelo-seu-papel)).
4. Clique em **Generate** e copie a chave — ela começa com `mcp_` e é **exibida apenas uma vez**. Guarde-a em local seguro.

Admins veem todas as chaves e autorizações OAuth do workspace; os demais membros veem apenas as chaves que criaram.

### Usar o token

O token vai no header `Authorization` de cada requisição MCP:

```
Authorization: Bearer mcp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

Normalmente você não digita esse header à mão — seu cliente o lê de um arquivo de configuração (veja os guias de conexão para [Cursor](/mcp/pt-br/connect/cursor), [n8n](/mcp/pt-br/connect/n8n) e [desenvolvimento local](/mcp/pt-br/connect/local-dev)).

## Segurança do service token

<Warning>
Um service token dá a quem o possui o que os escopos dele permitem — no mínimo acesso de leitura aos agentes do seu workspace e, com `write` ou `execute`, a capacidade de alterá-los ou executá-los. Trate-o como uma senha:
- Nunca o commite em um repositório Git.
- Nunca o cole em um documento público ou screenshot.
- Nunca o compartilhe no Slack, e-mail ou em qualquer mensagem que outras pessoas possam ver.
</Warning>

Se você acredita que um service token foi exposto:

1. Revogue-o em [**Settings → MCP Keys**](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens). Admins do workspace podem revogar qualquer chave; os demais membros só podem revogar as próprias.
2. Gere um novo.
3. Atualize seus arquivos de configuração do cliente com o novo token.

## Escopos

Uma chave carrega um ou mais de três escopos:

| Escopo | Concede | Tools |
|--------|---------|-------|
| `read` | Listar agentes, pastas e versões, buscar a estrutura completa de um agente e navegar tipos de node, modelos de IA, integrações e vozes. | [Agentes e pastas](/mcp/pt-br/tools/agents-and-folders), [Nodes e edges](/mcp/pt-br/tools/nodes-and-edges), [Versionamento](/mcp/pt-br/tools/versioning) |
| `write` | Criar e editar agentes, pastas, nodes e edges; criar snapshots e publicar versões. | [Escrevendo com segurança](/mcp/pt-br/tools/writing-safely), [Agentes e pastas](/mcp/pt-br/tools/agents-and-folders), [Nodes e edges](/mcp/pt-br/tools/nodes-and-edges), [Versionamento](/mcp/pt-br/tools/versioning) |
| `execute` | Executar um agente, acompanhar uma execução, cancelar uma execução. | [Executando agentes](/mcp/pt-br/tools/running-agents) |

`list_workspaces` e `list_node_types` não exigem nenhum escopo. `get_node_type` exige `read`. Uma tool que os escopos da chave não cobrem é recusada com `-32401 Insufficient scope`; veja [Interruptores no nível do workspace](#interruptores-no-nível-do-workspace) para distinguir isso de uma recusa por interruptor. Nenhum escopo dá acesso a faturamento, usuários ou configurações do workspace — isso nunca é exposto via MCP.

### Uma autorização pode cobrir vários workspaces

Uma única autorização OAuth ou service token **não** se limita a uma organização — a mesma chave
pode alcançar várias organizações de que você faz parte (marque-as na tela de consentimento, ou em
**Also grant this key access to** ao gerar uma chave), e os escopos são definidos **por workspace**,
então uma chave pode carregar `write` em um e apenas `read` em outro. Chame
[`list_workspaces`](/mcp/pt-br/tools/agents-and-folders#list_workspaces) para ver todos os workspaces
que uma autorização cobre e seus escopos em cada um.

Por isso, toda ferramenta exceto `list_workspaces`, `list_node_types` e `get_node_type` aceita um
parâmetro opcional `workspaceId`:

- Omita-o quando a autorização cobre exatamente um workspace — ele é inferido automaticamente.
- Informe-o quando a autorização cobre mais de um. Uma chamada que o omite nesse caso é recusada
  com `workspace_required`, e o erro lista os ids dos workspaces cobertos para você escolher.

### Os escopos são reduzidos pelo seu papel

Um cliente pede os escopos que quer; você não os escolhe na tela de consentimento e, se ele não pedir nenhum, a autorização é apenas `read`.

Se você não é admin de uma organização, pedir `write`/`execute` nela gera uma autorização reduzida a
`read`, em vez de um erro — isso vale para cada organização separadamente. Um admin do workspace
controla isso com o toggle **Let regular members create powerful keys** em
[Settings → MCP Keys](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens). Ele vem **ligado por
padrão**; quando um admin o desliga, membros não admins recebem apenas `read`.

O toggle não altera o diálogo **Generate key**: só admins veem as caixas de escopo nele, então
não admins sempre recebem uma chave somente de leitura por ali. O toggle define se um não admin pode ter
`write`/`execute` via consentimento OAuth ou pela API. Ele só é verificado quando uma chave é criada ou um
app é reconectado, então as chaves já existentes mantêm os escopos que receberam.

### Alterar os escopos de uma chave

Um admin do workspace pode alterar os escopos de uma chave existente a qualquer momento — não é preciso
revogá-la e emitir outra. Em [Settings → MCP Keys](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens),
a célula de escopos de cada chave na tabela de chaves mostra os escopos atuais como chips, com um
ícone de edição (lápis) ao lado. Clique nos chips ou no ícone, marque os escopos desejados e salve.
Quem não é admin vê os mesmos chips apenas como leitura.

Quanto tempo a mudança leva para chegar ao cliente depende da direção:

| Mudança | Quando passa a valer |
|---------|----------------------|
| Remover um escopo (ex.: `read` + `write` → `read`) | Imediatamente — a API principal lê os escopos atuais da chave em cada chamada. |
| Adicionar um escopo (ex.: `read` → `read` + `write`) | Em até `MCP_TOKEN_CACHE_TTL` segundos — **10 por padrão**. |

O servidor MCP mantém em cache a chave resolvida, escopos incluídos, por `MCP_TOKEN_CACHE_TTL` segundos
para evitar uma ida à API principal em cada chamada. Por isso, logo depois de um admin conceder `write`,
o cliente pode continuar sendo recusado por alguns segundos. Tente de novo depois de ~10 segundos ou
reconecte o cliente.

<Note>
O cache só pode atrasar uma concessão — ele nunca libera mais acesso do que a chave carrega no momento,
porque a API principal valida cada chamada contra os escopos atuais da chave.
</Note>

### Interruptores no nível do workspace

Mesmo com o escopo correto, dois interruptores do workspace precisam estar ligados. Um admin do
workspace os controla em **Settings → MCP Keys**, em **What connected AI assistants are allowed to do**.
Ambos vêm **ligados por padrão**.

| Interruptor na interface | Nome interno nas recusas | Desliga |
|--------------------------|--------------------------|---------|
| **Let AI assistants change things** | `mcp.writes.enabled` | Todas as ferramentas de escrita deste workspace. |
| **Let AI assistants run agents** | `mcp.execute.enabled` | O `run_agent` deste workspace. Execuções iniciadas pelo próprio app não são afetadas. |

Esses interruptores são um portão **independente**: ter o escopo certo na chave não basta enquanto o
interruptor estiver desligado. As duas recusas têm textos diferentes, e isso indica qual delas corrigir:

| Recusa | O que significa |
|--------|-----------------|
| `-32401 Insufficient scope`, com `data.required` informando o escopo que faltou | A chave não carrega esse escopo. Edite os escopos da chave. |
| `Tool execution failed: ERROR <id>: feature_disabled: mcp.writes.enabled is off for this workspace` (ou `mcp.execute.enabled`) | Os escopos da chave estão certos — o interruptor do workspace está desligado. Ligue o interruptor. |

O `<id>` da segunda muda a cada chamada, então busque `feature_disabled:` nos seus logs, e não a
linha inteira.

Em qualquer um dos casos, a correção está no mesmo lugar: **Settings → MCP Keys**.

Execuções iniciadas via MCP são cobradas e auditadas no **dono da chave** que as iniciou, e o nome da
chave/cliente que disparou aparece no histórico de execuções do agente.

## Perguntas frequentes

<AccordionGroup>
  <Accordion title="Qual método devo usar?">
    Use OAuth sempre que o seu cliente puder abrir um navegador — é o método recomendado para usuários e desenvolvedores. Use um service token para serviços de backend, scripts, n8n ou qualquer cliente que só consegue enviar um header.
  </Accordion>
  <Accordion title="Posso ter múltiplos service tokens para o mesmo workspace?">
    Sim — cada token é independente. Você pode ter um token por cliente (ex.: um para n8n, outro para um serviço de backend) e revogá-los individualmente em [**Settings → MCP Keys**](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens).
  </Accordion>
  <Accordion title="O service token expira?">
    Não — nem os service tokens nem os access tokens OAuth expiram, então revogue as chaves que você não usa mais (veja [O que uma autorização OAuth inclui](#o-que-uma-autorização-oauth-inclui)).
  </Accordion>
  <Accordion title="Posso usar minha API key comum do FluxPrompt no lugar?">
    Não. O servidor MCP usa um sistema de autenticação separado. Sua API key comum não funcionará.
  </Accordion>
  <Accordion title="O que o servidor MCP enxerga do meu workspace?">
    Ele vê os mesmos agentes e estrutura que o usuário autenticado consegue ver dentro da interface do FluxPrompt. Ele não tem acesso a credenciais, faturamento ou gerenciamento de usuários.
  </Accordion>
  <Accordion title="Liberei write para alguém, mas o cliente dela continua só com read">
    Verifique nesta ordem:
    1. **Os interruptores do workspace.** **Let AI assistants change things** (`mcp.writes.enabled`) e **Let AI assistants run agents** (`mcp.execute.enabled`) são um portão independente dos escopos da chave — uma chave que carrega `write` continua sendo recusada enquanto o interruptor estiver desligado. A recusa do interruptor contém `feature_disabled:`, não `Insufficient scope`.
    2. **Dê alguns segundos.** O servidor MCP mantém as chaves resolvidas em cache por `MCP_TOKEN_CACHE_TTL` segundos (10 por padrão), então um escopo recém-adicionado pode levar esse tempo para valer. Tente de novo depois de ~10 segundos ou reconecte o cliente.
    3. **Confirme que a mudança foi salva.** Reabra [**Settings → MCP Keys**](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens) e verifique se a célula de escopos da chave mostra os escopos esperados.
    4. **Confirme que o cliente não está com uma sessão antiga.** Alguns clientes só releem as ferramentas e permissões disponíveis quando reconectam.
  </Accordion>
</AccordionGroup>
