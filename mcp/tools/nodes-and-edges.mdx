## Description

These tools build the agent itself. Read [writing safely](/mcp/tools/writing-safely) first — every
tool here is dry-run by default and accepts `expectedVersion` and `versionId`.

Before writing a node, fetch its schema with `get_node_type`. Node data shapes are specific and a
plausible-looking field that does not exist is stored happily and then ignored at run time.

## `list_node_types`

A lightweight summary of every node type — `type`, `label`, `category` and `description`, and **no
schemas and no handles**. Fetch it once to discover the exact type names, then call
[`get_node_type`](#get_node_type) for each type you are about to build. Do not write a node from the
summary alone.

### Input

No parameters required. Like `get_node_type`, it takes no `workspaceId`.

### Output

```json
{
  "nodeTypes": [
    {
      "type": "commandTextNode",
      "label": "Command Text Node",
      "description": "Runs a prompt against an AI text model and passes the result downstream.",
      "category": "AI"
    },
    {
      "type": "conditionNode",
      "label": "Condition Node",
      "description": "Evaluates a condition and routes flow execution along the true or false branch.",
      "category": "Logic"
    }
  ]
}
```

#### Output fields

| Field | Type | Description |
|-------|------|-------------|
| `nodeTypes` | array | Full list of node types. |
| `nodeTypes[].type` | string | Machine-readable identifier (camelCase, e.g. `commandTextNode`). Matches the `type` field in `get_agent` node objects. |
| `nodeTypes[].label` | string | Human-readable name, composed as `"Front name (Technical name)"` when the canvas name and the technical name differ — e.g. `"Display Box (Output Controller)"` — or published as just the one name when they match or the type has no sidebar entry. This exact string, and the bare front name, are also valid input to [`add_node`](#add_node)'s `node.type` and to [`get_node_type`](#get_node_type)'s `type`. |
| `nodeTypes[].description` | string | What this node does. |
| `nodeTypes[].category` | string | Grouping: `Input/Output`, `AI`, `Data`, `Logic`, `Utility`, `Integration`. |

<Note>
  The schemas live behind [`get_node_type`](#get_node_type). The `fluxprompt://node-types`
  [resource](/mcp/tools/prompts-and-resources#resources) is the exception: it returns the full
  entries, schemas and handles included.
</Note>

## `get_node_type`

Returns one node type's full definition: `type`, `label`, `description`, `category`, `inputSchema`,
`outputSchema` and `handles`. Call it once per node type you use, and before wiring with
[`connect_nodes`](#connect_nodes). To fetch every schema at once, read the
[`fluxprompt://node-types`](/mcp/tools/prompts-and-resources#resources) resource.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `type` | string | Yes | The technical type (e.g. `commandTextNode`), the frontend/sidebar name (e.g. "Display Box"), or the composed label [`list_node_types`](#list_node_types) publishes (e.g. "Display Box (Output Controller)"). Matching is case-insensitive and collapses whitespace. A value that matches none of these returns an error (`isError: true`) instead of a schema. |

### The `handles` object

`handles` is the derived handle registry for the type — the most reliable source of connectable
handle names, and far better than guessing from `inputSchema` field names, which describe data, not
wiring.

| Field | Type | Description |
|-------|------|-------------|
| `sourceHandles` | array | `{ handle, role }` — output ports. `role` is `global`, `control`, `condition` or `data`. Global, control and condition handles continue the execution chain; data handles carry a value. |
| `targetHandles` | array | `{ handle, dataField? }` — input ports. `dataField` is the base `inputSchema` field the incoming edge value feeds, when there is one. The value lands in the companion array `<dataField>Data`, not in `dataField` itself. |
| `patterned` | array | `{ direction, pattern, discriminating }` — handles generated at render time that cannot be listed. `discriminating: false` means the pattern is a non-selective catch-all: evidence that some dynamic handle exists, not proof of any specific string. |
| `handlesPatterned` | boolean | `true` when the type has render-time handles beyond the two lists. Treat the lists as incomplete, not wrong: an unlisted handle is unproven, not invalid. |
| `unresolved` | boolean | `true` when the handles for this type could not be determined at all. |
| `canContinueExecutionChain` | boolean | Whether the type exposes an execution-continuation source handle. A `globalStarter` may only connect directly into a type where this is `true`. |

<Warning>
  **Respect `enum` when a field declares one.** Read the field's `enum` from `inputSchema` and never
  guess a plausible-looking value like `"default"`. A value outside the list is saved anyway,
  reported in `invalidEnumValues`, and the node does nothing — if a node is inert, verify the field
  name and value. Examples: `dynamicSettingsNode.selectedOption` is `"text"` or `"voice"`;
  `fluxObject.selectedType` is one of six exact strings such as `"Load All Entries"`.
</Warning>

## `list_ai_models`

Returns the AI models available to the workspace, so you can fill an AI node's `aiModel`/`aiSystem`
with a value that actually exists and is enabled for that workspace — rather than a model name you
remember from elsewhere.

### Input

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `workspaceId` | string | Only when this authorization covers more than one workspace | Call [`list_workspaces`](/mcp/tools/agents-and-folders#list_workspaces) to discover which workspaces this key covers. |
| `cursor` | string | No | Opaque cursor from a previous response's `nextCursor`. |

### Output

Each item carries `provider`, `modelName`, `displayName`, `description`, `modelType`,
`contextWindow`, `supportsVision`, `supportsReasoning`, `supportsImageOutput`,
`supportsImageGenerationTool` and a derived `tools` array (e.g. `image_generation`,
`image_output`, `web_search`, `structured_output`, `vision_input`, `reasoning`).

`supportsImageOutput` means the model itself returns an image (a native image model, or a chat model
whose output includes images, e.g. `gemini-2.5-flash-image`). `supportsImageGenerationTool` means the
model can call a provider-side image-generation tool from a chat completion (e.g. OpenAI's
`gpt-5-nano`/`gpt-5.5` calling `image_generation`) — these are two different mechanisms, and a model
can have either, both, or neither. `tools` is derived from these and the other capability fields, not
a separate source: it always agrees with the booleans.

```json
{
  "models": [
    {
      "provider": "openai",
      "modelName": "gpt-5-nano",
      "displayName": "GPT-5 Nano",
      "modelType": "Text",
      "supportsVision": true,
      "supportsReasoning": true,
      "supportsImageGenerationTool": true,
      "supportsImageOutput": false,
      "tools": ["image_generation", "web_search", "structured_output", "vision_input", "reasoning"]
    },
    {
      "provider": "gemini",
      "modelName": "gemini-2.5-flash-image",
      "displayName": "Gemini 2.5 Flash Image",
      "modelType": "Image",
      "supportsVision": true,
      "supportsReasoning": true,
      "supportsImageGenerationTool": false,
      "supportsImageOutput": true,
      "tools": ["image_output", "web_search", "vision_input", "reasoning"]
    }
  ],
  "total": 87
}
```

<Warning>
  Results are cached for a short period and may lag a few minutes behind an admin approving or
  toggling a model. Don't treat a model listed here as a guarantee it will still be available at
  execution time — `run_agent` reports it if a model becomes unavailable.
</Warning>

## `list_voices`

Returns the voices this user can pick for a `voiceBoxNode` (AI Voice Generator) — the same list the
canvas voice dropdown shows. Call it before setting a voice instead of guessing an id. It needs the
`read` scope.

### Input

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `workspaceId` | string | Only when this authorization covers more than one workspace | Call [`list_workspaces`](/mcp/tools/agents-and-folders#list_workspaces) to discover which workspaces this key covers. |
| `provider` | `"elevenlabs"` \| `"groq"` | No | Restrict the result to one provider. Omit to list both. |

### Output

```json
{
  "voices": [
    { "provider": "elevenlabs", "id": "pNInz6obpgDQGcFmaJgB", "name": "Adam", "custom": false, "isDefault": true,
      "labels": { "accent": "american", "gender": "male" } },
    { "provider": "elevenlabs", "id": "Zk3c…", "name": "My cloned voice", "custom": true, "isDefault": false, "labels": null }
  ],
  "total": 2
}
```

| Field | Type | Description |
|-------|------|-------------|
| `voices[].provider` | `"elevenlabs"` \| `"groq"` | Which provider the voice belongs to. |
| `voices[].id` | string | The value to set on the node. |
| `voices[].name` | string | What to show the user. |
| `voices[].custom` | boolean | `true` for a voice the user cloned. |
| `voices[].isDefault` | boolean | `true` for the default voice. |
| `voices[].labels` | object \| null | Extra descriptors such as accent and gender. |
| `total` | number | `voices.length`. |

The list is small and returned in full — there is **no pagination** and no `cursor`. PlayHT is not
offered.

### Setting the voice on a node

| Node `aiSystem` | Field that takes the `id` |
|-----------------|---------------------------|
| `elevenlabs` | `voiceId` |
| `groq` | `groqVoice` |

Show the names to the user and let them choose. When an elevenlabs node is written with no `voiceId`,
the server fills in the voice flagged `isDefault` (Adam, `pNInz6obpgDQGcFmaJgB`) and reports it in
`appliedDefaults`. A groq node gets no default.

<Warning>
  **`add_node` and `update_node` refuse a voice id the provider does not know**, with a
  `validation_error` telling you to call `list_voices` and use one of the returned ids. Always take
  the id from this list. If ElevenLabs cannot confirm a voice either way (a lookup failure other
  than "not found"), the write is accepted and the id is reported back in `unverifiedVoices`.
</Warning>

## `list_integrations`

Returns the third-party connections the authorizing user may use, so you can fill an integration
node's `integrationId` with one that exists **and** that this user is allowed to reach — rather than
an id copied from somewhere else.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `provider` | string | No | Restrict to one provider, e.g. `hubspot`. Omit to list every provider. An unknown name returns an empty list. |
| `cursor` | string | No | Opaque cursor from a previous response's `nextCursor`. |

Each item carries `id` (the value `integrationId` takes), `name`, `provider`, `ownerUserId`,
`ownerUserName`, `isOwn`, `isSharedWithOrg` and `createdAt`. Credentials are never returned — a
connection is referenced only by its id.

The list is the user's **own** connections plus those an active member of the workspace shared with
the organisation. Nothing else appears. The user is the one behind the key: the person who granted
the OAuth authorization, or the member who created the service key. The call is refused, rather than
widened to the whole workspace, only when that user is no longer an active member of the workspace
(or the key has no user behind it at all).

<Warning>
  Writing an `integrationId` that is not in this list is refused by `add_node` and `update_node`.
  Call this tool first instead of reusing an id you have seen elsewhere — an id from another user's
  connection is not usable even when it is valid.
</Warning>

## `list_integration_options`

Returns the values a `thirdPartyIntegration` picker offers for one field of a saved connection — the
same list the canvas dropdown shows — as `{label, value}` items. Set the node field to `value`, show
`label` to the user.

### Input

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `integrationId` | string | Yes | Connection to query, from [`list_integrations`](#list_integrations). The provider is taken from the connection — you never pass one separately. |
| `field` | string | Yes | The node field whose values you want — for example `team`, `space`, `folder`, `list`, `status`, `statusFilter` or `assignees` for clickup. [`get_node_type`](#get_node_type) `thirdPartyIntegration` names the fields for every provider. |
| `context` | object | No | Values already chosen for the parent pickers, keyed by node field name, e.g. `{"team": "9011479430", "space": "90110000001"}`. Only string, number and boolean values are sent, as strings. |

### Output

```json
{
  "integrationId": "5b1e2f3a-1111-4c2d-9a3e-abc123456789",
  "provider": "clickup",
  "field": "list",
  "options": [
    { "label": "Sprint backlog", "value": "901100234567" },
    { "label": "Bug triage", "value": "901100234599" }
  ],
  "total": 2
}
```

| Field | Type | Description |
|-------|------|-------------|
| `integrationId` | string | Echoes the connection you queried. |
| `provider` | string | Provider of that connection, e.g. `clickup`. |
| `field` | string | Echoes the field you asked about. |
| `options` | array | `{label, value}` items. |
| `total` | number | `options.length`. |

### The clickup picker chain

Pickers depend on the ones above them — pass the parent's chosen value in `context`, keyed by node
field name:

| Field | Needs in `context` | Notes |
|-------|---------------------|-------|
| `team` | none | ClickUp calls this the workspace. |
| `space` | `{team}` | |
| `folder` | `{space}` | Optional — a list can also live directly under a space. |
| `list` | `{folder}`, or `{space}` for a folderless list | |
| `status` / `statusFilter` | `{list}` | |
| `assignees` | `{team}` | |
| `taskId` | — | No picker. Read ids from a `tasks` pull instead. |

Other providers expose their own pickers the same way — for example a slack `channel` or a notion
`database` — and [`get_node_type`](#get_node_type) `thirdPartyIntegration` names the fields for each.

<Warning>
  **The connection must be reachable by the user, or the call is refused.** Same rule as
  [`list_integrations`](#list_integrations): a connection that is not this user's own, and not
  shared with the organisation by an active member, is refused with a 403 instead of returning
  options.
</Warning>

<Warning>
  **A provider error surfaces as a bad request.** When the provider itself rejects the call (a 4xx,
  for example an expired token), `list_integration_options` returns a bad request telling the user
  to reconnect the integration — it does not retry or fall back silently.
</Warning>

<Note>
  **An empty list means one of two things**: there is nothing to choose, or a parent value is
  missing from `context`. Check the chain above before assuming the picker is broken.
</Note>

<Warning>
  **Do not invent ids.** A value not taken from this list's `options` will fail at run time — this
  applies to clickup's `team`, `space`, `folder`, `list` and `assignees` as much as to any other
  provider's pickers.
</Warning>

## Authoring an integration node

`thirdPartyIntegration` talks to a configured service, and `hubSpotCRM` is the same node with the
provider fixed to `hubspot` — same fields, same execution engine, interchangeable for reads and
writes. Seven providers execute today: `clickup`, `hubspot`, `notion`, `slack`, `stripe`, `wordpress`,
`zapier`.

The order that works:

1. Pick `provider`.
2. Pick `mode` — `pull` to read, `push` to write. Absent means pull.
3. For a pull set `pullObjectType`; for a push set `pushAction`. Both are provider-specific and both
   decide which of the remaining fields apply, so read them from
   [`get_node_type`](/mcp/tools/nodes-and-edges#get_node_type) rather than guessing.
4. Set `integrationId` from `list_integrations`.
5. Resolve picker fields with [`list_integration_options`](#list_integration_options) — for example
   clickup's `team`, `space`, `folder`, `list`, `status`/`statusFilter` and `assignees` are ids from
   the connected account, not values to guess.
6. Set the fields that provider and that object type or action names.

Two things clients get wrong:

- **`providerEntry`** — only `zapier` offers more than one configuration (`zapier_pull`,
  `zapier_push`, `zapier_poll`). Leave it empty and the product resolves the entry by heuristic; set
  it explicitly for zapier.
- **`<field>Data`** — any field that accepts an incoming edge has a companion array of the same name
  plus `Data`, and the array **wins over** the typed value. Landing an edge reference in the scalar
  alone means the value never arrives. `connect_nodes` fills the companion for you.

`blobConfig` is the escape hatch: a JSON object, as a string, merged over the node data at run time.
It must carry a `provider` key or it is ignored entirely. Prefer the named fields when they exist.

<Note>
  Credentials are never node data. The connection lives in the saved integration and is selected by
  `integrationId`; no secret, site URL or API key belongs in a node.
</Note>

## `add_node`

Adds a node to an agent.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `agentId` | string (UUID) | Yes | Target agent. |
| `node` | object | Yes | React-Flow node: a unique `id`, plus `type` and `data` as needed. |

### Naming the node type

`node.type` accepts any of three forms: the technical type (`outputController`), the frontend/sidebar
name (`"Display Box"`), or the composed label [`list_node_types`](#list_node_types) publishes
(`"Display Box (Output Controller)"`). Matching is case-insensitive and collapses whitespace, so
`"display box"` resolves the same as `"Display Box"`.

A value that matches none of the three is rejected with a `validation_error` — including a
plausible-looking string that simply is not a real type.

### Do not invent coordinates

`node.position` is **optional and resolved by the server**. The position you send is a *hint*: the
first free slot at or to the right of it wins, and when you omit it the node continues the flow to
the right of the rightmost node. Existing nodes are never moved.

- Read `position` back from the response — it is the authoritative placement.
- `placementAdjusted: true` means the server moved the node off a spot that was already taken.
- `width`/`height` are filled in from the measured footprint of that node type when you omit them.

Clients that invent round coordinates (`{x:0,y:0}`, `{x:100,y:100}`) with no knowledge of node
dimensions used to pile every node on the same spot. Omitting `position` is both simpler and better.

```json
// request — no position
{ "agentId": "d2c2…", "node": { "id": "textgen_1", "type": "commandTextNode",
  "data": { "prompt": "Summarise the input", "aiModel": "gpt-4o", "aiSystem": "openai" } },
  "dryRun": false, "idempotencyKey": "add-textgen-1" }

// response — placement resolved
{ "dryRun": false, "applied": true, "placementAdjusted": true,
  "diff": { "added": [ { "id": "textgen_1", "type": "commandTextNode",
    "position": { "x": 435, "y": -240 }, "width": 825, "height": 789 } ], "updated": [], "removed": [] } }
```

### Referencing another node's output

On the node types whose catalogue field description says so — for example `webSearch.query`,
`commandContentNode.queryData`, `voiceBoxNode.text` and `imageGenerator.prompt` — a string field may
embed `{{<nodeId>.<key>}}`, and at run time the runtime substitutes that node's output for `<key>`
(typically `text`) before the node executes. Not every field supports this: read each field's own
description in [`get_node_type`](#get_node_type) before relying on it. The same syntax works in the
`patch` of [`update_node`](#update_node).

<Warning>
  A `globalStarter` node's id **must** contain the literal substring `flow-global-starter` (e.g.
  `flow-global-starter_main`). The backend resolves the flow's entry point by matching that
  substring, so any other id is rejected with `validation_error` up front.
</Warning>

<Note>
  An agent has **exactly one** `globalStarter`, and `create_agent` already creates it. Adding a second
  one is refused with `duplicate_global_starter`, which names the existing node to connect from. Only
  an agent that has none can receive one.
</Note>

## `update_node`

Merges a patch into an existing node.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `agentId` | string (UUID) | Yes | Target agent. |
| `nodeId` | string | Yes | Node to patch. |
| `patch` | object | Yes | Partial node fields. |

- Top-level fields (`type`, `position`, …) are **shallow-merged**.
- `patch.data` is merged **one level deep**, so data keys you omit are preserved, not deleted.
- Send the minimum: to change one field, send only that field.
- A `globalStarter`'s `type` cannot be changed (`global_starter_not_retypable`); edit its `data` instead.

Unlike `add_node`, `update_node` **honours the position you send exactly** — no anti-overlap
resolution. That is deliberate: it lets a client lay out a flow deterministically, one node at a
time, without the server second-guessing an intentional move.

## `remove_node`

Removes a node **and every edge touching it**. A `globalStarter` is never removed
(`global_starter_not_removable`): every agent keeps exactly one, as in the builder. To change where a
run starts, move its edge with `disconnect_nodes` and `connect_nodes`.

| Parameter | Type | Required |
|-----------|------|----------|
| `agentId` | string (UUID) | Yes |
| `nodeId` | string | Yes |

## `connect_nodes`

Creates an edge from a source node to a target node. Handles are validated against the derived
registry for the two node types: an unknown `(type, handle)` pair is refused with a
`validation_error` naming the valid handles for that type — call [`get_node_type`](#get_node_type)
and read `handles` instead of guessing from `inputSchema` field names.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `agentId` | string (UUID) | Yes | Target agent. |
| `source` | string | Yes | Source node id. |
| `target` | string | Yes | Target node id. |
| `sourceHandle` | string | No | Source port. Omit for the context-aware default (see below). Required from a `conditionNode`. |
| `targetHandle` | string | No | Target port. Omit for the context-aware default (see below). Required into a `nodesAdd` node. |
| `edgeId` | string | No | Explicit edge id. |

### Execution order vs data — the two-edge model

This is the single most common source of "I connected it but nothing happens":

- An edge from **`outputFlow` → `input`** makes the target **execute** after the source. It carries
  no data.
- An edge from **`output` → `<field>In`** (e.g. `contentIn`, `inputText`, `text-input` — the name differs per node type) carries the
  **data**. It does not trigger execution.

Chaining two `commandTextNode`s so B runs after A *and* sees A's text therefore needs **both** edges,
each with its own `edgeId`. Either one alone is a silent half-connection.

On top of the edge, the target's `data` must reference the source — the companion array
`<field>Data`, e.g. an `outputObjectNode`'s `data.textData`.

When the target has a single data handle feeding a text field, one call with both handles omitted
writes the execution edge, the data edge **and** the `<field>Data` entry — for example on a
`commandTextNode`, `outputObjectNode`, `textBox` or `webSearch`. Otherwise only the execution edge
is written and you wire the data edge yourself, with `sourceHandle: "output"` and a handle from
`handles.targetHandles`. It is never done from a `globalStarter`. Check `diff.edgesAdded` and
`diff.updated`, or run [`check_agent_integrity`](/mcp/tools/writing-safely#check_agent_integrity),
before patching `<field>Data` yourself — doing so appends a duplicate. A successful edge does not
schedule the target: do not read it as "the target will now run".

### Handle defaults

Omit both handles and the server picks based on the node types. It only uses `outputFlow` / `input` when the registry confirms the type really has that handle, and otherwise refuses the call instead of miswiring it.

| Situation | `sourceHandle` | `targetHandle` |
|-----------|----------------|----------------|
| Source is `globalStarter` | `a` | `input` |
| Either side is a `mediaBox` | `mediaOutput` | `mediaInput` |
| Source is `dynamicSettingsNode` | `outputModelTextSettings` | `modelSettings` — including into a `voiceBoxNode`; refused if the target has no such handle |
| Target is a terminal display node (`outputObjectNode`, `richTextBox`) | The source's data output: the first of `output`, `textOutput`, `contentOut` that it has | `input` |
| Anything else | `outputFlow`, if the source type has it | `input`, if the target type has it |

Two cases need an explicit handle:

- From a `conditionNode`, pass `sourceHandle` — `conditionHandle-T{n}`/`conditionHandle-F{n}` for
  SWITCH conditions, or `outputHandle-0`/`outputHandle-1` for boolean ones.
- Into a `nodesAdd` node, pass `targetHandle` — `nodesInput` (node-list payload) or `edgesInput`
  (edge-list payload).

## `disconnect_nodes`

Removes an edge. Identify it either by `edgeId`, or by `source` + `target`.

**One call undoes one `connect_nodes`** — both edges and the `<field>Data` reference it added. Read
`diff.edgesRemoved` / `diff.updated` for exactly what changed. This removes **only edges**; to
delete a node use `remove_node`.
