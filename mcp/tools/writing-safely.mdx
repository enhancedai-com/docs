## Description

Every tool that changes something — agents, folders, nodes, edges, versions, runs — follows the same
four conventions. Learn them once and every write tool behaves predictably.

## Dry-run is the default

**Every write tool defaults to `dryRun: true` and changes nothing.** It returns the diff of what
*would* happen so you can inspect it first. To actually apply the change you must pass **both**
`dryRun: false` **and** an `idempotencyKey`.

<Warning>
  **`cancel_run` is the one exception.** It defaults to `dryRun: false` and cancels immediately —
  pass `dryRun: true` explicitly to validate without cancelling. See
  [Running agents](/mcp/tools/running-agents#cancel_run).
</Warning>

```json
// 1. Inspect
{ "agentId": "a1b2…", "nodeId": "textBox_1", "patch": { "data": { "text": "hi" } } }

// 2. Apply
{ "agentId": "a1b2…", "nodeId": "textBox_1", "patch": { "data": { "text": "hi" } },
  "dryRun": false, "idempotencyKey": "set-greeting-2026-07-27-1" }
```

The response always tells you which mode you got:

| Field | Meaning |
|-------|---------|
| `dryRun` | `true` when nothing was applied. |
| `applied` | `true` when the change was persisted. |
| `diff` | What changed (or would change): `added`, `updated`, `removed`, `edgesAdded`, `edgesRemoved`. |

<Tip>
  Read the diff, don't assume it. `add_node` returns the node **as stored**, including the
  `position`, `width` and `height` the server resolved — which may differ from what you sent.
</Tip>

**A dry-run refuses what the apply would refuse.** `create_agent`, `create_folder` and `move_agent`
run their validation and permission checks before returning the dry-run, so a dry-run that succeeds
means the destination folder or space accepted the call. Earlier builds returned first and checked
later, which let a dry-run report that a call would work when the apply would have refused it.

## Idempotency keys

`idempotencyKey` is required whenever `dryRun` is `false`. A replay with the **same key and the same
payload** returns the cached result instead of applying the change twice — so a network timeout or a
client retry cannot duplicate a node or dispatch a second run.

Use a key that describes the intent and is unique per change, e.g. `add-summary-node-2026-07-27-1`.
Reusing a key for a *different* payload is a mistake: it will not do what you expect.

## Version conflicts (`expectedVersion`)

Pass the `updatedAt` you got from `get_agent` as `expectedVersion`. If anyone else changed the agent
in the meantime, the write is refused with `version_conflict` instead of silently overwriting their
work. Re-read the agent, re-decide, and retry.

This is optional but strongly recommended whenever a human might be editing the same flow in the
canvas at the same time.

## Which copy am I editing? (`versionId`)

Node and edge tools accept `versionId`, and it decides *what* you are editing:

| `versionId` | You are editing |
|-------------|-----------------|
| **Omitted** (default) | The **live working copy**. Edits accumulate untracked until you call [`create_version`](/mcp/tools/versioning). |
| A version id | That **existing version snapshot**, in place. |

<Warning>
  `versionId` does **not** start a new version. It targets a snapshot that already exists. To create
  one, call [`create_version`](/mcp/tools/versioning). Passing a `versionId` hoping to "begin a new
  version" edits that old snapshot instead.
</Warning>

## Permissions

Write tools require the `write` scope on your key; running agents requires `execute`. Both are also
gated **per workspace** by the workspace owner:

- `mcp.writes.enabled` — turns all write tools off for the workspace.
- `mcp.execute.enabled` — turns `run_agent` off for the workspace.

These switches are an independent gate, not part of your key's scope, and the two failures look
different: a missing scope is the JSON-RPC error `-32401`, while a switch that is off comes back as a
tool result with `isError: true` whose text contains `feature_disabled:`.

If your key was issued to a non-admin member, its scopes may have been clamped to `read` only. A
workspace admin can allow non-admin write/execute keys in **Settings → MCP Tokens**. See
[Authentication](/mcp/authentication).

## Errors you should expect

| Error | Why | What to do |
|-------|-----|------------|
| `-32401` insufficient scope | Your key lacks `write`/`execute`. `data.required` names the scope that was missing. | Re-authorize with the needed scopes, or ask an admin to raise the key's scope. |
| `feature_disabled` (tool error) | The workspace switch is off. It arrives as a tool result with `isError: true`, reading `Tool execution failed: ERROR <id>: feature_disabled: mcp.writes.enabled is off for this workspace` — not as a JSON-RPC error. The `<id>` changes on every call, so match on `feature_disabled:`. | Ask a workspace admin to turn the switch back on. Re-authorizing changes nothing. |
| `version_conflict` | The agent changed since your `expectedVersion`. | Re-read with `get_agent` and retry. |
| `validation_error` | The payload breaks a rule (e.g. a `globalStarter` id without `flow-global-starter`). | Fix the payload; the write did **not** partially apply. |
| `integrationId` not reachable | The node names a third-party connection this user neither owns nor received through an organisation share. | Call [`list_integrations`](/mcp/tools/nodes-and-edges#list_integrations) and use an id from that list. |
| `provider_not_ready` | The provider is not enabled for MCP writes in this environment. | Ask an admin; the allowlist is per environment. |
| `-32006` rate limited | 60 requests/minute or 5 000/day per key. | Honour `retryAfterMs`. |
| `-32602` invalid params | A required parameter was omitted. `data.missing` names them. | Send the parameter; the schema for each tool lists what is required. |

## `check_agent_integrity`

Checks whether an agent's current node/edge graph will actually render and execute the way it looks
— without changing anything. It needs only the `read` scope and is safe to call on any agent,
including one this MCP did not author.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `agentId` | string (UUID) | Yes | Agent to check. From `list_agents`. |
| `versionId` | string | No | Check a specific version snapshot instead of the current draft. |

Returns:

| Field | Type | Description |
|-------|------|-------------|
| `ok` | boolean | `false` when `flowEntryIssues`, `unrenderableEdges`, `missingInputs`, `unreachableNodes` or `wrongEdgeTypes` has at least one entry. Does **not** depend on `unverifiableEdges`. `ok: true` never means the flow produces correct output — it cannot see a starved third-party call that still reports success, or an unfed data field on a node type this MCP did not author. |
| `flowEntryIssues` | array | `{ code, reason }` — no usable execution entry point; the flow will not run at all. `code` is `no_global_starter`, `global_starter_id_not_resolvable` or `global_starter_not_connected`. |
| `unrenderableEdges` | array | `{ edgeId, source, target, sourceHandle, targetHandle, reason, validSourceHandles?, validTargetHandles? }` — edges whose handle does not exist on the node and so will not be drawn. |
| `missingInputs` | array | `{ code, nodeId, nodeType, targetHandle, companionField?, sourceEdgeId, reason }` — data that is wired but will never arrive. `code` is `empty_companion_array` or `control_classified_data_handle`. |
| `unreachableNodes` | array | `{ nodeId, nodeType }` — nodes with no control/global/condition path from the global starter. |
| `wrongEdgeTypes` | array | `{ edgeId, sourceHandle, expectedType, actualType }` — control/global edges not drawn as execution edges. |
| `unverifiableEdges` | array | `{ edgeId, source, target, sourceHandle, targetHandle, reason }` — edges the write path accepted because the target node type accepts any handle, so the registry cannot confirm or deny the handle is valid. Present for visibility only; does not affect `ok`. |

<Warning>
  **Call this on agents you just authored or edited too, not only pre-existing ones.** A write can
  pass validation on each individual edge and still leave the agent wrong as a whole — for example a
  control edge where a data edge was needed. `ok: true` only means this specific set of checks found
  nothing, not that the flow works.
</Warning>

## What the response tells you beyond the diff

A write can succeed and still not do what you meant. These fields say so — read them.

| Field | Meaning |
|-------|---------|
| `unknownArguments` | Arguments you sent that the tool does not declare. They were **ignored**, so the tool did something other than what you asked. |
| `invalidEnumValues` | A node field whose value is outside the declared enum. The write applied, but the executor will not recognise the value and the node will do nothing at run time. |
| `missingRequiredFields` | On `check_agent_integrity`: a required node field left empty. Reported rather than refused, because some declared-required fields are not needed at run time. |
| `placementAdjusted` | The server moved your node so it would not overlap another. |
