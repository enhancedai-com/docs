## Connection checklist

Before digging into specific errors, verify these five things:

<Steps>
  <Step title="Auth method matches the client">
    Claude Desktop and Claude.ai use **OAuth only** — no token. If you're trying to paste a token into them, that's the problem; add FluxPrompt as a custom connector instead. The steps below apply to service-token clients (Cursor, n8n, CLI, backend services).
  </Step>
  <Step title="Token format (service-token clients)">
    Your service token should start with `mcp_` and contain no spaces. If you copied it from [**Settings → MCP Keys**](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens), check for trailing whitespace.
  </Step>
  <Step title="Authorization header format (service-token clients)">
    It must be `Bearer <token>` (capital B, one space). Not `bearer`, not `Token`, not the raw token without the prefix.

    ✅ `Bearer mcp_abc123`
    ❌ `mcp_abc123`
    ❌ `bearer mcp_abc123`
  </Step>
  <Step title="Server URL">
    The URL must be `https://mcp.fluxprompt.ai/mcp` (no trailing slash). If your team uses a custom endpoint, confirm the URL with FluxPrompt.
  </Step>
  <Step title="Client restart">
    For Claude Desktop: fully quit (system tray → Exit) and reopen — closing the window is not enough.
  </Step>
  <Step title="JSON syntax">
    Config files (claude_desktop_config.json, cursor/mcp.json) must be valid JSON. Use [jsonlint.com](https://jsonlint.com) to validate if you edited manually.
  </Step>
</Steps>

## Error reference

### Claude Desktop says the token is invalid / I can't paste my token

**Cause:** Claude Desktop (and Claude.ai) reject user-pasted bearer tokens. They authenticate via **OAuth**, not a token in a config file.

**Fix:** Don't paste a token. Add FluxPrompt as a custom connector and complete the login + consent flow — see [Connect Claude Desktop](/mcp/connect/claude-desktop). Service tokens are only for clients like Cursor, n8n, the CLI, and backend services.

---

### "Unauthorized" / 401

**Cause:** The HTTP response is `401` with `{"error": "Unauthorized", "reason": "..."}` and a `WWW-Authenticate` header that points to the server's OAuth metadata. The `reason` tells you which case you hit:

- `missing_token` — the request had no `Authorization: Bearer ...` header.
- `invalid_token` — the token is unknown, revoked, expired, or has no active workspace binding.

OAuth clients (Claude Desktop, Claude.ai) read the `WWW-Authenticate` header and start the login flow themselves — see the entry above if one can't sign in.

**Fix:**
1. Confirm your `Authorization` header is `Bearer mcp_xxxxx` with no extra characters.
2. Check the key is still active in [**Settings → MCP Keys**](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens), or click **Generate key** to create a new one.

---

### "Upstream rejected this server" / 502 `upstream_auth_rejected`

**Cause:** The MCP server reached the core API, and the core API refused *its* credential — not yours. Your token is fine. This happens when `MCP_INTERNAL_SECRET` differs between the two services, typically after one of them is redeployed with a new value.

**Fix:** Set `MCP_INTERNAL_SECRET` to the identical value on both `back` and `mcp-server`, then restart the MCP server.

<Note>
Earlier builds returned a bare `500 Internal server error` here, which gave no hint about where to look. If you are on an older build and see a persistent, unexplained `500` on every call, this is the first thing to check.
</Note>

Do **not** re-run the OAuth flow to resolve this — the failure is on the server side and re-authorizing cannot fix it.

---

### "Service temporarily unavailable" / 503 `upstream_dependency_failed`

**Cause:** An internal call from the MCP server to the core API failed with a retryable status — the core API answered `429` or a `5xx`, or was unreachable. Your token, your scopes and your payload are fine, and the MCP server itself is working.

**Fix:** Retry the request. The response says so explicitly:

```json
{
  "error": "Service temporarily unavailable",
  "reason": "upstream_dependency_failed",
  "retryable": true,
  "upstreamStatus": 503
}
```

`upstreamStatus` is the status the core API returned, and is absent when the call never got a response at all. If retries keep failing for several minutes, check the [FluxPrompt status page](https://status.fluxprompt.ai).

<Note>
Earlier builds returned a bare `500 Internal server error` here, which was indistinguishable from a defect in the MCP server. A `500` with no `reason` on a call that used to work is worth retrying once before reporting it.
</Note>

---

### "Service temporarily unavailable" / 503 `upstream_unavailable`

**Cause:** The MCP server couldn't connect to the core API at all — connection refused, DNS failure, or a timeout. Your token and payload are fine. In production this means the core API is down or unreachable; in a local setup it usually means `BACK_BASE_URL` is wrong.

**Fix:** Retry after a moment. If it keeps happening, check the [FluxPrompt status page](https://status.fluxprompt.ai). For local setups, see [Local development](/mcp/connect/local-dev#troubleshooting).

---

### "Agent not found" (`isError: true`)

**Cause:** The `agentId` you passed doesn't exist in your workspace, or belongs to a different workspace. `get_agent` reports this as a tool error (`result.isError: true`) rather than a protocol-level error code.

**Fix:**
1. Use `list_agents` to get valid IDs from your workspace.
2. Confirm you are using the correct workspace token (if you have tokens for multiple workspaces).

---

### Tools return empty list (`"agents": []`)

**Cause:** Your workspace has no agents, or the token doesn't have access to the workspace.

**Fix:**
1. Log in to FluxPrompt and confirm you have at least one agent.
2. If you do, contact FluxPrompt — your token may be scoped to the wrong workspace.

---

### "Rate limit exceeded" or "Service temporarily unavailable" / -32006

**Cause:** The request was rejected before it reached a tool. The JSON-RPC `error.data.reason` says why:

- `rate_limited` — your key went over its per-minute or per-day request quota.
- `circuit_open` — too many recent calls with this key failed, so the server pauses it for a cooldown.

Both include `retryAfterMs`:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32006,
    "message": "Rate limit exceeded",
    "data": { "reason": "rate_limited", "retryAfterMs": 12000 }
  }
}
```

**Fix:** Wait at least `retryAfterMs` milliseconds, then retry, and reduce your call frequency. For `circuit_open`, fix whatever is making the calls fail first (for example a wrong `agentId` or node payload).

---

### `-32602` `workspace_required`

**Cause:** Your OAuth authorization or key covers more than one workspace, and the tool you called needs to know which one. The error includes `reason: "workspace_required"` and the list of covered workspace IDs.

**Fix:** Call `list_workspaces`, then pass the chosen `workspaceId` as an argument to the tool. For resources, read them as `<uri>?workspaceId=<id>`.

---

### `-32401` Unauthorized / Insufficient scope

**Cause:** The call was authenticated but not allowed. Check `error.data`:

- `{"required": "read" | "write" | "execute"}` (message `Insufficient scope`) — the key or authorization doesn't include that scope. Read tools need `read`, running an agent needs `execute`.
- `{"reason": "workspace_not_covered"}` — the `workspaceId` you passed isn't one this authorization covers.
- `{"reason": "no_context"}` (message `Unauthorized`) — the request reached a task method without an authenticated context; reconnect the client.

**Fix:** Generate a key with the scope you need under **MCP Keys**, or re-authorize the connector and grant the missing access. Use `list_workspaces` to see which workspaces you can use.

---

### "Task result not ready" / -32001

**Cause:** You called `tasks/result` for a task that is still `working`. Long-running tools such as `run_agent` can run as tasks that finish later.

**Fix:** Poll `tasks/get` until the status is no longer `working` (respect the `pollInterval` it returns), then call `tasks/result` again. Results stay retrievable for a limited time, so fetch them soon after the task completes.

---

### "Method not found" / -32601

**Cause:** The tool name is wrong (e.g. `listAgents` instead of `list_agents`).

**Fix:** Use the exact tool names with underscores: `list_agents`, `get_agent`, `list_node_types`.

---

### `{"error":"invalid_client"}` on `/oauth/authorize` (Claude Code CLI)

**Cause:** Claude Code's official OAuth client metadata declares its loopback `redirect_uris` (`http://localhost/callback`, `http://127.0.0.1/callback`) **without a port**, but the CLI always binds an ephemeral local port when it opens the callback listener (e.g. `http://localhost:56626/callback`). If the deployed `mcp-server` requires an exact `redirect_uri` match, every Claude Code OAuth attempt fails with `invalid_client` — this is not a token, workspace, or env-var problem.

**Fix:** `mcp-server`'s `OauthClientService.resolveClient` must tolerate port variation on loopback redirect URIs per [RFC 8252 §7.3](https://www.rfc-editor.org/rfc/rfc8252#section-7.3) — same protocol, hostname, path and query, any port. This was fixed in `src/oauth/oauth-client.service.ts` (`redirectUriMatches`); if this error resurfaces in an environment, confirm that environment's `mcp-server` deploy includes that fix (check for `redirectUriMatches`/`loopbackHostnames` in `oauth-client.service.ts`) rather than re-diagnosing it as a missing env var or DB registration.

---

### `Transport channel closed, when send initialized notification`

**Cause:** The client finished authenticating and then failed on the notification that closes the handshake, usually alongside `unexpected server response: expect accepted or json, got Sse(None)`. Clients built on the Rust `rmcp` library — Codex CLI among them — send `Accept: text/event-stream` on every message, and the server used to answer that notification with an SSE stream instead of a bare `202 Accepted`.

**Fix:** A JSON-RPC notification (a message with no `id`) is now answered with `202 Accepted` and no body whatever the `Accept` header says, per the MCP streamable-HTTP transport spec, so these clients complete the handshake. If the error persists, update the client to its current release and confirm the server URL is `https://mcp.fluxprompt.ai/mcp` — re-running the OAuth flow does not help, since the authentication already succeeded.

---

### "Service disabled" / -32005

**Cause:** The FluxPrompt MCP server is temporarily disabled for maintenance.

**Fix:** Wait a few minutes and try again. Check the [FluxPrompt status page](https://status.fluxprompt.ai) for ongoing incidents.

---

### Claude Desktop shows no MCP tools

**Cause:** Config file was not read because Claude Desktop was not fully restarted, or the JSON is malformed.

**Fix:**
1. Fully quit Claude Desktop (right-click system tray → Exit on Windows, or Dock → Quit on macOS).
2. Validate your `claude_desktop_config.json` at [jsonlint.com](https://jsonlint.com).
3. Reopen Claude Desktop and start a new conversation.

---

### n8n: "Connection refused" or timeout

**Cause:** n8n version is below 1.22 (no Streamable HTTP support), or a network/firewall issue.

**Fix:**
1. Check your n8n version: **Settings → About**. Upgrade to 1.22+ if needed.
2. From your n8n instance, verify it can reach `https://mcp.fluxprompt.ai` (no corporate firewall blocking HTTPS outbound).

## Still stuck?

Contact the FluxPrompt team with:

1. The exact error message or JSON error response
2. Which client you are using (Claude Desktop / Cursor / n8n / other)
3. Your workspace ID (find it in FluxPrompt **Settings → Workspace**)

Do **not** include your MCP token in any support message.
