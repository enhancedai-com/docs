## Two authentication methods

FluxPrompt's inbound MCP server supports **two** ways to authenticate. Which one you use depends on your client:

| Method | When to use it | What you do |
|---|---|---|
| **OAuth 2.0** | Claude Desktop and Claude.ai (**required** — they reject pasted tokens), and optionally Claude Code / CLI, Codex, and Cursor | Add the server URL as a connector and log in through a FluxPrompt consent screen — **no token** |
| **Static service token** | Backend / machine-to-machine services, the CLI, Codex, OpenCode, Cursor, and n8n — clients that can't or shouldn't run a browser consent flow | Generate a token and put it in the `Authorization` header |

<Info>
**Claude Desktop and Claude.ai users do NOT use a token.** Those clients reject user-pasted bearer tokens, so they authenticate exclusively via OAuth. If a guide tells you to paste a token into Claude Desktop, it is out of date — see [Connect Claude Desktop](/mcp/connect/claude-desktop).
</Info>

## Method 1 — OAuth 2.0

OAuth is the right choice for any client that can open a browser. You never see or handle a token.

1. In your client, add `https://mcp.fluxprompt.ai/mcp` as a custom connector.
2. The client opens a FluxPrompt login + consent screen.
3. You log in and see the list of your **Organizations**. All of them are checked; uncheck the ones you don't want to grant, then click **Authorize** (or **Deny**).
4. The client stores the resulting authorization automatically.

This is **required** for Claude Desktop and Claude.ai, and **supported** by Claude Code / CLI, Codex, and Cursor. See the per-client guides for the exact steps.

### What an OAuth grant includes

- **Scopes.** The client asks for the scopes it wants. If it asks for none, FluxPrompt grants `read` only. You don't pick scopes on the consent screen — you approve or deny what the client asked for. Each selected workspace then clamps the scopes by your role there (see [Scopes are clamped by your role](#scopes-are-clamped-by-your-role)).
- **Workspaces.** You can authorize several organizations in one go. Scopes are worked out **per workspace**, so the same grant can carry `write` in one and `read` in another.
- **Lifetime.** OAuth access tokens **do not expire** by default, and there is **no refresh token**: the server only supports the `authorization_code` grant. The client keeps using the same token until you revoke it in [**Settings → MCP Keys**](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens) (OAuth grants appear there with the type **OAuth**). After a revocation, reconnect the client to authorize again.

## Method 2 — Static service token

For machine-to-machine clients (backend services), the CLI, Cursor, and n8n, you use a **service token** instead of a browser flow.

### Generate a service token

Any active member of a workspace can generate one in the FluxPrompt UI:

1. Open [**Settings → MCP Keys**](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens).
2. Click **Generate key**. In the **Generate MCP key** dialog, enter a **Key name** (for example `n8n`). If you belong to other organizations, you can also tick them under **Also grant this key access to**.
3. Choose the scopes. Workspace admins see the scope checkboxes, with `read` preselected. Other members always get a key with read-only access and can ask an admin to widen it later.
4. Click **Generate**, then copy the key — it starts with `mcp_` and is **shown only once**. Store it somewhere safe.

Admins see every key and OAuth grant in the workspace; other members see only the keys they created.

### Use the token

The token goes in the `Authorization` header of every MCP request:

```
Authorization: Bearer mcp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

You usually don't type this header by hand — your client reads it from its config file (see the connection guides for [Cursor](/mcp/connect/cursor), [n8n](/mcp/connect/n8n), and [local development](/mcp/connect/local-dev)).

## Service token security

<Warning>
A service token gives its holder whatever its scopes allow — at minimum read access to your workspace agents, and with `write` or `execute` the ability to change or run them. Treat it like a password:
- Never commit it to a Git repository.
- Never paste it in a public document or screenshot.
- Never share it on Slack, email, or in any message that others can see.
</Warning>

If you believe a service token has been exposed:

1. Revoke it from [**Settings → MCP Keys**](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens). Workspace admins can revoke any key; other members can revoke only their own.
2. Generate a new one.
3. Update your client config files with the new token.

## Scopes

A key carries one or more of three scopes:

| Scope | Grants |
|-------|--------|
| `read` | List agents and folders, fetch an agent's full structure, browse node types and AI models. |
| `write` | Create and edit agents, folders, nodes and edges; snapshot and publish versions. |
| `execute` | Run an agent, poll a run, cancel a run. |

No scope grants access to billing, users, or workspace settings — those are never exposed over MCP.

### One authorization can cover multiple workspaces

A single OAuth authorization or service token is **not** limited to one organization — the same key
can reach several organizations you belong to (tick them on the consent screen, or under
**Also grant this key access to** when you generate a key), and scopes are set **per workspace**, so a
key can carry `write` in one and only `read` in another. Call
[`list_workspaces`](/mcp/tools/agents-and-folders#list_workspaces) to see every workspace an
authorization covers and its scopes in each.

Because of this, every tool except `list_workspaces`, `list_node_types` and `get_node_type` accepts
an optional `workspaceId` parameter:

- Omit it when the authorization covers exactly one workspace — it is inferred automatically.
- Pass it when the authorization covers more than one. A call that omits it in that case is refused
  with `workspace_required`, and the error lists the covered workspace ids so you can choose.

### Scopes are clamped by your role

If you are not an admin of an organization, requesting `write`/`execute` there yields a grant
clamped to `read` instead of an error — this applies to each organization separately. A workspace
admin controls this with the **Let regular members create powerful keys** toggle in
[Settings → MCP Keys](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens). It is **on by
default**; when an admin turns it off, non-admin members get `read` only. The toggle is checked only
when a key is created or an app is reconnected, so keys that already exist keep the scopes they were given.

### Change a key's scopes

A workspace admin can change the scopes of an existing key at any time — there is no need to revoke it
and issue a new one. In [Settings → MCP Keys](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens),
the scopes cell of each key in the keys table shows the current scopes as chips with an edit
(pencil) icon next to them. Click either the chips or the icon, tick the scopes you want, and save.
Non-admins see the same chips as read-only.

How long the change takes to reach the client depends on the direction:

| Change | When it takes effect |
|--------|----------------------|
| Removing a scope (for example `read` + `write` → `read`) | Immediately — the core API reads the key's current scopes on every call. |
| Adding a scope (for example `read` → `read` + `write`) | Within `MCP_TOKEN_CACHE_TTL` seconds — **10 by default**. |

The MCP server caches the resolved key, scopes included, for `MCP_TOKEN_CACHE_TTL` seconds to avoid a
round-trip to the core API on every call. So right after an admin grants `write`, the client can keep
being refused for a few seconds. Retry after ~10 seconds, or reconnect the client.

<Note>
The cache can only delay a grant — it can never hand out more access than the key currently carries,
because the core API validates every call against the key's current scopes.
</Note>

### Workspace-level switches

Even with the right scope, two workspace switches must be on. A workspace admin controls them in
**Settings → MCP Keys**, under **What connected AI assistants are allowed to do**. Both are **on by
default**.

| Switch in the UI | Internal name in refusals | Turns off |
|------------------|---------------------------|-----------|
| **Let AI assistants change things** | `mcp.writes.enabled` | Every write tool for this workspace. |
| **Let AI assistants run agents** | `mcp.execute.enabled` | `run_agent` for this workspace. Runs started from the app itself are not affected. |

These switches are an **independent** gate: the right scope on the key is not enough while the switch is
off. The two refusals read differently, which tells you which one to fix:

| Refusal | What it means |
|---------|---------------|
| `-32401 Insufficient scope`, with `data.required` naming the scope that was missing | The key does not carry that scope. Edit the key's scopes. |
| `Tool execution failed: ERROR <id>: feature_disabled: mcp.writes.enabled is off for this workspace` (or `mcp.execute.enabled`) | The key's scopes are fine — the workspace switch is off. Turn the switch on. |

The `<id>` in the second one is a different value on every call, so search your logs for
`feature_disabled:` rather than for the whole line.

Either way, the fix is in the same place: **Settings → MCP Keys**.

Runs started through MCP are billed and audited against the **owner of the key** that started them, and
the triggering key/client name appears in the agent's execution history.

## FAQ

<AccordionGroup>
  <Accordion title="Which method should I use?">
    If your client is Claude Desktop or Claude.ai, you must use OAuth. For backend services, the CLI, or n8n, use a service token. Cursor and Claude Code can use either — OAuth is simplest if you can open a browser.
  </Accordion>
  <Accordion title="Can I have multiple service tokens for the same workspace?">
    Yes — each token is independent. You can have one token per client (e.g. one for n8n, one for a backend service) and revoke them individually from [**Settings → MCP Keys**](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens).
  </Accordion>
  <Accordion title="Does a service token expire?">
    Neither service tokens nor OAuth access tokens expire automatically. They remain valid until revoked, and there is no refresh flow. We recommend revoking keys you no longer use.
  </Accordion>
  <Accordion title="Can I use my regular FluxPrompt API key instead?">
    No. The MCP server uses a separate authentication system. Your regular API key will not work.
  </Accordion>
  <Accordion title="What does the MCP server see about my workspace?">
    It sees the same agents and structure that the authenticated user can see inside the FluxPrompt UI. It does not have access to credentials, billing, or user management.
  </Accordion>
  <Accordion title="I granted someone write access but their client still only has read">
    Check these in order:
    1. **The workspace switches.** **Let AI assistants change things** (`mcp.writes.enabled`) and **Let AI assistants run agents** (`mcp.execute.enabled`) are an independent gate from the key's scopes — a key that carries `write` is still refused while the switch is off. A switch refusal contains `feature_disabled:`, not `Insufficient scope`.
    2. **Give it a few seconds.** The MCP server caches resolved keys for `MCP_TOKEN_CACHE_TTL` seconds (10 by default), so a newly added scope can take that long to apply. Retry after ~10 seconds, or reconnect the client.
    3. **Confirm the change saved.** Reopen [**Settings → MCP Keys**](https://app.fluxprompt.ai/dashboard-beta?settings=mcpTokens) and check that the key's scopes cell shows the scopes you expect.
    4. **Confirm the client is not holding an old session.** Some clients only re-read the available tools and permissions when they reconnect.
  </Accordion>
</AccordionGroup>
