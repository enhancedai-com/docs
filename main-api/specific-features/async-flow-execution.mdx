title: "Asynchronous flow execution"
description: "How POST /flux/api-v2 queues a run: the flow_execution_status record, the 202 + statusUrl contract, the GET /flux/executions/:id poll endpoint, and the concurrency and wait-timeout knobs."
---

Every call to `POST /flux/api-v2` is queued. The request no longer runs the flow on the request
thread — it writes a `flow_execution_status` row, puts a job on the api-v2 queue, and then decides
whether to wait for the result or hand the caller a URL to poll.

This is what makes a long flow survive a client timeout, and what stops a burst of API calls from
running an unbounded number of flows at once.

## The two response shapes

Which one you get depends on a single query parameter: `callback_url`.

| Call | What the API does | Response |
|---|---|---|
| **With `callback_url`** | Enqueues and returns straight away. The result is POSTed to your URL when the run finishes. | `202` + `{ executionId, statusUrl }` |
| **Without `callback_url`** | Enqueues, then waits up to `AGENT_WAIT_TIMEOUT_MS` for the run to finish. | `200` with the output if it finished in time, otherwise `202` + `{ executionId, statusUrl, status: "in_progress" }` |

So the second form is *opportunistically* synchronous: a fast flow still answers in one round trip,
exactly as it did before, and only a slow one degrades into a poll.

<Note>
  `202` is not an error and does not mean the run failed — it means the run outlived the wait window
  and is still going. Poll `statusUrl` until `status` is `completed` or `error`.
</Note>

### `callback_url` validation

The parameter is rejected with `400 Bad Request` before anything is enqueued when it is repeated in
the query string (*"callback_url must be a single string value"*), is not a parsable URL
(*"callback_url is not a valid URL"*), or uses a scheme other than `http`/`https`
(*"callback_url must use http or https protocol"*). An empty value is treated as absent.

## Requesting a run

```http
POST /flux/api-v2?flowId=<flowId>&callback_url=https://example.com/hook
x-api-key: <api key>
Content-Type: application/json
```

`sessionId` and `versionId` are still accepted and unchanged.

```json
{
  "executionId": "6f1c9f0e-6a5a-4d4b-9c2f-5f1d4e2b7a10",
  "statusUrl": "https://api.fluxprompt.ai/flux/executions/6f1c9f0e-6a5a-4d4b-9c2f-5f1d4e2b7a10"
}
```

`executionId` is generated by the API before the job is queued, and it is also the Bull job id, so the
id in your hand always matches the row and the job. `statusUrl` is built from `API_URL` when that is
set, and falls back to the protocol and host of the incoming request.

### When the wait window is used

Without `callback_url` the controller races the job against the timeout:

| Outcome | Status | Body |
|---|---|---|
| The run finished in time | `200` | The flow's output, in the standard success envelope |
| A node failed | `400` | `{ "status": "error", "data": { "message": "<node error>" } }` |
| The wait elapsed first | `202` | `{ executionId, statusUrl, status: "in_progress" }` |
| The job itself threw | `500` | `{ executionId, statusUrl, error: "<message>" }` |

On the `500` path the message is read back from the `flow_execution_status` row when the processor
recorded one, so the caller gets the real failure rather than a generic wrapper.

## Polling a run

```http
GET /flux/executions/:executionId
x-api-key: <api key>
```

The id must be a UUID — anything else is a `400`. The lookup is scoped to the caller, so an id that
exists but belongs to somebody else answers exactly like one that does not exist:

```json
{ "status": "error", "data": { "message": "Execution not found" } }
```

with `404 Not Found`.

Every successful response carries the same base:

```json
{
  "executionId": "6f1c9f0e-6a5a-4d4b-9c2f-5f1d4e2b7a10",
  "flowId": "0b4a2f3e-1c8d-4f5a-8e7b-2d9c6a1f0b33",
  "status": "in_progress",
  "createdAt": "2026-08-24T13:41:02.113Z",
  "startedAt": "2026-08-24T13:41:02.702Z",
  "finishedAt": null
}
```

and the terminal statuses add to it:

| `status` | Extra fields |
|---|---|
| `pending` | — the job is queued and has not started |
| `in_progress` | — the job is running |
| `completed` | `output`, `tokensUsed`, `totalCost`, `durationMs` |
| `error` | `errorMessage` |

`startedAt` stays `null` while the run is `pending`, and `finishedAt` is only set once the run reaches
`completed` or `error`.

## What the run is recorded in

The queue writes to its own table rather than reusing the node-level tables:

```ts
// back/src/entities/flow_execution_status.entity.ts
@Entity('flow_execution_status')
@Index('IDX_flow_exec_flow_id', ['flowId'])
@Index('IDX_flow_exec_user_id', ['userId'])
```

The row is created by the controller (status `pending`) before the job is enqueued, so a status URL is
answerable the instant the caller receives it — there is no window where the id exists but the row
does not. `callbackUrl` is stored on the row, which is why a callback still fires for a run whose HTTP
request was abandoned long ago.

Created by migration `CreateFlowExecutionStatus`.

## Tuning

| Var | Default | Effect |
|---|---|---|
| `AGENT_CONCURRENCY` | `5` | How many api-v2 flow executions run at the same time. It is the Bull processor's concurrency, so extra calls queue instead of being rejected. |
| `AGENT_WAIT_TIMEOUT_MS` | `30000` | How long a call **without** `callback_url` waits for the result before answering `202` with the `statusUrl`. Ignored when a callback URL is given. |

Both are parsed defensively: a missing, non-numeric, or non-positive value falls back to the default
rather than disabling the queue or the wait.

<Warning>
  Raising `AGENT_CONCURRENCY` raises the number of flows — and therefore the number of AI provider
  calls — the API runs in parallel. It is the only thing standing between a burst of API traffic and
  an unbounded fan-out, so change it with the provider rate limits in mind.
</Warning>
