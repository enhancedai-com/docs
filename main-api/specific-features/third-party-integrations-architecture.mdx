## Overview

The third-party integrations system acts as a bridge between your FluxPrompt flows and external services — WordPress, Slack, Notion, Stripe, HubSpot, QuickBooks, ClickUp, Supabase, Zapier and MCP servers. Every integration operates in one of two modes:

- **Pull mode** — fetch data from an external service into your flow (e.g., read Notion pages, list Slack channels).
- **Push mode** — send data from your flow to an external service (e.g., post a Slack message, create a Stripe product).

Some providers support both modes; others support only one.

## User journey

The lifecycle of an integration follows three phases:

1. **Connect** — You save credentials (API key, OAuth token, or webhook URL) to link your account.
2. **Use in flow** — You add a Third Party Integration node to a flow and select the connected provider.
3. **Collaboration** — Other workspace members can use your connection via `connectedByUserId`, without seeing your raw credentials.

### Connection states

Every integration node can be in one of three states from the perspective of the current user:

| State | Meaning |
|---|---|
| **Connected by me** | You authenticated the integration yourself. |
| **Connected by another user** | A teammate connected and shared access via `connectedByUserId`. |
| **Not connected** | No credentials exist; the node cannot run until someone connects. |

## Supported providers

| Provider | Auth method | Pull | Push | In production |
|---|---|---|---|---|
| WordPress | Credentials (URL + app password) | Yes | Yes | Yes |
| Slack | OAuth | Yes | Yes | Yes |
| Zapier | Webhook URL | Yes | Yes | Yes |
| Stripe | Secret API key | Yes | Yes | Yes |
| Notion | OAuth | Yes | Yes | Yes |
| HubSpot | OAuth | Yes | Yes | Yes |
| MCP | Credentials (API key or token, per transport) | Yes (list tools) | No | Yes |
| ClickUp | OAuth | Yes | Yes | 🚧 Not yet |
| Supabase | Credentials (project URL + service role key) | Yes | Yes | 🚧 Not yet |
| QuickBooks | OAuth (company selected at consent; `realmId` scopes every call) | Yes | Yes | 🚧 Not yet |

<Warning>
  The three providers marked **🚧 Not yet** are complete on the development branches — adapter,
  provider config, and enum value — but no production release has shipped them. On production the
  `user_integrations.provider` enum accepts only `microsoft`, `google`, `hubspot`, `wordpress`,
  `slack`, `stripe`, `notion`, `zapier` and `mcp`, so a connection for ClickUp, Supabase or
  QuickBooks cannot even be saved there. Their pages carry the same marker.
</Warning>

## Adapter pattern

Every provider is implemented as a class that conforms to the `IIntegrationProviderAdapter` interface. This keeps provider-specific logic isolated and makes the system easy to extend.

<Tip>
The adapter pattern means you can add a new provider without modifying any existing provider code. Each adapter is self-contained and registered once in the service layer.
</Tip>

```typescript
export interface IIntegrationProviderAdapter {
  /** 'oauth' | 'credentials' | 'webhook'. A readonly property, not a method. */
  readonly connectionMode: IntegrationConnectionMode;

  /** Opt in to CSRF state verification on the OAuth callback. */
  readonly requiresStateVerification?: boolean;

  /** Build the provider's authorization URL. */
  getInstallUrl(userId: string, state?: string): Promise<string>;

  /** Exchange an authorization code for tokens. */
  exchangeCode(code: string): Promise<OAuthTokenResult>;

  /** Refresh an access token. Receives the whole row, not just the token. */
  refreshAccessToken(integration: UserIntegration): Promise<OAuthTokenResult>;

  /** Store user-supplied credentials. Credentials-mode providers only. */
  connectWithCredentials?(
    userId: string,
    credentials: Record<string, unknown>,
  ): Promise<CredentialsConnectResult>;

  pull(
    integration: UserIntegration,
    payload: Record<string, unknown>,
    context?: Record<string, unknown>,
  ): Promise<unknown>;

  push(
    integration: UserIntegration,
    payload: Record<string, unknown>,
  ): Promise<unknown>;

  /** Dynamic dropdown options. `context` carries the other form values,
   *  plus `search` for type-ahead and `ids` to resolve stored ids to labels. */
  getOptions?(
    integration: UserIntegration,
    fieldName: string,
    context?: Record<string, string>,
  ): Promise<Array<{ label: string; value: string }>>;

  /** Schema for filter builders and property editors. Notion and Supabase use these. */
  getDatabaseSchema?(integration: UserIntegration, databaseId: string): Promise<Schema>;
  getDatabaseSchemaFromRecordId?(integration: UserIntegration, recordId: string): Promise<Schema>;

  testConnection?(identity: ConnectionTestIdentity): Promise<ConnectionTestResult>;
}
```

Three things about this interface are easy to get wrong:

- **Every method receives the whole `UserIntegration` row**, not a loose token or a params bag. `refreshAccessToken` in particular needs the row, because a rotating refresh token has to be read from and written back to it.
- **Only `connectionMode`, `getInstallUrl`, `exchangeCode`, `refreshAccessToken`, `pull` and `push` are required.** Everything else is optional and exists because some provider needed it: `getOptions` for dropdowns, `getDatabaseSchema*` for Notion's filter builder and Supabase's table columns, `connectWithCredentials` for the non-OAuth providers, `testConnection` for the connection card.
- **`getOptions` must honour both `context.search` and `context.ids`.** `search` powers type-ahead; `ids` resolves an already-stored id back to its human label, which is what stops a saved flow from showing a raw provider id to the user. A picker that ignores `ids` looks fine when you build it and shows a UUID after a page reload.

<Note>
QuickBooks adds an optional second parameter to `exchangeCode` (`oauthParams`), because Intuit returns the company id as its own callback query parameter rather than inside the token response. It is optional, so existing adapters are unaffected. See the [QuickBooks page](/main-api/specific-features/integrations/quickbooks).
</Note>

## Where a node executes

A Third Party Integration node does not always run in the same process, and the difference matters when you are debugging one.

**Editor-time operations always run in the API.** Connecting, refreshing a token, loading a dropdown (`getOptions`), fetching a schema, testing a connection — all of these are API endpoints, for every provider, always.

**Execution — `pull` and `push` during a flow run — is being moved into the Temporal worker, one provider at a time.** The back keeps a set of migrated providers; when a node's provider is in that set, the back stops executing it inline and dispatches to the worker instead, which holds its own copy of the adapter's runtime path. The provenance of each ported adapter is recorded in `PORTED_FROM.md` in the worker's `third-party-integration` module.

The set is `MIGRATED_INTEGRATION_PROVIDERS` in `back/src/shared/integration/integration-executable-node.ts`, and it is the **only** thing that decides where a provider runs — no environment flag is involved. Nothing else in the routing code names a provider, so releasing one is a single-line change.

### Rollout to production

Providers reach production one release at a time, each as its own deploy. A provider absent from this table still executes inline in the back on production, even though the worker already carries its adapter.

| Provider | On the worker in production | Release |
|---|---|---|
| Stripe | yes | `868ke6j3r` |
| WordPress | yes | `868ke6j56` |
| Slack | yes | `868ke6j6m` |
| Notion | yes | `868ke6j7t` |
| Zapier | yes | `868ke6j9d` |
| HubSpot | yes — both `thirdPartyIntegration` and the dedicated `hubSpotCRM` node | `868ke6jb7` |

<Note>
The worker ships **every** ported adapter as soon as the first provider is released, because the module builds its adapter map in one factory. An adapter present in the worker is therefore not evidence that its provider is routed there — only the back's set is. This is deliberate: hand-trimming the registry per release is how an inline-vs-worker behaviour difference would get introduced unnoticed.
</Note>

Two consequences worth knowing:

- **The worker needs the provider's OAuth client credentials too**, not just the API. It refreshes access tokens during a run, so a worker missing `<PROVIDER>_CLIENT_ID`/`_SECRET` fails every node on a connection whose token has expired — while the same node works fine in the editor, because the editor path never leaves the API.
- **The rollout is per environment.** An environment that has not received the worker routing still executes every provider inline in the back. A provider can therefore behave correctly in one environment and fail in another with the same flow, and the difference is where it ran.

<Warning>
When a provider is migrated, **deploy the worker before the back**. The back's routing flag is what stops inline execution; if it ships first, the worker's registry does not yet contain the adapter and every node for that provider fails with "this integration provider is not supported by the worker yet".
</Warning>

## Adding a new provider (backend)

<Steps>
  <Step title="Create the adapter">
    Add a new file at `src/app-api/integrations/adapters/<provider>.adapter.ts` that implements `IIntegrationProviderAdapter`. Define the connection mode, authentication flow, and pull/push logic for your provider.
  </Step>
  <Step title="Register in IntegrationsService">
    Open `IntegrationsService` and add your adapter to the provider map so the service can resolve it at runtime:

    ```typescript
    this.adapters.set(IntegrationProvider.NEW_PROVIDER, new NewProviderAdapter());
    ```
  </Step>
  <Step title="Register the adapter as a NestJS provider">
    Add the adapter class to the providers array in `AppApiModule`, and inject `HttpModule` if it makes HTTP calls. Registering it in the service map is not enough — without this, Nest cannot construct it.
  </Step>
  <Step title="Add to the provider enum, with a migration">
    Add a new entry to the `IntegrationProvider` enum:

    ```typescript
    export enum IntegrationProvider {
      // ...existing providers
      NEW_PROVIDER = 'new_provider',
    }
    ```

    The enum is backed by a Postgres enum type, so **the code change alone is not enough** — a migration has to extend the database type or every insert for the new provider fails:

    ```typescript
    await queryRunner.query(
      `ALTER TYPE "user_integrations_provider_enum" ADD VALUE IF NOT EXISTS 'new_provider'`,
    );
    ```
  </Step>
  <Step title="Port the runtime path to the worker">
    A new provider is delivered with its worker adapter in the same change, not handed off to be migrated later. That means the runtime `pull`/`push` subset, its own HTTP helper (global `fetch`, not `@nestjs/axios`), its own error classification, an entry in the worker's adapter registry, and the provider string added to the back's migrated-providers set. Editor-time operations stay in the API and are deliberately not ported.
  </Step>
</Steps>

<Tip>
Every value a user could not reasonably know by heart — a customer id, an invoice number, a channel, a database, a table — must be a searchable picker backed by `getOptions`, never a free-text field. This is a hard rule for the node, not a preference: the Third Party Integration node is used by non-technical people, and asking them to paste a provider's internal id means asking them to leave FluxPrompt to find it.
</Tip>

## Adding a new provider (frontend)

<Steps>
  <Step title="Create a config file">
    Add a config file that describes the UI for your provider: display name, icon, connection fields, pull/push option schemas, and any help text. This file lives alongside the other provider configs in the frontend integrations directory.
  </Step>
  <Step title="Register in registry.ts">
    Import your config and add it to the provider registry so the Third Party Integration node can render the correct UI when a user selects your provider.
  </Step>
</Steps>

## Database schema

Integration credentials are stored in the `user_integrations` table:

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key |
| `userId` | UUID | Owner of the connection |
| `name` | varchar(255) | User-facing connection label (nullable) |
| `provider` | enum | Provider identifier — backed by a Postgres enum type, so adding one needs a migration |
| `providerAccountId` | text | External account id (nullable). QuickBooks stores the `realmId` here |
| `accessToken` | text | OAuth access token |
| `refreshToken` | text | OAuth refresh token |
| `expiresAt` | timestamp | Access-token expiry, used to decide when to refresh |
| `apiCredentialsEncrypted` | text | Non-OAuth credentials, AES-256-GCM encrypted |
| `metadata` | JSONB | Provider-specific extra data (workspace id, realm, environment, MSAL cache…) |
| `isSharedWithOrg` | boolean | Whether teammates may use this connection |

**A user can hold several connections to the same provider.** There was a `UNIQUE (userId, provider)` constraint originally; it was dropped and replaced by a plain index so a user could connect, for example, two Slack workspaces. This is what the connection picker and `integrationId` on the node exist for — code that assumes one row per `(userId, provider)` is wrong.

<Warning>
Treat every credential column in this table as sensitive. A token or credentials blob read out of `user_integrations` is enough to act as that user in the external service — no password and no second factor involved. Never log one, never return one from an endpoint, and never copy a row between environments.
</Warning>

## Credential sharing

When a flow is shared or collaboratively edited, the integration node stores a `connectedByUserId` field in `node.data`. At execution time the system uses the following fallback logic:

1. Try the **current user's** credentials for the provider.
2. If none exist, try the credentials of the user identified by `connectedByUserId`.
3. If the provider is webhook-based, fall back to a **webhook stub** (Zapier).
4. If no credentials can be resolved, return an **error** prompting the user to connect.

### Sharing a connection with the organization

Separate from that per-node fallback, a connection can be offered to the whole company by setting `isSharedWithOrg`. The connection picker then lists, for a given provider:

- every connection **owned by the current user**, and
- connections owned by **other active members of the same company**, but only those with `isSharedWithOrg = true`.

Company membership is read from `company_user` with `status = 'active'`, so revoking someone's membership immediately removes their shared connections from everyone else's picker. With no company in context, only the user's own connections are listed.

This is why a teammate can run a flow whose integration they never connected — and why the node shows **Connected by another user** rather than prompting them to authenticate.

## Module structure

There is **no dedicated `IntegrationsModule`**. The controllers, the service and every adapter are declared in `AppApiModule`, which is why adding a provider means editing that file — registering the adapter in the service's map alone leaves Nest unable to construct it.

`src/app-api/integrations/` holds:

| File | Role |
|---|---|
| `integrations.controller.ts` | The editor-facing REST surface, behind `JwtAuthGuard` — connect, disconnect, status, pull, push, `getOptions`, schema |
| `integrations-api.controller.ts` | The same domain exposed to external callers behind `ApiKeyGuard` |
| `slack-public.controller.ts` | Unauthenticated by design — receives Slack's event callbacks, which arrive from Slack rather than from a logged-in user |
| `integrations.service.ts` | Resolves the adapter by provider key, owns credential CRUD, and orchestrates pull/push |
| `oauth-state.service.ts` | Issues and verifies the OAuth `state` value, for adapters that set `requiresStateVerification` |
| `slack-events.service.ts` | Handles the Slack Events API payloads |
| `zapier-webhook-*.service.ts` | The shared store, archive and trigger path for inbound Zapier webhooks |
| `adapters/*.adapter.ts` | One per provider, injected through the DI container |

Each adapter is unit-testable in isolation — mock its HTTP helper and assert the request it builds — which is how the provider suites are written.

<Note>
OAuth `state` is verified only for adapters that opt in via `requiresStateVerification`. It is not applied uniformly across providers, so do not assume a callback was CSRF-checked without looking at the adapter.
</Note>
