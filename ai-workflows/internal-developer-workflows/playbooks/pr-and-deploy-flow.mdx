## When to use this

You finished work on a ClickUp task and need to ship it. This is the team's standard end-to-end flow.

## The five stages

```
┌───────────┐   ┌─────┐   ┌────────┐   ┌────────┐   ┌──────────────┐
│ ClickUp   │ → │ PR  │ → │ Review │ → │ Deploy │ → │ Announcement │
└───────────┘   └─────┘   └────────┘   └────────┘   └──────────────┘
```

## Branch convention

| Repo | Dev branch | Staging branch | Production branch |
| --- | --- | --- | --- |
| Flux-Prompt (`back/`) | `develop` | `staging` | `main` |
| Flux-Prompt-Frontend (`front/`) | `develop` | `staging` | `main` |
| Flux-Prompt-Worker (`worker/`) | `develop` | `staging` | `main` |
| FluxPrompt-MCP (`mcp/`) | `develop` | `staging` | `main` |

The legacy `production` and `master` branches are frozen since 2026-10-13. Never branch from them or target a PR at them.

Feature branches follow `<change_type>/<task_code>` where `change_type` ∈ `fix`, `feat`, `refactor`, `chore`. Example: `feat/868jk7x3j`.

This page covers the PR and deploy end of the lifecycle. The whole lifecycle, from the ticket to docs, is the [Delivery practice](/engineering/ways-of-working/delivery).

All PRs target `main`. To test on dev or staging, merge your feature branch into `develop` or `staging` and push. Never merge `develop` or `staging` into your feature branch. The full flow is in [Git workflow](/getting-started/git-workflow).

## Stage 1 — Create the PR

Use the [`pr-creator` agent](/ai-workflows/internal-developer-workflows/agents/pr-creator) with the ClickUp task code:

```
use the pr-creator agent — https://app.clickup.com/t/868jk7x3j
```

The agent finds the task's branches in `back/`, `front/`, `worker/`, `mcp/` and `docs/`, refuses a head that is an env branch or carries `develop` or `staging` merges, formats the title (`[FEAT] Imperative name`), fills the body (Description / Preview / Test map / Plan / References), runs `gh pr create --base main`, and cross-links the PRs. It never merges and never runs a deploy.

## Stage 2 — Review

Standard team review. The agent leaves `Preview` as a placeholder for you to fill with screenshots/logs before requesting review.

## Stage 3 — Deploy

### CI/CD triggers (`back/`)

| Workflow | Trigger | Behavior |
| --- | --- | --- |
| `cicd_dev.yml` | `push` to `develop` or `workflow_dispatch` | Auto-deploy to ECS dev |
| `cicd_staging.yml` | `push` to `staging` or `workflow_dispatch` | Auto on push, manual on demand |
| `cicd_prod.yml` | `workflow_dispatch` **only** | Manual command — never auto-deploys |

Front repo has the equivalent S3 deploys: `Deploy to S3 Dev` (push to `develop`), `Deploy to S3 Staging` (push to `staging`), `Deploy to S3 Prod` (`workflow_dispatch`). Every prod workflow (back `cicd_prod.yml`, front `cicd-prod.yaml`, worker `cicd_prod.yml`, mcp `cicd_prod.yml`) is `workflow_dispatch` only: a PR merged into `main` ships nothing until a person runs it. Running it is always a person's decision, never an agent's.

When GitHub Actions is blocked (out of minutes), deploy from your machine with the `deploy-direct` skill (`scripts/deploy-direct/deploy.sh` in the Workflow repo).

### Production deploy command

```bash
gh workflow run cicd_prod.yml --ref main
```

The workflow builds an image tagged with `${{ github.sha }}` of `main`, pushes to ECR, renders the task definition, and deploys to `api-service-prod`.

### Watch the rollout

```bash
aws ecs describe-services \
  --cluster enhancedai-prod \
  --services api-service-prod \
  --region us-east-1 \
  --query 'services[0].{desired:desiredCount,running:runningCount,pending:pendingCount,deployments:deployments[].rolloutState}'
```

### See what commit is live

```bash
aws ecs describe-task-definition \
  --task-definition api-task-definition-prod \
  --query 'taskDefinition.containerDefinitions[0].image' \
  --region us-east-1
```

The SHA tag in the image URI equals the git commit.

A green deploy is not a finished rollout: confirm the new task is the only one serving before concluding anything about a new route or fix. Then run the `prod-health` skill, and for a deploy that carried a migration, check read-only that the migration is recorded and the API booted cleanly.

## ECS topology (back/, us-east-1)

| Env | Cluster | Service | Task def family | ECR repo |
| --- | --- | --- | --- | --- |
| Dev | `enhancedai-dev` | `api-service-dev` | `api-task-definition-dev` | `enhancedai-ecr-dev` |
| Staging | `enhancedai-staging` | `api-service-staging` | `api-task-definition-staging` | `enhancedai-ecr-staging` |
| Prod | `enhancedai-prod` | `api-service-prod` | `api-task-definition-prod` | `enhancedai-ecr-prod` |

CloudWatch log groups: `/ecs/api-task-definition-{dev,staging,prod}` (us-east-1).

Container env is mostly empty — secrets come from AWS Secrets Manager. Adding a runtime knob means adding to `containerDefinitions[0].environment` in the task definition and registering a new revision.

## Resizing a task definition

When a task needs more CPU/memory (e.g., after diagnosing a [memory leak](/ai-workflows/internal-developer-workflows/playbooks/memory-leak-diagnosis)):

<Warning>
  Registering a task definition and updating a service in prod are production infrastructure writes. They need explicit authorization from the owner for that specific change; prepare the commands with what they do and how to revert them, and let the owner run them.
</Warning>

<Steps>
  <Step title="Pull current task def JSON">
    ```bash
    aws ecs describe-task-definition \
      --task-definition api-task-definition-prod \
      --query 'taskDefinition' --region us-east-1 > taskdef.json
    ```
  </Step>
  <Step title="Strip read-only fields">
    Remove: `taskDefinitionArn`, `revision`, `status`, `requiresAttributes`, `compatibilities`, `registeredAt`, `registeredBy`, `deregisteredAt`.
  </Step>
  <Step title="Edit cpu and memory">
    Update the top-level `cpu` and `memory` values. Preserve `requiresCompatibilities` exactly — dev/staging include `MANAGED_INSTANCES` alongside `FARGATE`; prod is `FARGATE` only.
  </Step>
  <Step title="Write the file without a BOM">
    On Windows PowerShell, `Out-File -Encoding utf8` writes UTF-16 LE with BOM, which AWS CLI rejects. Use:
    ```powershell
    [System.IO.File]::WriteAllText(
      "$pwd\taskdef.json",
      $json,
      (New-Object System.Text.UTF8Encoding $false)
    )
    ```
  </Step>
  <Step title="Register the new revision">
    ```bash
    aws ecs register-task-definition --cli-input-json file://taskdef.json --region us-east-1
    ```
  </Step>
  <Step title="Update the service">
    ```bash
    aws ecs update-service \
      --cluster enhancedai-prod \
      --service api-service-prod \
      --task-definition api-task-definition-prod:<new-rev> \
      --force-new-deployment \
      --region us-east-1
    ```
  </Step>
</Steps>

<Warning>
  Setting `--max-old-space-size` larger than the container memory budget causes silent SIGKILL (exit 137, no V8 trace). Always keep V8 heap ≤ ~85% of container memory.
</Warning>

## Stage 4 — Deploy announcement

After the rollout completes, use the `deploy-announcer` agent (or, for the PRs created in the same session, step 10 of the [`pr-creator` agent](/ai-workflows/internal-developer-workflows/agents/pr-creator)). A PR counts only when a successful prod workflow run in the window contains its merge commit; merged PRs not yet deployed are listed apart. The message:

```
Hey team, I just deployed the following to production:

- <Task name 1> — https://app.clickup.com/t/<task_code_1>
- <Task name 2> — https://app.clickup.com/t/<task_code_2>

Please give me a shout if anything looks off after the rollout. Thanks!
```

Format rules:

- Plain text (no markdown bold/italic — Google Chat renders plain text)
- No emojis
- One bullet per ClickUp task, even if it had PRs in both repos
- Em dash (`—`) between task name and URL

The agent copies the message to your clipboard. Paste into the team channel, then move each card to `deployed on live`.
