## Overview

The `generateFileActivity` asks the main API to turn a node's text into a file and returns the file URL. It lives in `src/modules/temporal/activities/activities.service.ts`.

<Warning>
This activity makes a real HTTP call, but it is **dead code**: no live workflow invokes it. It is registered in `worker.service.ts` and proxied in `workflows/configs.ts`, and the only reference in a workflow is a commented-out block in `process-agent.workflow.ts`. `processAgent` itself is not exported from `workflows/index.ts`, so the worker does not register it. Until something calls this activity, it never runs in production.
</Warning>

The back endpoint behind it, `POST /worker/generate-file`, is live: the Display Box (`display-box.service.ts`) and Report Builder (`report-builder.service.ts`) services call it directly with `fetch`, not through this activity.

## Signature

```typescript
async generateFileActivity({
  nodeId: string,
  fileType: string
}): Promise<string>
```

## Inputs

| Parameter | Type | Description |
|-----------|------|-------------|
| `nodeId` | `string` | ID of the node whose text becomes the file |
| `fileType` | `string` | File type passed to the back's `uploadService.uploadText` |

## Outputs

Returns the `file` field of the back's JSON response: the URL of the uploaded file. When the back refuses the request (for example 400 because the node has no text), the response has no `file` and the activity returns `undefined`; it does not check the HTTP status.

## Implementation details

The activity sends `POST ${URL_MAIN_API}/worker/generate-file` with `{ nodeId, fileType }` and the `internal-api-key` header, then returns `data.file`. The file is generated on the back, not in the worker.

## Back endpoint

`WorkerController.generateFile` in `back/src/temporal/worker.controller.ts`:

- **Request body**: `{ nodeId, fileType, text?, customFileName?, useDocRaptor?, userId?, flowId?, flowVersionHistoryId?, spaceId?, provider? }`
- Without `text`, it reads `data.text` from the node row. Without any text, it returns `400 { success: false, message: 'No text content available to generate file' }`.
- It uploads the file with `uploadService.uploadText`; an upload failure returns `500 { success: false, message: 'Failed to generate file' }`.
- With `userId`, it records the file through `generatedFileService.persist` (provider defaults to `outputController`).
- It writes `fileLink` (`{ src, name }`) onto the node's `data` and appends the URL to `data.fileLinks`.
- **Response on success**: `200 { success: true, message: 'File generated successfully', file, fileLink }`

Because this activity sends only `nodeId` and `fileType`, the back looks the node up by `nodeId` alone, without the flow and version scope (`flowId`, `flowVersionHistoryId`) the other callers can pass.
