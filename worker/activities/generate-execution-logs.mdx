## Overview

The `generateExecutionLogsActivity` creates log entries in the database to track workflow executions. These logs are used for debugging, auditing, and monitoring workflow performance.

## Purpose

- Track workflow execution history
- Record success and failure information
- Store error stack traces for debugging
- Maintain execution metadata for analysis
- Enable workflow auditing and compliance

## When it's executed

This activity is called at two key points:

1. **After successful execution**: Logs successful node completion with execution details
2. **On error**: Logs error information including stack traces and error messages

## Signature

```typescript
async generateExecutionLogsActivity({
  execId: string,
  nodeId: string,
  flowId: string,
  flowVersionHistoryId: string | null,
  userId: string,
  sessionId: string,
  message: string,
  userMessage?: string | null,
  errorStack?: string | null,
  errorCategory?: string | null,
  errorField?: string | null,
  isError: boolean,
}): Promise<void>
```

## Inputs

| Parameter | Type | Description |
|-----------|------|-------------|
| `execId` | `string` | Execution id this log belongs to; also drives the broader post-insert behavior below |
| `nodeId` | `string` | ID of the node being logged |
| `flowId` | `string` | ID of the flow containing the node |
| `flowVersionHistoryId` | `string \| null` | Version history id for the flow, used when resetting stale node output on error |
| `userId` | `string` | ID of the user executing the workflow |
| `sessionId` | `string` | Session identifier for tracking execution context |
| `message` | `string` | Dev-facing log message describing the execution result |
| `userMessage` | `string \| null` (optional) | User-facing message; combined with `message` in the node's `errorMessage` when both are set and differ |
| `errorStack` | `string \| null` (optional) | Error stack trace (omitted for successful executions) |
| `errorCategory` | `string \| null` (optional) | Error classification (e.g. the thrown error's `NodeError` subclass) |
| `errorField` | `string \| null` (optional) | The node data field the error is attributed to, when known |
| `isError` | `boolean` | Flag indicating whether this is an error log |

There is no `metadata` parameter — the activity does not accept one. The `execution_logs.metadata` column is always written as a literal `null` by this INSERT.

## Outputs

Returns `void`. The activity completes when the log entry is successfully created (and, when `execId` is present, after the additional updates described below).

## Implementation details

The activity inserts one row into `execution_logs` — `nodeId`, `flowId`, `userId`, `sessionId`, `message`, `userMessage`, `errorStack`, `errorCategory`, `errorField`, `metadata` (always `null`), `isError`, `execId`. For an error log with an `execId`, the insert is deduplicated: it's skipped (no row, no side effects below) if an error log already exists for that exact `(flowId, nodeId, execId)` triple.

This activity does **more** than insert a log row — when `execId` is present, it also keeps `node_executions` and `flows_nodes` in sync with the outcome:

- **On error** (`isError: true`): updates the matching `node_executions` row (`isError = true`, `executionLogId`, `output` set to the combined `userMessage`/`message`, `outputType: 'error'`), then resets any stale output already written onto the live `flows_nodes.data` row via `buildFailedNodeOutputReset` (type-specific reset shape) merged with `errorMessage` and `executionStatus: "FAILED"`.
- **On success** (`isError: false`): re-reads the `node_executions` row's `outputData`, resolves it through the claim-check layer if needed, extracts `{ output, outputType }` for the node's type, sums the node's `token_transaction` rows into `nodeUsedTokens`, and updates `node_executions` (`output`, `outputType`, `metadata.nodeUsedTokens`, `outputData.nodeUsedTokens`, `executionLogId`).

If `execId` is not provided, the activity only inserts the log row and returns — none of the `node_executions`/`flows_nodes` updates above happen.

## Example usage in workflow

### Success logging

```typescript
await generateExecutionLogsActivity({
  execId,
  nodeId,
  flowId,
  flowVersionHistoryId,
  userId,
  sessionId,
  message: 'Node executed successfully',
  isError: false,
});
```

### Error logging

```typescript
const errorMessage = error instanceof Error ? error.message : String(error || "Error unknown in workflow");
const stack = error.cause?.stack || error.stack || 'No stack';

await generateExecutionLogsActivity({
  execId,
  nodeId,
  flowId,
  flowVersionHistoryId,
  userId,
  sessionId,
  message: errorMessage,
  userMessage: error instanceof NodeError ? error.userMessage : undefined,
  errorStack: stack,
  isError: true,
});
```

## Log structure

Each log entry contains:

- **Execution context**: `execId`, `nodeId`, `flowId`, `userId`, `sessionId`
- **Result information**: `message`, `userMessage`, `isError`
- **Debugging data**: `errorStack`, `errorCategory`, `errorField`

## Error handling

The activity may throw an error if:

- Database connection fails
- The insert query fails
- Required fields are missing

Errors in logging should not block workflow execution, but they may be caught and handled silently.

## Use cases

Execution logs are used for:

- **Debugging**: Understanding why workflows failed
- **Monitoring**: Tracking workflow success rates
- **Auditing**: Maintaining execution history
- **Analytics**: Analyzing workflow performance
- **Troubleshooting**: Identifying patterns in failures
