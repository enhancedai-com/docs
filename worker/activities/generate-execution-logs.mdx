## Overview

The `generateExecutionLogsActivity` (`src/modules/temporal/activities/activities.service.ts`) creates log entries in the database to track workflow executions. These logs are used for debugging, auditing, and monitoring workflow performance.

## Purpose

- Track workflow execution history
- Record success and failure information
- Store error stack traces for debugging
- Maintain execution metadata for analysis
- Enable workflow auditing and compliance

## When it's executed

`processSingleNode` calls it at three points:

1. **After successful execution**: logs the message built by `buildSuccessMessage` (`src/modules/temporal/workflows/build-success-message.ts`)
2. **On error**: logs the error detail from `extractNodeError`, including the stack, category and field
3. **On cancellation**: logs the cancelled-node message with `isError: false`

## Signature

```typescript
async generateExecutionLogsActivity({
  execId: string,
  nodeId: string,
  flowId: string,
  flowVersionHistoryId: string | null,
  userId: string,
  sessionId: string,
  message: string,
  userMessage?: string | null,
  errorStack?: string | null,
  errorCategory?: string | null,
  errorField?: string | null,
  isError: boolean,
  runToken?: string,
}): Promise<void>
```

## Inputs

| Parameter | Type | Description |
|-----------|------|-------------|
| `execId` | `string` | Execution id this log belongs to; also drives the broader post-insert behavior below |
| `nodeId` | `string` | ID of the node being logged |
| `flowId` | `string` | ID of the flow containing the node |
| `flowVersionHistoryId` | `string \| null` | Version history id for the flow, used when resetting stale node output on error |
| `userId` | `string` | ID of the user executing the workflow |
| `sessionId` | `string` | Session identifier for tracking execution context |
| `message` | `string` | Dev-facing log message describing the execution result |
| `userMessage` | `string \| null` (optional) | User-facing message; combined with `message` in the node's `errorMessage` when both are set and differ |
| `errorStack` | `string \| null` (optional) | Error stack trace (omitted for successful executions) |
| `errorCategory` | `string \| null` (optional) | Error category of the thrown `NodeError`: `user_config`, `integration`, `provider`, `timeout`, `system`, `schema_validation` or `node_not_found` |
| `errorField` | `string \| null` (optional) | The node data field the error is attributed to, when known |
| `isError` | `boolean` | Flag indicating whether this is an error log |
| `runToken` | `string` (optional) | Token the back minted when it opened the node's row; typed on the props but not read by this activity |

There is no `metadata` parameter — the activity does not accept one. The `execution_logs.metadata` column is always written as a literal `null` by this INSERT.

## Outputs

Returns `void`. The activity completes when the log entry is successfully created (and, when `execId` is present, after the additional updates described below).

## Implementation details

The activity inserts one row into `execution_logs` — `nodeId`, `flowId`, `userId`, `sessionId`, `message`, `userMessage`, `errorStack`, `errorCategory`, `errorField`, `metadata` (always `null`), `isError`, `execId`. For an error log with an `execId`, the insert is deduplicated: no new row is written if a non-deleted error log already exists for that exact `(flowId, nodeId, execId)` triple. The updates below still run; `executionLogId` then keeps its existing value (`COALESCE`).

This activity does **more** than insert a log row — when `execId` is present, it also keeps `node_executions` and `flows_nodes` in sync with the outcome:

- **On error** (`isError: true`): updates the matching `node_executions` row (`isError = true`, `executionLogId`, `output` set to the combined `userMessage`/`message`, `outputType: 'error'`), then resets any stale output already written onto the live `flows_nodes.data` row via `buildFailedNodeOutputReset` (type-specific reset shape) merged with `errorMessage` (the same combined message). It does not write `executionStatus`.
- **On success** (`isError: false`): re-reads the `node_executions` row's `outputData`, resolves it through the claim-check layer if needed, extracts `{ output, outputType }` for the node's type, sums the node's `token_transaction` rows (by `execId` and `nodeId`) into `nodeUsedTokens` (or removes `nodeUsedTokens` when there are none), and updates `node_executions` (`output`, `outputType`, `metadata.nodeUsedTokens`, `outputData.nodeUsedTokens`, `executionLogId`).

If `execId` is not provided, the activity only inserts the log row and returns — none of the `node_executions`/`flows_nodes` updates above happen.

## Example usage in workflow

### Success logging

```typescript
await generateExecutionLogsActivity({
  execId,
  nodeId,
  flowId,
  flowVersionHistoryId,
  runToken,
  userId,
  sessionId,
  message,
  errorStack: null,
  isError: false,
});
```

### Error logging

```typescript
const detail = extractNodeError(error);
const stack = error?.cause?.stack ?? error?.stack ?? 'No stack';

await generateExecutionLogsActivity({
  execId,
  nodeId,
  flowId,
  flowVersionHistoryId,
  runToken,
  userId,
  sessionId,
  message: detail.devMessage,
  userMessage: detail.userMessage,
  errorStack: stack,
  errorCategory: detail.category,
  errorField: detail.field,
  isError: true,
});
```

## Log structure

Each log entry contains:

- **Execution context**: `execId`, `nodeId`, `flowId`, `userId`, `sessionId`
- **Result information**: `message`, `userMessage`, `isError`
- **Debugging data**: `errorStack`, `errorCategory`, `errorField`

## Error handling

The activity throws when a query fails (database connection, insert or update). The workflow does not catch it: the activity runs with `maximumAttempts: 1` and a 60-second `startToCloseTimeout` (`SINGLE_ATTEMPT_GROUP_TIMEOUT_MS`), so a logging failure fails the `processSingleNode` workflow.

## Use cases

Execution logs are used for:

- **Debugging**: Understanding why workflows failed
- **Monitoring**: Tracking workflow success rates
- **Auditing**: Maintaining execution history
- **Analytics**: Analyzing workflow performance
- **Troubleshooting**: Identifying patterns in failures
