## Overview

<Warning>
`getInfoInDatabaseActivity` is currently **dead code**. It's implemented and registered with the Temporal worker (`worker.service.ts`), but no workflow (`process-single-node.workflow.ts`, `process-agent.workflow.ts`, or any other) ever calls it. The activity that actually fetches node info in its place is [`getNodeInfoActivity`](#the-activity-actually-used-getnodeinfoactivity), described below.
</Warning>

`getInfoInDatabaseActivity` executes an arbitrary, caller-supplied SQL query against the worker's database pool and returns the first row. It's a generic query-runner, not specific to nodes — there's nothing in its implementation that reads node data, only what a caller's `query`/`params` ask for.

## Purpose

- Run an arbitrary parameterized SQL query against the worker's database
- Return the first row, or throw if none are found

## When it's executed

Never, currently — see the warning above. If it were called, nothing constrains it to node-related queries; the example queries below are just what a caller could pass.

## Signature

```typescript
async getInfoInDatabaseActivity({
  query: string,
  params: any[]
}): Promise<any>
```

## Inputs

| Parameter | Type | Description |
|-----------|------|-------------|
| `query` | `string` | SQL query string to execute |
| `params` | `any[]` | Array of parameters for the SQL query (prevents SQL injection) |

## Outputs

Returns the first row from the query result as an object. If no rows are found, throws an error.

## Implementation details

The activity uses the `DatabaseService` to execute the query. It:

1. Executes the query with the provided parameters
2. Checks if any rows were returned
3. Throws an error if no data is found
4. Returns the first row as an object

## Example usage in workflow

```typescript
// Get node information
const node = await getInfoInDatabaseActivity({
  query: `SELECT type, flow_id, data FROM flows_nodes WHERE node_id = $1`,
  params: [nodeId],
});

// Access node properties
const nodeType = node.type;
const flowId = node.flow_id;
const nodeData = node.data;
```

## Common query patterns

### Get node by ID

```typescript
const node = await getInfoInDatabaseActivity({
  query: `SELECT type, flow_id, data FROM flows_nodes WHERE node_id = $1`,
  params: [nodeId],
});
```

### Get multiple nodes

```typescript
const nodes = await getInfoInDatabaseActivity({
  query: `SELECT node_id, type, data FROM flows_nodes WHERE flow_id = $1`,
  params: [flowId],
});
```

## Error handling

The activity throws an error if:

- No rows are returned from the query
- The database connection fails
- The query syntax is invalid

## Return structure

The returned object structure depends on the query, but typically includes:

- `type`: Node type (e.g., `TEXT_GENERATOR`)
- `flow_id`: ID of the flow containing the node
- `data`: JSON object containing node configuration and settings

## The activity actually used: `getNodeInfoActivity`

[`processSingleNode`](/worker/workflows/process-single-node) calls `getNodeInfoActivity` (`activities.service.ts:206-219`), not `getInfoInDatabaseActivity`. It runs right after `notifyStatusActivity` announces the node as `PENDING`, and before the `switch (node.type)` dispatch that runs the node-specific activity — so the "right after notifying execution has started, before any node-specific processing" framing above is correct, it's just the wrong activity name.

```typescript
async getNodeInfoActivity({
  execId: string,
  nodeId: string,
  flowId: string,
  flowVersionHistoryId: string | null,
  runToken?: string,
}): Promise<{
  type: string;
  flow_id: string;
  data: Record<string, unknown>;
}>
```

It fetches the node row via the shared `fetchNodeRow` helper (the same claim-check-aware lookup other node activities use), then narrows `data` down to a fixed, small set of fields — `NODE_CONFIG_FIELDS = ["label", "aiSystem", "aiModel", "type"]` — rather than returning the node's full `data` blob. This trimmed result is only used by the workflow to decide which activity to dispatch to and to label the run; each node-specific service (e.g. `TextGeneratorService`, `MathFunctionService`) does its own separate `fetchNodeRow` call to read the full node `data` it actually needs.

If no row is found, `fetchNodeRow` throws before the workflow's own `if (!node) throw new Error("Node not found")` check is reached in practice.
