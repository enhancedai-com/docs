## Overview

<Warning>
`getInfoInDatabaseActivity` is currently **dead code**. It's implemented (`src/modules/temporal/activities/activities.service.ts:481-491`), registered with the Temporal worker (`worker.service.ts`) and proxied in `workflows/configs.ts`, but no workflow (`process-single-node.workflow.ts`, `process-agent.workflow.ts`, or any other) ever calls it. The activity that actually fetches node info in its place is [`getNodeInfoActivity`](#the-activity-actually-used-getnodeinfoactivity), described below.
</Warning>

`getInfoInDatabaseActivity` executes an arbitrary, caller-supplied SQL query against the worker's database pool and returns the first row. It's a generic query-runner, not specific to nodes — there's nothing in its implementation that reads node data, only what a caller's `query`/`params` ask for.

## Purpose

- Run an arbitrary parameterized SQL query against the worker's database
- Return the first row, or throw if none are found

## When it's executed

Never, currently — see the warning above. If it were called, nothing constrains it to node-related queries; the example queries below are just what a caller could pass.

## Signature

```typescript
async getInfoInDatabaseActivity({
  query: string,
  params: any[]
}): Promise<any>
```

## Inputs

| Parameter | Type | Description |
|-----------|------|-------------|
| `query` | `string` | SQL query string to execute |
| `params` | `any[]` | Array of parameters for the SQL query (prevents SQL injection) |

## Outputs

Returns the first row from the query result as an object. If no rows are found, throws an error.

## Implementation details

The activity uses the `DatabaseService` to execute the query. It:

1. Executes the query with the provided parameters
2. Checks if any rows were returned
3. Throws an error if no data is found
4. Returns the first row as an object

## Example usage in workflow

```typescript
// Get node information
const node = await getInfoInDatabaseActivity({
  query: `SELECT type, flow_id, data FROM flows_nodes WHERE node_id = $1`,
  params: [nodeId],
});

// Access node properties
const nodeType = node.type;
const flowId = node.flow_id;
const nodeData = node.data;
```

## Common query patterns

### Get node by ID

```typescript
const node = await getInfoInDatabaseActivity({
  query: `SELECT type, flow_id, data FROM flows_nodes WHERE node_id = $1`,
  params: [nodeId],
});
```

### Queries that match several rows

The activity returns only `rows[0]`. A query such as `SELECT node_id, type, data FROM flows_nodes WHERE flow_id = $1` returns the first matching node, not a list.

## Error handling

The activity throws an error if:

- No rows are returned from the query
- The database connection fails
- The query syntax is invalid

## Return structure

The returned object structure depends on the query, but typically includes:

- `type`: Node type string (for example `commandTextNode`, the value of `NodeType.TEXT_GENERATOR`)
- `flow_id`: ID of the flow containing the node
- `data`: JSON object containing node configuration and settings

## The activity actually used: `getNodeInfoActivity`

[`processSingleNode`](/worker/workflows/process-single-node) calls `getNodeInfoActivity` (`activities.service.ts:438-452`), not `getInfoInDatabaseActivity`. It runs after `notifyStatusActivity` announces the node as `PENDING` and after `resolveNodeInputActivity` (when the back sent an input resolution), and before the node credit gate and the `switch (node.type)` dispatch that runs the node-specific activity.

```typescript
async getNodeInfoActivity({
  execId: string,
  nodeId: string,
  flowId: string,
  flowVersionHistoryId: string | null,
  runToken?: string,
}): Promise<{
  type: string;
  flow_id: string;
  data: Record<string, unknown>;
}>
```

It fetches the node row via the shared `fetchNodeRow` helper (`src/modules/nodes/shared/fetch-node-row.ts`, the same claim-check-aware lookup other node activities use). With an `execId` it reads the run's snapshot, the `input` column of the latest `node_executions` row for that node; without one it reads the live `flows_nodes` row. It then narrows `data` down to a fixed, small set of fields — `NODE_CONFIG_FIELDS = ["label", "aiSystem", "aiModel", "type"]` — rather than returning the node's full `data` blob. The workflow uses this trimmed result to pick the activity to dispatch to, to pass `aiModel`/`aiSystem` to the credit gate, model-access check and token charge, and to label the run; each node-specific service (e.g. `TextGeneratorService`, `MathFunctionService`) does its own separate `fetchNodeRow` call to read the full node `data` it actually needs.

If no row is found, `fetchNodeRow` throws a `NodeNotFoundError` (user message "This node no longer exists. Refresh the page."), so the workflow's own `if (!node) throw new Error("Node not found")` check is not reached in practice.
