## Overview

<Warning>
`nodeExecutionErrorActivity` is currently a **complete no-op**: `async nodeExecutionErrorActivity(_props) { return; }` (`activities.service.ts:387-391`). It is still called from the workflow's error path, with a real props shape, but it does nothing when it runs — no query, no update. This page documents the prop shape it's still typed to receive and the call site that still invokes it, for whenever it gets a real implementation.
</Warning>

## Purpose (as typed, not as implemented)

The activity's real props (`NodeExecutionErrorActivityProps`) suggest it was meant to persist a failed node's error status, but as shipped it has no effect — the node-state update that actually happens on failure is done by [`generateExecutionLogsActivity`](/worker/activities/generate-execution-logs)'s `isError` branch, which runs immediately before this activity in the workflow's error path (it updates both `node_executions` and `flows_nodes.data`).

## When it's executed

This activity is called during error handling, in `process-single-node.workflow.ts`'s catch block:

1. **On workflow failure**: When an error occurs during node execution
2. **After error logging**: Called after `generateExecutionLogsActivity` (which does the real persistence)
3. **Before status notification**: Executes before `notifyStatusActivity` notifies of the failure

## Signature

```typescript
async nodeExecutionErrorActivity({
  nodeId: string,
  flowId: string,
  flowVersionHistoryId: string | null,
  executionStatus: "FAILED",
  errorMessage: string,
  userMessage: string,
}): Promise<void>
```

There is no `nodeData` field — that was never part of the real prop shape.

## Inputs

| Parameter | Type | Description |
|-----------|------|-------------|
| `nodeId` | `string` | ID of the node that encountered an error |
| `flowId` | `string` | ID of the flow containing the node |
| `flowVersionHistoryId` | `string \| null` | Version history id for the flow |
| `executionStatus` | `"FAILED"` | Execution status literal — no other value is valid on this type |
| `errorMessage` | `string` | Dev-facing error message (the caller passes the same `detail.devMessage` also sent to `generateExecutionLogsActivity`) |
| `userMessage` | `string` | User-facing error message |

## Outputs

Returns `void` immediately — the function body is `return;`. No database call is made.

## Implementation details

```typescript
async nodeExecutionErrorActivity(_props: NodeExecutionErrorActivityProps): Promise<void> {
  return;
}
```

## Example usage in workflow

```typescript
// In process-single-node.workflow.ts's catch block, after generateExecutionLogsActivity
await nodeExecutionErrorActivity({
  nodeId,
  flowId,
  flowVersionHistoryId,
  executionStatus: "FAILED",
  errorMessage: detail.devMessage,
  userMessage: detail.userMessage,
});
```

## Integration with error flow

This activity is part of the error handling sequence:

<Steps>
  <Step title="Log error and update node state">
    [`generateExecutionLogsActivity`](/worker/activities/generate-execution-logs) creates the error log entry **and** updates `node_executions`/`flows_nodes.data` with the failure — this is where the real node-state update actually happens today.
  </Step>
  <Step title="No-op">
    `nodeExecutionErrorActivity` runs but does nothing.
  </Step>
  <Step title="Notify user">
    [`notifyStatusActivity`](/worker/activities/notify-status) sends failure notification
  </Step>
</Steps>
