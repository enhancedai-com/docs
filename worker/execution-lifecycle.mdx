This page names every stop in the run lifecycle and points to where each stop lives in code. The ordered diagrams for the two run modes (full flow and single-node) live on the published pipeline page, and this page is the verbal index into them. It does not restate the pipeline — it tells you which file and symbol to open when a particular stop misbehaves.

## Two dispatch routes

`FluxService.apiV2` (`back/src/app-api/flux/flux.service.ts`) picks one of two routes per run, and logs the choice as `[B4] engine decision`:

- **Workflow route.** When the `engine_in_workflow` feature flag is on (`ENGINE_IN_WORKFLOW_FLAG` in `back/src/app-api/flux/engine-selector.ts`) and every node type is eligible, `runApiV2ViaWorkflow` persists a run seed and starts one `processFlow` workflow with id `run-<runId>`. `processFlow` schedules the nodes and starts one `processSingleNode` child per node.
- **Legacy loop.** Otherwise the back walks the nodes itself. For each worker node type, `processNodeViaTemporal` creates the `node_executions` row and `executeNodeViaTemporal` starts `processSingleNode` and waits for its result.

Both routes run each node in a `processSingleNode` workflow with id `node-process-<nodeId>-<execId>` (`buildNodeWorkflowId` in `back/src/temporal/workflow-ids.ts`). The single-node **Run** button takes the second route for one node.

## The eight stops

A run flows through eight observable stops:

1. **Entry endpoint**: the back receives the run request.
2. **`node_executions` row**: a row is created for the node, keyed by `(execId, nodeId)`.
3. **Temporal dispatch**: the back (or `processFlow`) starts `processSingleNode`.
4. **`fetchNodeRow`**: the node activity reads the row's `input`.
5. **Execute**: the node module runs.
6. **`persistNodeSuccess`**: the node activity writes the output to the row.
7. **Redis event**: `notifyStatusActivity` publishes the node status.
8. **Socket emit**: the back relays the status to the front.

## Where each stop lives

| # | Stop | File | Symbol |
|---|---|---|---|
| 1 | Entry endpoint | `back/src/app-api/flux/flux.service.ts` | `apiV2` |
| 2 | `node_executions` row created | `back/src/app-api/flux/flux.service.ts` (entity: `back/src/entities/node_execution.entity.ts`) | `createNodeExecution`; on the workflow route, reached through `openNodeExecutionActivity` → `POST /worker/open-node-execution` → `openWorkerNodeExecution` |
| 3 | Temporal dispatch | `back/src/app-api/flux/flux.service.ts`; `worker/src/modules/temporal/workflows/process-flow.workflow.ts` | `runApiV2ViaWorkflow` / `executeNodeViaTemporal`; `executeChild(processSingleNode)` |

## What you observe at each stop

`fetchNodeRow` and `persistNodeSuccess` are helpers called inside the node activity, not activities of their own, so the Temporal UI shows them as part of the node activity (for example `scriptingActivity`).

| # | Stop | `node_executions` row state | Temporal UI event | Worker log |
|---|---|---|---|---|
| 1 | Entry endpoint | row not yet created | — | — |
| 2 | Row created | `input` populated by the API, `outputData` empty, `isError: false` | on the workflow route, `openNodeExecutionActivity` in `run-<runId>` | — |
| 3 | Temporal dispatch | unchanged | `WorkflowExecutionStarted` on `node-process-<nodeId>-<execId>` | — |
| 4 | `fetchNodeRow` | unchanged (worker reads `input` of the latest row for `(execId, nodeId)`) | `ActivityTaskStarted` on the node activity | — |
| 5 | Execute | unchanged (worker in-memory) | node activity running | node-specific log lines |
| 6 | `persistNodeSuccess` | `outputData` replaced, `updatedAt` bumped; the live `flows_nodes.data` is merged too | `ActivityTaskCompleted` on the node activity | — |
| 7 | Redis event | unchanged | `notifyStatusActivity` with `COMPLETED` | — |
| 8 | Socket emit | unchanged | — | — |

<Note>
The `node_executions` entity does **not** have a `status` column. State is observed via the combination of `input` presence (set by the API at row creation), `outputData` presence (set by `persistNodeSuccess`), `isError`, and `cancelledAt` (set when a run is cancelled). See [Running and debugging locally](/worker/running-locally) for the SQL and the full set of columns.
</Note>
