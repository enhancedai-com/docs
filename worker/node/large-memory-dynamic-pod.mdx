title: "Large Memory: dynamic pod id"
description: "How the Large Memory node accepts a memory pod id at runtime via the podIdData input — the natural pairing for pods created through the Public API."
---

The Large Memory node (technical name Command Content Node, node type `commandContentNode`) reads from a FluxPrompt memory pod during flow execution. Until commit `663f20e5`, the node was hard-tied to a single pod selected manually in the UI (`node.data.nameSpace`). External applications that already know which pod belongs to the current case, project, or client now have a runtime alternative: pass the pod id into the flow as a variable, and the node picks it up.

This page documents that integration point.

## The problem this solves

If you're running flows on behalf of multiple customers — one pod per customer, one pod per case, one pod per project — you don't want to maintain N copies of the same flow with different pods baked in. The pod id is data, not configuration.

External apps that integrate with FluxPrompt typically:

1. Create a pod via [`POST /flux/memory-pods`](/main-api/specific-features/memory-pods-api/create-pod) when their event fires.
2. Persist the returned pod id on their side, keyed by their internal record.
3. Trigger a flow and pass the pod id as a `variableInputs` entry.

The flow's Large Memory node now reads that variable and queries the right pod for that run only.

## The `podIdData` input

The node has a `podIdData` input slot with the **same shape as `queryData`** (both are `EdgeDataItem[]`, `{ id, text, label }`) — connect any upstream output that produces a UUID-shaped value.

### Resolution rules

The worker's `LargeMemoryService.resolvePod` (private method, `large-memory.service.ts:74-105`) computes the final pod at execution time:

<Steps>
  <Step title="Collect connected items">
    `resolveEdgeData(data.podIdData, undefined)` dedupes the connected `podIdData` items by `id`, filters out empty `text` values, and joins the rest with no separator, in order. There is no `{{var}}` placeholder substitution anywhere in this path — it's a plain edge-array text join, the same helper other worker nodes use for edge-driven fields.
  </Step>
  <Step title="Dynamic id present">
    If the joined value is a non-empty string, the worker queries the `namespace` table directly by SQL: `SELECT id, "podName" FROM namespace WHERE id = $1 AND "deletedAt" IS NULL LIMIT 1`. A match is used as the pod for this execution only. **No match** throws — see [Error case](#error-case) — the node does **not** fall back to the manually selected pod once a dynamic id was supplied but not found.
  </Step>
  <Step title="No dynamic id">
    If `podIdData` has no upstream connection (or every connected item is empty), the joined value is `""` and the node falls back to the manually selected pod (`data.nameSpace`, `{ id, name }`). If that's also unset, it throws a `UserConfigError` ("Configure a Large Memory pod before running this node.").
  </Step>
</Steps>

## End-to-end recipe

The typical integration looks like this:

<Steps>
  <Step title="Provision the pod">
    Your application creates a memory pod when its event fires:

    ```bash
    curl -X POST "https://app.fluxprompt.ai/flux/memory-pods" \
      -H "api-key: <your-api-key>" \
      -H "content-type: application/json" \
      -d '{
        "name": "Case 12345 — Patient X",
        "metadata": { "caseId": "12345" }
      }'
    ```

    Persist `data.pods.id` against your internal record.
  </Step>
  <Step title="Ingest documents">
    As documents arrive, ingest them:

    ```bash
    curl -X POST "https://app.fluxprompt.ai/flux/memory-pods/<podId>/add-document" \
      -H "api-key: <your-api-key>" \
      -F "files=@lab-results.pdf"
    ```

    Poll [`GET /memory-pods/get`](/main-api/specific-features/memory-pods-api/list-pods) until files reach `"Finished"`.
  </Step>
  <Step title="Build the flow once">
    In the FluxPrompt UI, create a flow with a Large Memory node. Leave the static pod selection empty or pick any default. Wire the `podIdData` input to a Variable Input node (or any upstream node whose output is a UUID).
  </Step>
  <Step title="Trigger the flow with the pod id">
    When your app needs to query the case's knowledge, call the flow with the pod id in `variableInputs`:

    ```bash
    curl -X POST "https://app.fluxprompt.ai/flux/api-v2?flowId=<flowId>" \
      -H "api-key: <your-api-key>" \
      -H "content-type: application/json" \
      -d '{
        "variableInputs": [
          { "inputId": "varInputNode_...", "inputText": "<podId>" }
        ]
      }'
    ```

    The Large Memory node reads `<podId>`, verifies it exists, and queries that pod for this execution only.
  </Step>
</Steps>

## Error case

If the resolved pod id does not exist (or has been soft-deleted), `resolvePod` throws a `UserConfigError` (field `podIdData`):

```
userMessage: "Large Memory pod not found (id: <podId>)."
```

The id is included in the message so the upstream variable can be traced quickly.

## What stays the same

- The UI experience for picking a pod manually is unchanged. Flows without `podIdData` connections behave exactly as before.
- The `queryData` input (the search query) is independent — connect it however you do today.
- The node's underlying retrieval logic (chunking, similarity search, top-k) is unchanged.
