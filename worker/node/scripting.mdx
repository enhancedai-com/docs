## Overview

The **scripting** node (technical name Scripting Node, node type `scripting`) runs code the user provides in **JavaScript** or **Python**. The Worker resolves the node from the database, invokes the matching Lambda executor, persists `result` and `console` on the node row, and returns the same payload to the workflow.

The Temporal activity [`scriptingActivity`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/temporal/activities/activities.service.ts) delegates to [`ScriptingService.process`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/nodes/scripting/scripting.service.ts).

## When it runs

`scriptingActivity` is invoked from the [`processSingleNode`](/worker/workflows/process-single-node) workflow when the node type is **scripting** (`NodeType.SCRIPTING`).

## Activity signature

```typescript
async scriptingActivity({
  nodeId: string,
  sessionId: string,
  userId: string,
}): Promise<ScriptingResponse>
```

`ScriptingResponse`:

```typescript
{
  result?: unknown;   // script “output”
  console?: unknown[]; // collected logs
}
```

## End-to-end flow

1. Load `flows_nodes` by `nodeId` and read `data` (language, script source, variables).
2. Choose the Lambda function from `data.language` (`code-executor-python` or `code-executor-js`).
3. Build the script string: prefer merged `scriptData[]` rows (`text` joined by newlines); if empty, use `data.script`.
4. Invoke Lambda with `{ script, variables }`.
5. On success, merge `result` and `console` into `data` and `UPDATE flows_nodes`.
6. Return `{ result, console }` to the workflow.

Lambda errors (missing function, runtime errors, timeouts) surface as thrown errors in the Worker.

## Outputs

| Concept | Meaning |
| -------- | -------- |
| **Output** | Stored in `result`. How it is set depends on the runtime (see [Executors](#executors)). |
| **Console** | Stored in `console`: every line produced by the sandbox `console` API (`log`, `warn`, `error`), including `[ERROR]` / `[WARN]` prefixes where applicable. |

## Node `data` fields (Worker expectations)

| Field | Role |
| ----- | ----- |
| `language` | `JavaScript` or `Python` (see `Language` enum in the Worker). Selects which Lambda to call. |
| `script` | Fallback script string when `scriptData` is empty or has no usable text. |
| `scriptData` | Optional array of rows; each row’s `text` is concatenated with newlines and used as the script when non-empty. |
| `variables` | Array of `{ name, value }` entries for substitution and (Python) injection (see [Variables](#variables)). |

After execution, `data` is updated with `result` and `console` from Lambda.

## Variables

Both executors:

1. Build a map of variable `name` → string `value`.
2. Replace every occurrence of `{{name}}` in the script with that string (regex / global replace).

**Python** also injects assignments at the top of the wrapped file so each name is available as a Python variable (values JSON-serialized for literals).

**JavaScript** also spreads `variablesMap` onto the VM sandbox so names are available as identifiers in addition to `{{name}}` placeholders.

## Executors

Execution happens in AWS Lambda, not inside the Worker process.

### Python (`code-executor-python`)

- **Package type:** Container image (ECR: `<aws-account-id>.dkr.ecr.us-east-1.amazonaws.com/code-executor`).
- **Base image:** `public.ecr.aws/lambda/python:3.12`.
- **Pre-installed libraries:** `numpy` 2.2.6, `pandas` 2.2.3, `scipy` 1.15.3, `pendulum` 3.1.0, `matplotlib` 3.10.3, `pypdf` 6.8.0. Available to user scripts without runtime installation.
- **Configuration:** 512 MB memory, 30 s timeout.
- **API:** `console.log`, `console.error`, `console.warn`; **`setResult(value)`** sets the structured output `result`.
- **Output:** The wrapper prints a JSON line with `{ result, console }`. If the process exits non-zero, the Lambda returns an `error` string (stderr).
- Placeholders `{{varName}}` are applied after the variable map is built.
- **Source:** `infra/lambda-executor/` (Dockerfile + `lambda_handler.py`).
- **CI/CD:** three `workflow_dispatch`-only workflows, no push/path trigger — `deploy-lambda-executor.yml` (legacy, single-environment), `deploy-lambda-executor-prod.yml`, and `deploy-lambda-executor-nonprod.yml`. Each builds the Docker image from `infra/lambda-executor/`, pushes it to ECR, updates `code-executor-python`'s code, and — the prod/nonprod workflows only — publishes a new Lambda version and repoints the `prod`/`non-prod` alias at it (the `LAMBDA_PYTHON_ALIAS` the worker invokes as its `Qualifier` — see [Lambda function names](#lambda-function-names)).

### JavaScript (`code-executor-js`)

- **Package type:** Zip (Node.js runtime).
- **Timeout:** 30 seconds (`vm.runInContext`).
- **API:** `console.log`, `console.error`, `console.warn`; **`setResult(value)`** sets `result`.
- **Output:** `result` is `scriptResult` if `setResult` was used; otherwise the **last expression** value from `vm.runInContext` when it is not `undefined`; otherwise `null`.
- On uncaught errors, the handler returns `error` (timeout message or `err.message`) and may still return partial `console` logs.

## Lambda function names

The Worker resolves the Lambda function name directly from the language, but for Python it also sets an explicit `Qualifier` from an environment variable:

| Language | Lambda function | Package type | `Qualifier` |
| -------- | --------------- | ------------ | ----------- |
| `Python` | `code-executor-python` | Container image (ECR) | `process.env.LAMBDA_PYTHON_ALIAS` — required, no default; selects the `prod`/`non-prod` alias so dev/staging/prod hit isolated aliases of the same function. See [Environment Variables](/worker/environment-variables). |
| `JavaScript` | `code-executor-js` | Zip (Node.js) | none — always invokes `$LATEST` |

If `language` does not match either value, `ScriptingService` throws a `UserConfigError` ("Unsupported language: …").

The `LambdaClient`'s `region` is hardcoded to `"us-east-1"` in `scripting.module.ts` — the `AWS_REGION` env var is not read.

## Timeouts and output budgets

- The worker aborts the Lambda `InvokeCommand` itself after `LAMBDA_TIMEOUT_MS = 110_000` (110 seconds), independent of whatever timeout the Lambda function is configured with.
- The activity's returned `{ result, console }` is capped at `MAX_ACTIVITY_RESULT_BYTES = 1_000_000` (1 MB, serialized). Above that, `result` is truncated to a `100_000`-byte preview (`ACTIVITY_RESULT_PREVIEW_BYTES`) with a truncation marker, and `console` entries are kept up to a `400_000`-byte budget (`ACTIVITY_CONSOLE_BUDGET_BYTES`) before the rest are replaced with an "omitted" notice. The full, untruncated values are still persisted onto the node row — only the value returned to the workflow/heartbeat is bounded.
- `consoleAsResult` (node data field, default `true`): when the Lambda's own `result` is empty (`undefined`/`null`/`""`), the service promotes the last JSON-shaped `console` entry (or, failing that, the last string entry) into `result` instead.
- `assertNotSwapped` is a heuristic safety check: if `result` came back empty but a `console` entry looks like a JSON value, that's treated as a sign the Lambda wrote its real output to the wrong stream, and the run fails with an `IntegrationError` ("Scripting engine routed the result to the wrong output.") rather than silently returning an empty result.

## Local development

When `NODE_ENV === 'local'`, [`ScriptingModule`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/nodes/scripting/scripting.module.ts) configures the AWS SDK `LambdaClient` with explicit credentials from the environment:

- `AWS_ACCESS_KEY_ID`
- `AWS_SECRET_ACCESS_KEY`

Set these (and region) so local Worker runs can invoke the same Lambdas your AWS account deploys.
