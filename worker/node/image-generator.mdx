## Overview

The **image generator** node produces an image from a prompt assembled out of several node fields, then uploads the result and charges the user for one (or more) generated images. The node supports six provider systems, selected by `nodeData.aiSystem` (default `openai`):

- **`openai`**, **`gemini`**, **`fal`**, **`meta`** (Muse, executed via the `fal` client) — call [`generateImage()`](https://ai-sdk.dev/docs/ai-sdk-core/image-generation) from the [AI SDK](https://ai-sdk.dev/) against a model returned by `aiProviders.<provider>.image(...)`.
- **`stabilityai`**, **`ideogram`** — make direct HTTP calls, bypassing the AI SDK entirely.

<Note>
  A seventh legacy system, **`opensources`** (Kandinsky via Replicate), was removed 2026-09-03 — it was confirmed broken in both dev and prod (Replicate returned HTTP 401) with no viable replacement. `aiSystem: "opensources"` now falls through to the generic "aiSystem not supported" `UserConfigError`.
</Note>

[`imageGeneratorActivity`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/temporal/activities/activities.service.ts) delegates to [`ImageGeneratorService.process`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/nodes/image-generator/image-generator.service.ts), which builds the prompt and hands every provider call to [`ImageProviderService`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/ai-provider/image/image-provider.service.ts) (see [The shared image provider layer](#the-shared-image-provider-layer)). That service dispatches through two lookup tables keyed by `aiSystem`: `PROVIDER_BUILDERS` (the AI SDK path) and `DIRECT_HTTP_BUILDERS` (the direct-HTTP path). If `aiSystem` matches neither, the activity throws a `UserConfigError`.

<Note>
  This node was ported from the back's `imageGeneratorNode` handler. See [Provenance](#provenance) for the full source-to-worker file mapping and the behavior differences introduced during the port.
</Note>

## When it runs

`imageGeneratorActivity` is invoked from the [`processSingleNode`](/worker/workflows/process-single-node) workflow when the node type is **image generator** (`NodeType.IMAGE_GENERATOR`, stored value `imageGenerator`).

## Activity signature

```typescript
async imageGeneratorActivity({
  execId: string,
  nodeId: string,
  sessionId: string,
  userId: string,
  flowId: string,
  flowVersionHistoryId: string | null,
}): Promise<ImageGeneratorResponse>
```

`ImageGeneratorResponse`:

```typescript
{
  text: string; // the stored image URL
}
```

## The shared image provider layer

`ImageGeneratorService` carries **no provider call of its own** — everything provider-specific (the `ai`
package's `generateImage()` call, every fal/Stability/Ideogram HTTP request, error classification) lives in
`worker/src/modules/ai-provider/image/`, behind `ImageProviderService`. This split was deliberate: the node
layer is what a future image node reuses instead of copying provider logic. See the
[A5 task spec](https://github.com/enhancedai-com/Workflow/blob/main/.specs/features/worker-flow-execution-epic/TASK-A5-IMAGE-FAMILY.md)
for the extraction's history.

`ImageProviderService` exposes two methods:

| Method | Role |
| ------ | ---- |
| `supports(aiSystem)` | `true` if `aiSystem` has a registered builder (either map below) |
| `generate(request)` | Dispatches to the matching builder and returns a normalized `ImageProviderResult` |

Two dispatch tables select the builder:

| Map | `aiSystem` keys | How it calls the provider |
| --- | ---------------- | -------------------------- |
| `PROVIDER_BUILDERS` | `openai`, `gemini`, `fal`, `meta` | Builds an `ImageGenerateSpec` (model + call args), then `ImageProviderService.generate()` calls the **AI SDK**'s `generateImage()` once, uniformly, for all four |
| `DIRECT_HTTP_BUILDERS` | `stabilityai`, `ideogram` | Each builder makes its own raw HTTP calls and **charges itself** via an injected `ctx.charge` closure, because charge-before-vs-after-the-call timing differs per provider and can't be normalized into one shared post-call charge |

An unsupported or missing `aiSystem` — including `opensources` (Kandinsky via Replicate, removed 2026-09-03
after being confirmed broken with no viable replacement) — fails `supports()`, and `ImageGeneratorService`
throws a `UserConfigError`: *"This image provider is not yet available in the worker."*

## End-to-end flow

1. **Load node** — read the node row (`execId`-scoped `node_executions.input` during a run, `flows_nodes.data` otherwise); read `data`.
2. **Resolve the provider** — look up `nodeData.aiSystem` (default `"openai"`) in `PROVIDER_BUILDERS` and `DIRECT_HTTP_BUILDERS`. Neither match throws `UserConfigError`.
3. **Build the prompt** — assemble `prompt`/`subject`/`environment`/`tone`/`view`/`style`/`negativePrompt` (see [Building the prompt](#building-the-prompt)). An empty result throws `UserConfigError`.
4. **Heartbeat `"generating"`** — `Context.current().heartbeat({ nodeId, phase: "generating" })`.
5. **Generate** — `ImageProviderService.generate()`: either `generateImage()` from the `ai` package (AI SDK path) or the provider's own HTTP call chain (direct-HTTP path), with the activity's cancellation signal passed through (see [Cancellation](#cancellation)).
6. **Heartbeat `"uploading"`** — `Context.current().heartbeat({ nodeId, phase: "uploading" })`.
7. **Upload** — `POST /worker/store-image` with the generated bytes or source URL (see [Storing the image](#storing-the-image)).
8. **Charge** — `POST /worker/charge-tokens` (see [Billing](#billing)). On the direct-HTTP path, the provider module charges itself, at its own point in the call chain, instead of `process()` charging once afterward.
9. **Persist** — write `text`, `previewIndex`, and `previewResponses` back onto the node's `data` (see [Persisted node `data`](#persisted-node-data)), with `executionStatus: "COMPLETED"`.
10. **Return** — `{ text: src }`.

## Node `data` fields

### Shared prompt fields

Read by [`buildPrompt`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/nodes/image-generator/build-prompt.ts), independent of provider:

| Field | Role |
| ----- | ---- |
| `prompt` | Main prompt text. |
| `subject` | Subject line, appended as `Subject: …`. |
| `environment` | Appended as `Environment: …`. |
| `tone` | Appended as `Tone: …`. |
| `view` | Appended as `View: …`. |
| `style` | Appended as `Style: …`, but only when `style_present === "None"`. |
| `negativePrompt` | Read by several direct-HTTP providers as a separate negative-prompt parameter; not merged into the assembled prompt text itself. |

Each of these fields also has an edge-driven counterpart — `promptData`, `subjectData`, etc. When the corresponding `*Data` array is non-empty, its items' `text` values (joined with `" \n"`) override the static field before the prompt is assembled.

### Provider selection

| Field | Role |
| ----- | ---- |
| `aiSystem` | Selects the provider system: `openai` (default), `gemini`, `fal`, `meta`, `stabilityai`, or `ideogram`. |
| `aiModel` | Model id, read by `openai`, `gemini`, and (via [`resolveImageModel`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/ai-provider/image/resolve-image-model.ts)) `stabilityai`/`ideogram` as the primary source of the model — the per-provider legacy field (`engineId`, `ideogramModel`) is a fallback for stored data older than `aiModel`. |
| `spaceId` | Optional; threaded through to the upload call. |

### `openai`

| Field | Role |
| ----- | ---- |
| `size` | Passed straight through to `generateImage()`. |
| `quality` | When set, forwarded as `providerOptions.openai.quality`. |

The actual API call always targets `gpt-image-1` — `aiModel` is not read for the call itself. It is only used, via `persistModel`, to label the stored image (see [Persisted node data](#persisted-node-data)). `type` and `openAiModels` — the fields that would select Image to Image / AI Edit / Expand Image — are not read either; see [Known limitations](#known-limitations).

### `gemini`

| Field | Role |
| ----- | ---- |
| `aiModel` | Model id; falls back to a literal `"gpt-image-1"` default if unset (a ported default, not a real Gemini id — no observed node hits this fallback in practice). |
| `aspectRatio` | Passed to `generateImage()`'s standard `aspectRatio` parameter, which the AI SDK's Google adapter maps onto the real `imageConfig.aspectRatio`. No default is forced when unset. |

### `fal`

| Field | Role |
| ----- | ---- |
| `falModel` | Selects the model family: any `"…pro…"` variant, `"schnell"`, `"dev"`, or a Flux id looked up in the model maps. Defaults to `"pro"`. |
| `imageSize` | Fal's named size preset (e.g. `landscape_4_3`); sent via `providerOptions.fal.image_size` as a raw passthrough, not the SDK's own `size`/`aspectRatio` params. |
| `sync_mode` | Compared against the **literal string** `"false"` — only that exact string resolves to `false`; anything else, including the boolean `false` and `undefined`, resolves to `true`. Preserved as a known back bug rather than normalized. |
| `num_images` | Sent as `n`. Defaults to `1`. |
| `fal_seed` | Sent as `seed`. |
| `guidance_scalefloat` | Sent as `providerOptions.fal.guidanceScale` for pro/dev/Flux families (not `schnell`). Defaults to `3.5`. |
| `safety_tolerance` | Sent as `providerOptions.fal.safetyTolerance` for pro/Flux families only (not `schnell` or `dev`). Defaults to `"2"`. |
| `inference_steps` | Sent as `providerOptions.fal.numInferenceSteps`, capped at `12` for `schnell` and forced to `8` for "fast" Flux variants (`flash`/`turbo` in the id). |

### `stabilityai`

Dispatch is three levels deep: `type` picks the operation family, then `engineId` (Text to image) or `imageToImageSelectedType` (Image to image) picks the specific method.

| Field | Role |
| ----- | ---- |
| `type` | `"Text to Image"` (default), `"Image to image"`, `"Enhance resolution"`, or `"Upscale Image"`. Any other value throws `UserConfigError`. |
| `engineId` | Resolved via `resolveImageModel` (falls back to legacy field, default `"sd3"`). Selects between the SD3 family, `core`, `stability-ultra`, or the legacy text-to-image engine. |
| `imageToImageSelectedType` | For `"Image to image"`: `"sketch"` (default), `"structure"`, or `"style"`. |
| `inputPreview` | Required for `"Image to image"` — missing it throws `UserConfigError`. Also read by `"Enhance resolution"`/`"Upscale Image"`. |
| `output_format`, `aspect_ratio`, `steps`, `cfg_scale`, `height`, `width`, `clip_guidance_preset`, `promptWeight`, `style_present` | Per-method request parameters for the text-to-image family. |
| `influenceStrength`, `outputFormat`, `seed`, `selectedImageToImageAspectRatio` | Per-method request parameters for the image-to-image family (note `outputFormat`, camelCase, is a distinct field from `output_format`). `influenceStrength` is a **0–100 percentage** (the canvas slider shows "Influence Strength: N%"), divided by 100 before use, so `0.5` means 0.5 %; higher keeps more of the source image. |

`"Enhance resolution"` and `"Upscale Image"` both route to the same upscale method — the back's original code only recognized `"Upscale Image"`, which meant every real `"Enhance resolution"` node silently no-op'd. Accepting both is a deliberate fix (see [Provenance](#provenance), D16).

Any `type` outside this table throws `UserConfigError` — including two real production values, `"AI Edit"` and `"AI erase"`; see [Known limitations](#known-limitations).

### `ideogram`

| Field | Role |
| ----- | ---- |
| `type` | `"Image to image"` routes to remix (requires `inputPreview`); anything else routes to generate. `"Expand Image"` is explicitly refused — see below. |
| `ideogramModel` | Model id, e.g. `ideogram-v3`, `ideogram-v3-turbo`, `ideogram-v3-quality`. Also drives the rendering speed sent to the API. |
| `magicPrompt` | Sent as `magic_prompt`. |
| `aspect_ratio_ideogram` | Sent as `aspect_ratio`. Mutually exclusive with `resolution` — if both are set, `resolution` is dropped before the request is sent. |
| `resolution` | Sent as `resolution`, subject to the mutual-exclusion rule above. |
| `style_type`, `negativePrompt` | Additional request parameters. |
| `inputPreview` | Required for remix; the source image is fetched and embedded in the request. |

`type: "Expand Image"` throws `UserConfigError`. The back silently routed this to its upscale method; this port refuses instead, since no real node was found using this combination — see [Provenance](#provenance), D15.

### `meta` (Muse, via fal)

`meta` shares its builder with `fal` (`buildFalSpec` handles both `aiSystem` values — there is no separate `meta` module) but is a distinct catalog identity, matching the `stabilityai`/`ideogram` precedent of a dedicated `aiSystem` id that still executes through an existing client. It is selected whenever `falModel === "muse"` and calls `fal.ai/models/meta/muse-image/{text-to-image,edit}`.

| Field | Role |
| ----- | ---- |
| `type` | `"Image to image"` routes to the `edit` endpoint (requires `inputPreview`, throws `UserConfigError` if missing); anything else routes to `text-to-image`. |
| `imageSize` | Fal's named size preset (the same field/values `fal` uses), converted to Muse's own colon aspect-ratio string (e.g. `landscape_4_3` → `4:3`) via a lookup table — Muse's endpoint takes `aspect_ratio`, not `image_size`. |
| `output_format` | Sent as `outputFormat`. The installed AI SDK's fal options schema only accepts `"jpeg"`/`"png"`; any other value (including Muse's own real default, `"webp"`) falls back to `"png"`. |
| `sync_mode` | Same literal-string-`"false"` comparison as the `fal` provider. |
| `inputPreview` | For image-to-image, sent as `images: [inputPreview]` on a multi-image prompt (`providerOptions.fal.useMultipleImages: true`), which makes the AI SDK serialize it as fal's plural `image_urls` field. |
| `num_images` | Sent as `n`, same as `fal`. Defaults to `1`. |

Muse does not read `guidance_scalefloat`, `safety_tolerance`, or `inference_steps` — its request shape has no equivalents for those fal-family parameters.

## Building the prompt

[`buildPrompt`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/nodes/image-generator/build-prompt.ts) runs in two steps:

1. **Edge overrides** — for each of `prompt`, `subject`, `environment`, `tone`, `view`, `style`, and `negativePrompt`, if the matching `<field>Data` array is non-empty, its items' `text` values are joined with `" \n"` and replace the static field.
2. **Merge** — the resolved fields are concatenated into a single string in a fixed order (`Prompt:`, then `Style:` only when `style_present === "None"`, then `View:`, `Subject:`, `Environment:`, `Tone:`), each on its own line.

An empty result (no text at all) throws `UserConfigError` before any provider call is attempted.

## Storing the image

Uploads go through `storeGeneratedImage` (in [`store-and-charge.ts`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/nodes/image-generator/store-and-charge.ts)), which calls `POST /worker/store-image`:

```typescript
// request
{
  nodeId: string;
  execId: string;
  provider: string;   // e.g. 'openAi', 'gemini', 'fal', 'meta', 'stabilityAi', 'ideogram'
  model: string;
  userId: string;
  flowId?: string;
  spaceId?: string;
  mimeType?: string;
} & (
  | { base64: string; sourceUrl?: never }
  | { sourceUrl: string; base64?: never }
)

// response
{ success: true, src: string }
```

Exactly one of `base64` (raw bytes for providers that return generated bytes directly) or `sourceUrl` (a provider-hosted URL to fetch and re-upload) is sent. A non-2xx response or a response without `success: true` throws `SystemError`.

<Info>
  `/worker/store-image` is a **new** endpoint, separate from `/worker/store-payload` (used to persist other large node outputs). `/worker/store-payload` is a private claim-check: it writes to a private S3 location keyed by `(execId, nodeId)` and hands back an opaque key the worker resolves later. A generated image needs a public, durable URL that gets written into the node's `data` for the front to render — a different lifetime and a different bucket policy than a claim-check. `/worker/store-image` exists because reusing `/worker/store-payload` for this would have been the wrong contract, not a smaller one.
</Info>

## Billing

Charging goes through `chargeImageGeneration` (also in `store-and-charge.ts`), which calls `POST /worker/charge-tokens` — the same endpoint documented in [Charge tokens](/worker/activities/charge-tokens), extended with three optional fields (`label`, `usedTokens`, `billingFlowId`) that existing callers don't send.

By default, this node charges **one `usedTokens` credit per generated image** (`usedTokens: params.usedTokens ?? 1`, `label: "Image"`). Some direct-HTTP providers pass a different value instead of the default — for example, Stability's `textToImage` charges `Math.ceil(steps / 30)` credits when `steps > 30` (otherwise `1`). On the AI SDK path, `process()` charges once, after the call succeeds; on the direct-HTTP path, each provider method calls `ctx.charge(...)` itself, at whatever point in its own call chain matches the back's original charge-before-vs-after-the-call timing for that method:

- **`stabilityai`** — every method charges **before** submitting the fal request. If generation then fails, times out, or is cancelled, the charge already happened and nothing in the worker refunds it.
- **`ideogram`** — charges only **after** a successful fal response.
- **`openai` / `gemini` / `fal` / `meta`** — the image is stored first, then charged once, always after a successful image.

<Warning>
  The back's real `openai` path charges input and output tokens separately, via two `updateTokens` calls. This endpoint's charge-deduplication logic (keyed by `(execId, nodeId)`) makes a second charge call for the same node execution a silent no-op, so that two-call behavior could not be replicated here. This is a known, tracked gap in the port — not a bug introduced by it.
</Warning>

## Persisted node `data`

### On success

| Field | Role |
| ----- | ---- |
| `text` | The stored image URL returned by `/worker/store-image`. |
| `previewIndex` | Index of the new entry within `previewResponses` (equal to the array's previous length). |
| `previewResponses` | Existing entries plus one new entry — see the shape split below. |
| `executionStatus` | `"COMPLETED"`. |
| `errorMessage` / `errorStatusCode` | Cleared to `null`. |

Other `data` fields are preserved via spread (`...nodeData`).

**`previewResponses` entry shape** — this varies by provider, and the three shapes are not interchangeable:

| Providers | Shape |
| --------- | ----- |
| `fal`, `meta`, `stabilityai` | A bare **string** — the image URL itself. |
| `openai`, `gemini` | An **object**: `{ message: string; usedTokens: number; cost: number }` — `message` holds the URL. |
| `ideogram` | An **object**: `{ image: string; usedTokens: number; cost: number }` — note the key is `image`, not `message`. |

### On failure

The activity does not write an error field onto `data` — it **throws** a typed `NodeError` subclass instead (see [Errors](#errors)). This differs from some older, not-yet-migrated node types, which write `errorMessage`/`errorStatusCode` onto `data` without throwing and rely on a separate detection step downstream. The thrown error flows through the standard Temporal failure path shared by every migrated node type, which the front already renders correctly off `executionStatus`/`executionError` from the socket status broadcast.

## Known limitations

Two provider-specific gaps, distinct from the [Provenance](#provenance) deviations above, show up in real production usage.

<Warning>
  **`openai` never reads mode or model selection.** [`buildOpenAiSpec`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/ai-provider/image/openai-provider.ts) reads only `nodeData.size` and `nodeData.quality` — `nodeData.type` and `nodeData.openAiModels` are never referenced anywhere in the file or its call site. An `openai`-system node configured for `"Image to Image"`, `"AI Edit"`, or `"Expand Image"` still runs plain text-to-image generation and is billed for it; any connected source image is ignored. This matches the back's original `imageSystem === 'openai'` dispatch, which has the identical gap — a known limitation carried over from the back, not a worker regression, but one that affects real, currently-recorded usage: 22 rows across `Image to Image`/`Image to image` node configurations.
</Warning>

<Note>
  **`stabilityai` fails loud on two unimplemented modes.** The [dispatch](#stabilityai) only recognizes `"Text to Image"`/unset, `"Image to image"`, and `"Enhance resolution"`/`"Upscale Image"`. Any other `type` — including `"AI Edit"` and `"AI erase"`, both present in production data (26 combined rows) — falls through to `unsupportedStabilityMode`, which throws `UserConfigError` (`userMessage: "This image mode is not yet available in the worker."`). The back's dispatch has no branch for either label, but falls through silently — no error, no image, no charge. A node using one of these modes now surfaces an explicit error instead.
</Note>

## Cancellation

Unlike [`textGeneratorActivity`](/worker/node/text-generator) and `apiCallerActivity`, `imageGeneratorActivity`
is **not** wrapped in `runCancellableNode` — it has no graceful partial-output concept to save. Instead:

- `ImageGeneratorService.process` reads the activity's own `Context.current().cancellationSignal` and passes
  it straight into `ImageProviderService.generate()` as `request.abortSignal`.
- **AI-SDK path** — the signal is forwarded to `generateImage({ ..., abortSignal })`. An abort is detected with
  `isAbortError()` and **rethrown as-is**, bypassing `classifyAiSdkError` entirely (not wrapped into a
  `ProviderError`).
- **Direct-HTTP path** — the signal is threaded into every fal submit/status/result `fetch(url, { signal })`
  call, into `fetchSourceImageBuffer`, and into the poll wait between attempts via
  [`abortableSleep(ms, signal)`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/ai-provider/image/abortable-sleep.ts) — an abort during the wait rejects immediately instead of finishing the interval.
- Either way, the resulting abort error propagates uncaught up to `runNodeActivity`, whose
  `isRequestedCancellation()` check recognizes it (an `AbortError`/`CancelledFailure` while
  `Context.current().cancellationSignal.aborted` is `true`) and rethrows it unwrapped, rather than turning it
  into an `ApplicationFailure`.

**The workflow's own cancellation type matters here.** `imageGeneratorActivity`'s Temporal proxy
(`workflows/configs.ts`) uses only the `COMMON` retry policy — it does **not** set
`ActivityCancellationType.WAIT_CANCELLATION_COMPLETED` the way `textGeneratorActivity`/`apiCallerActivity` do
(their `INTERRUPTIBLE` preset). With the SDK's default `TRY_CANCEL`, `processSingleNode`'s
`cancelScope.run(...)` for this node settles as cancelled as soon as the cancel signal is requested, **without
waiting** for the activity to actually stop — the node is reported `CANCELLED` to the run while the activity
keeps executing in the background until its own abort unwinds it. Because that unwind throws rather than
returning a `CancelledNodeOutput`, `processSingleNode` reaches this case through its outer
`catch (isCancellation(error))` branch (with `output: null`), not the `isCancelledNodeOutput` branch
`runCancellableNode`-wrapped nodes use.

`resolveCancelSettlement` only charges a cancelled node when its type is `TEXT_GENERATOR`, so cancelling an
image-generator node never triggers an extra charge from the workflow's settlement path — but it also never
**reverses** whatever the provider itself already charged, which is what makes `stabilityai`'s pre-charge
(above) a real, unrefunded cost on a cancelled run.

### fal queue jobs are cancelled fal-side

Every fal queue submission response includes a `cancel_url`. When the run is aborted, or the poll budget expires,
the worker sends a best-effort `PUT <cancel_url>` (5s cap, errors ignored). A job still in fal's queue is removed;
one already processing receives a cancellation signal and may still finish on fal's side.

## Retry and timeout behavior

`imageGeneratorActivity` is registered with `startToCloseTimeout: "5 minutes"` and `heartbeatTimeout: "30 seconds"`, and `maximumAttempts: 1` (no Temporal-level retry) in [`configs.ts`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/temporal/workflows/configs.ts). The single 5-minute ceiling was validated against 30 days of production `imageGenerator` executions (2026-09-25): `openai` 230 runs, p95 33 s, max 91 s; `fal` 17 runs, max 19 s. `gemini`, `ideogram` and `meta` had no production runs in that window.

`stabilityai` and `ideogram` do not rely on that ceiling: both poll fal's queue (submit, then `GET <status_url>` every second until `COMPLETED`, then fetch `response_url`) against their own wall-clock budget, so they fail with a classified `TimeoutError` before Temporal would kill the activity:

| Provider | fal poll budget | Why |
| -------- | --------------- | --- |
| `stabilityai` | 270 s | Raised from ~2 minutes: 38 of 60 production Stability runs had been poll timeouts, and fal's queue wait for its endpoints varies (15 s to ~2 minutes observed on dev). Still under the 5-minute ceiling. |
| `ideogram` | 120 s | Unchanged. |

The same budget is sent as `X-Fal-Request-Timeout` (seconds) on submit, so fal never starts a request the worker has already given up on. When the budget runs out, the worker also cancels the job (see [fal queue jobs are cancelled fal-side](#fal-queue-jobs-are-cancelled-fal-side)).

The activity is kept alive by a heartbeat every 15 seconds (`withKeepAliveHeartbeat`, half the 30-second `heartbeatTimeout`) regardless of provider. The service also calls `Context.current().heartbeat()` twice per run to report its phase:

- `{ nodeId, phase: "generating" }` — before the provider call.
- `{ nodeId, phase: "uploading" }` — before the upload to `/worker/store-image`.

## Errors

| Condition | Class |
| --------- | ----- |
| Missing prompt, unsupported provider/mode pair, Ideogram `'Expand Image'` | `UserConfigError` |
| Missing/invalid provider API key, no user product found | `IntegrationError` |
| Provider 4xx/5xx, content-policy refusal, no image generated | `ProviderError` |
| fal poll exceeds its budget (270 s `stabilityai`, 120 s `ideogram`) | `TimeoutError` |
| Image upload or DB write failure | `SystemError` |

Implemented by [`ai-sdk-error-classifier.ts`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/ai-provider/image/ai-sdk-error-classifier.ts) for the AI SDK path (`openai`/`gemini`/`fal`/`meta`) and [`http-error-classifier.ts`](https://github.com/enhancedai-com/Flux-Prompt-Worker/blob/main/src/modules/ai-provider/image/http-error-classifier.ts) for the direct-HTTP path (`stabilityai`/`ideogram`).

## Provenance

This node was copy-ported from the back's `imageGeneratorNode` handler, targeting byte-identical behavior including pre-existing back bugs, with a small number of deliberate, explicitly-classified deviations.
