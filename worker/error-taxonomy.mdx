Node activities throw a specific `NodeError` subclass to say what kind of failure happened. The subclass sets the error's `category` (what the user, the logs and the back see) and its `nonRetryable` flag. Choose the wrong subclass and the failure is mislabeled: a user typo reads as our bug, or a flaky network call reads as bad input.

## The hierarchy

- **`UserConfigError`** (`user_config`): the user's input is wrong (bad URL, missing variable). `ContextLengthError` extends it with `code: "context_length_exceeded"`.
- **`IntegrationError`** (`integration`): a connected integration (OAuth, API key) failed in a user-visible way.
- **`ProviderError`** (`provider`): the third-party provider (OpenAI, Anthropic, Luma, …) returned an error.
- **`TimeoutError`** (`timeout`): the operation exceeded its budget.
- **`SystemError`** (`system`): our bug, our infrastructure, our dependency on something we own. `runNodeActivity` also wraps any error that is not a `NodeError` in a `SystemError` with the message `Internal error while running this node.`
- **`SchemaValidationError`** (`schema_validation`): a model's structured output did not match the requested schema; carries `rawOutput`.
- **`NodeNotFoundError`** (`node_not_found`): the node's row no longer exists; `fetchNodeRow` throws it with "This node no longer exists. Refresh the page."

All seven live in `worker/src/modules/nodes/shared/node-error.ts`, with the category list in `NODE_ERROR_CATEGORIES`. The eighth category, `egress_policy`, belongs to the outbound-request errors in `worker/src/modules/safe-fetch/safe-fetch.errors.ts`: `BlockedAddressError`, `ResponseTooLargeError` and `RedirectRefusedError` are non-retryable, `RequestTimeoutError` is retryable.

## Retry behavior

| Subclass | `nonRetryable` flag |
|---|---|
| `UserConfigError`, `ContextLengthError` | `true` |
| `IntegrationError` | `false` |
| `ProviderError` | `true` unless constructed with `retryable: true` |
| `TimeoutError` | `false` |
| `SystemError` | `true` |
| `SchemaValidationError` | `true` |
| `NodeNotFoundError` | `true` |

The `runNodeActivity` wrapper in `worker/src/modules/nodes/shared/run-node-activity.ts` reshapes every `NodeError` into `ApplicationFailure.create({ type: nodeErr.category, nonRetryable: nodeErr.nonRetryable, details: [detail], ... })`, and passes `retryAfterMs` as `nextRetryDelay` when the error has one.

In practice the flag rarely decides anything, because the retry policies in `worker/src/modules/temporal/workflows/configs.ts` already stop a node error from being retried:

- `COMMON` (`maximumAttempts: 1`) is used by `apiCallerActivity`, `thirdPartyIntegrationActivity`, `mcpActivity`, `scriptingActivity`, `counterActivity`, `mathFunctionActivity`, `pushDataActivity`, `fileSaveActivity`, `sqlQuerierActivity` and `reportBuilderActivity`: one attempt, whatever the flag.
- `RETRY_ON_WORKER_LOSS` (in `workflows/retry-policies.ts`) is used by `textGeneratorActivity`, `imageGeneratorActivity`, `imageReaderActivity`, `displayBoxActivity`, `largeMemoryActivity` and the other heavy node activities. It allows 2 attempts but lists every `NODE_ERROR_CATEGORIES` value, plus the start-to-close timeout, in `nonRetryableErrorTypes`. A node error is therefore never retried; the second attempt exists only for a worker that died or shut down mid-activity.

## How to choose

Ask the next question in order:

1. Is this because of the user's input? → `UserConfigError`.
2. Is this a connected integration failing? → `IntegrationError`.
3. Is this a third-party provider returning an error? → `ProviderError`.
4. Did the operation exceed its budget? → `TimeoutError`.
5. Everything else, including bugs in our own code → `SystemError`.

## Examples

### `UserConfigError`

```ts
if (!ALLOWED_MODES.has(explicit)) {
  throw new UserConfigError({
    field: "counterMode",
    devMessage: `unsupported counter mode: ${explicit}`,
    userMessage: "Counter mode is invalid.",
  });
}
```

### `IntegrationError`

```ts
throw new IntegrationError({
  devMessage: `Fetch failed: ${err instanceof Error ? err.message : String(err)}`,
  userMessage: "The remote server did not respond. Try again.",
  cause: err,
});
```

### `ProviderError`

```ts
throw new ProviderError({
  devMessage: `Evaluation error: ${message}`,
  userMessage: `The evaluation model rejected the request: ${message}`,
  cause: err,
});
```

### `TimeoutError`

```ts
throw new TimeoutError({
  devMessage: `Fetch timed out after ${timeoutMs}ms`,
  userMessage: "The remote server did not respond in time. Try again.",
  cause: err,
});
```

### `SystemError`

```ts
throw new SystemError({
  devMessage: `store-image failed with status ${response.status}: ${JSON.stringify(data)}`,
  userMessage: "Failed to save the generated image.",
});
```

## What goes wrong if you choose wrong

### `SystemError` thrown on user error

A null-check that should have raised `UserConfigError` instead raises `SystemError`. Both are non-retryable, so the activity still fails once, but the category is wrong: the error now reads as our bug in logs and dashboards, so an on-call engineer gets paged for an invalid URL the user typed.

### `UserConfigError` thrown on a flaky network blip

A transient fetch failure gets caught and re-thrown as `UserConfigError` because the handler reused the wrong class. The user sees "your input is wrong" when nothing about the input was wrong, and the `user_config` category hides a provider or network problem from whoever reads the logs.
