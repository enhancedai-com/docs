## Overview

The `WorkerService` is the entry point of the worker microservice. It creates a Temporal Worker instance, registers all workflows and activities, and starts polling a task queue for work.

**Source:** `src/modules/temporal/worker.service.ts` in the worker repo. `src/main.ts` creates the Nest application context and calls `WorkerService.run()`.

## How it works

When the application starts, the `WorkerService.run()` method:

1. Reads the task queue name from the `TEMPORAL_TASK_QUEUE` environment variable
2. Creates a Temporal Worker on the connection `TemporalService` opened to `TEMPORAL_ADDRESS` (default `localhost:7233`)
3. Registers all workflow definitions (`workflowsPath: require.resolve("./workflows")`) and activity implementations
4. Starts polling the task queue for workflow and activity tasks

```typescript
const worker = await Worker.create({
  connection: this.temporalService.connection,
  namespace: "default",
  taskQueue: process.env.TEMPORAL_TASK_QUEUE || "enhanced-ai-queue",
  maxConcurrentWorkflowTaskExecutions: 20,
  maxConcurrentActivityTaskExecutions: MAX_CONCURRENT_ACTIVITY_TASK_EXECUTIONS,
  maxCachedWorkflows: 20,
  defaultHeartbeatThrottleInterval: "2 seconds",
  maxHeartbeatThrottleInterval: "2 seconds",
  shutdownGraceTime: WORKER_SHUTDOWN_GRACE_MS,
  shutdownForceTime: WORKER_SHUTDOWN_FORCE_MS,
  workflowsPath: require.resolve("./workflows"),
  activities: bindRunToken({
    chargeTokensActivity: ...,
    textGeneratorActivity: ...,
    // all other activities
  }),
});

return worker.run();
```

## Task queue configuration

The task queue is the channel through which Temporal routes workflows to workers. The API and the worker **must use the same task queue name** for workflows to be picked up.

<Warning>
If the API sends workflows to a task queue that no worker is listening on, the workflows will remain queued indefinitely and never execute.
</Warning>

### Multi-environment setup

When multiple environments (dev, staging, production) share the same Temporal server, each environment **must use a different task queue** to prevent cross-environment routing.

Without separate task queues, Temporal distributes workflows to any available worker on the queue. A workflow triggered in staging could be picked up by the dev worker, which connects to the dev database and would fail to find the node data.

```
Temporal server
├── enhanced-ai-queue-dev       → Worker DEV (database: dev)
└── enhanced-ai-queue-staging   → Worker STAGING (database: staging)
```

### Configuration

Set the `TEMPORAL_TASK_QUEUE` environment variable in **both** the API and the worker for each environment. The values live in each environment's deployment configuration, not in the code; this is the naming pattern:

| Environment | `TEMPORAL_TASK_QUEUE` value |
|-------------|---------------------------|
| Dev         | `enhanced-ai-queue-dev`     |
| Staging     | `enhanced-ai-queue-staging` |
| Production  | `enhanced-ai-queue-prod`    |

<Note>
If the variable is not set, both sides default to `enhanced-ai-queue`. This fallback exists to avoid breaking existing setups, but you should always set it explicitly in deployed environments.
</Note>

**API side.** Every place in back that starts a workflow or registers a schedule reads the same variable: `src/temporal/temporal.controller.ts`, `src/app-api/flux/flux.service.ts`, `src/app-api/flux/flux.controller.ts`, `src/app-api/flux/output-delivery/output-delivery.service.ts`, `src/app-api/router/router.service.ts` and `src/app-api/schedule/temporal-schedule-registrar.service.ts`. For example, `POST /process/single-node`:

```typescript
const handle = await this.temporalService.client.start<ProcessSingleNodeInterface>(
  'processSingleNode',
  {
    taskQueue: process.env.TEMPORAL_TASK_QUEUE || 'enhanced-ai-queue',
    args: [nodeId, user.id, sessionId, flowId, flowVersionHistoryId ?? null],
    workflowId: `node-process-${nodeId}-${Date.now()}`,
  },
);
```

**Worker side** (`src/modules/temporal/worker.service.ts`):

```typescript
taskQueue: process.env.TEMPORAL_TASK_QUEUE || "enhanced-ai-queue",
```

## Worker settings

| Setting | Value | Description |
|---------|-------|-------------|
| `maxConcurrentWorkflowTaskExecutions` | 20 | Maximum workflow tasks processed simultaneously |
| `maxConcurrentActivityTaskExecutions` | 10 (`MAX_CONCURRENT_ACTIVITY_TASK_EXECUTIONS`, `temporal.constants.ts`) | Maximum activity tasks processed simultaneously |
| `maxCachedWorkflows` | 20 | Maximum workflows kept in memory cache |
| `defaultHeartbeatThrottleInterval` / `maxHeartbeatThrottleInterval` | 2 seconds | How often activity heartbeats are sent to the server |
| `shutdownGraceTime` | 100 000 ms (`WORKER_SHUTDOWN_GRACE_MS`) | Time running activities get to finish after shutdown starts |
| `shutdownForceTime` | 110 000 ms (`WORKER_SHUTDOWN_FORCE_MS`) | Time after which shutdown is forced |

## Registered workflows

`workflows/index.ts` exports the workflows the worker runs:

| Workflow | Started by |
|----------|-----------|
| `processSingleNode` | The main API, once per worker-executed node, and `processFlow` as a child. See [processSingleNode](/worker/workflows/process-single-node) |
| `processFlow` | The main API's `apiV2` path when the `engine_in_workflow` flag is on and the flow is eligible; also `processBatch` and `runScheduledFlow` as a child |
| `processBatch` | `flux.controller.ts` for a batch file. See [processBatch](/worker/workflows/process-batch) |
| `runScheduledFlow` | Temporal schedules that back's `temporal-schedule-registrar.service.ts` registers |
| `completionWorkflow` | The Completions API (`router.service.ts`) |
| `deliverRunOutputs` | Output delivery (`output-delivery.service.ts`). See [deliverRunOutputs](/worker/activities/deliver-run-outputs) |

[`processAgent`](/worker/workflows/process-agent) is not exported, so it is not registered.

## Troubleshooting

### Workflows stuck in "Scheduled" state

If workflows appear in the Temporal UI as scheduled but never execute:

1. Verify the worker is running and connected to the Temporal server (the worker does not log a startup line of its own; check that the ECS task is running and that the Temporal UI lists a poller on the task queue)
2. Confirm the task queue name matches between the API and worker
3. Ensure `TEMPORAL_ADDRESS` points to the correct Temporal server

### Workflows executing with wrong data

If workflows execute but return incorrect results or "Node not found" errors:

1. Verify each environment uses a unique `TEMPORAL_TASK_QUEUE` value
2. Confirm the worker's database connection (`TYPEORM_*` variables) points to the correct database for that environment
