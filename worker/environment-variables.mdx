All 31 vars are actively used — none obsolete. `LAMBDA_ENDPOINT`, `CLAIM_CHECK_THRESHOLD_BYTES`, `APICALLER_MAX_RESULT_BYTES`, `LOG_PROVIDER_OPTIONS` and `SLACK_API_BASE` are read directly via `process.env`, not through the Zod schema — no type-safety there, but that's expected since they're all optional with fallbacks.

## Cross-repo gotcha

`INTEGRATIONS_ENCRYPTION_KEY` must be **identical** to `back`'s value — same SSM param in every environment, and it must **never** be set to `JWT_SECRET`. The worker's copy of the credentials-decryption helper (ported from `back/src/common/credentials-encryption.service.ts` for the P0+Stripe migration, `868ke6j3r`) deliberately has no `JWT_SECRET` fallback: a `user_integrations` row encrypted by `back` only decrypts on the worker if the keys match exactly.

`SLACK_CLIENT_ID` and `SLACK_CLIENT_SECRET` must be the **same Slack app credentials** as `back`'s — the worker calls Slack's OAuth token endpoint with these to refresh a rotated access token, and that only succeeds if it's the same app that originally issued the token.

`NOTION_CLIENT_ID` and `NOTION_CLIENT_SECRET` must likewise be the **same Notion OAuth app credentials** as `back`'s, for the same rotating-token-refresh reason.

`HUBSPOT_CLIENT_ID` and `HUBSPOT_CLIENT_SECRET_ID` must be the **same HubSpot app credentials** as `back`'s. HubSpot access tokens live roughly 30 minutes, so unlike Slack and Notion the worker refreshes these routinely rather than occasionally — if the pair is missing from the task definition, every HubSpot node fails with a "not configured" error.

## CI/CD

Runtime vars are not baked into the Docker image at build/CI time — they live in the ECS task definition (backed by SSM), fetched fresh on every deploy. The GitHub Actions workflow itself only needs 2 repo secrets: `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, both confirmed present.
