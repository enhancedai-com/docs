## Cross-repo gotcha

`INTEGRATIONS_ENCRYPTION_KEY` must be **identical to the key `back` actually encrypted with** — and that is not always `back`'s `INTEGRATIONS_ENCRYPTION_KEY`. The back derives it as:

```ts
const key = process.env.INTEGRATIONS_ENCRYPTION_KEY || process.env.JWT_SECRET;
```

The worker has **no such fallback** (`z.string().min(32)`, validated with `envSchema.parse`, so it will not boot without the var). So read the back's environment first and follow whichever branch is true:

| `back`'s `INTEGRATIONS_ENCRYPTION_KEY` | What the worker must be given |
|---|---|
| set | that same value |
| empty / unset | the value of `back`'s `JWT_SECRET` — because that is what the stored rows were encrypted with |

<Warning>
Earlier revisions of this page said the worker must **never** be set to `JWT_SECRET`. That is only true once `back` has its own `INTEGRATIONS_ENCRYPTION_KEY` set. While `back` is on the fallback, setting the worker to anything else means every `user_integrations` row fails to decrypt — and this fails **silently at run time**, after a green deploy, not at boot. Confirm the back's real environment before deploying the worker.
</Warning>

The SSM parameter existing is not the same as the worker task definition actually referencing it — staging and prod were found (during the P6 HubSpot rollout, `868ke6jb7`) running revisions that never declared this secret at all, despite already running Stripe/WordPress. `.specs/features/worker-thirdparty-integration-migration/p6-hubspot/verify-worker-hubspot-secrets.sh` checks (and can fix) this per environment — run it before any deploy that touches a migrated adapter.

## CI/CD

Runtime vars are not baked into the Docker image at build/CI time — they live in the ECS task definition (backed by SSM), fetched fresh on every deploy. The GitHub Actions workflow itself only needs 2 repo secrets: `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, both confirmed present.
