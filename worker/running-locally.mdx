## Stack overview

The local stack is defined in `docker/devdb/docker-compose.devdb.yaml` at the workspace root (the Workflow repository) and brings up the following services:

- **back** — the NestJS API.
- **worker** — the Temporal worker process.
- **temporal** — the Temporal server (auto-setup image).
- **temporal-ui** — the Temporal Web UI, exposed on host port `8080`.
- **temporal_db** — PostgreSQL used by the Temporal server itself.
- **app_db** — PostgreSQL for the application data (contains `node_executions`).
- **redis** — Redis for queue and signals.
- **tunnel** — an SSH tunnel container used to reach the dev database; not required for a fully local-only run.

## Starting the stack

1. From the workspace root:

   ```bash
   docker compose -f docker/devdb/docker-compose.devdb.yaml up -d
   ```

2. Verify the containers are running:

   ```bash
   docker ps --filter 'label=com.docker.compose.project=enhanced-devdb'
   ```

3. The front dev server runs separately. In a second terminal:

   ```bash
   cd front && pnpm dev
   ```

## Finding a run in Temporal UI

Open the local Temporal UI at `http://localhost:8080/` (served by the `temporal-ui` container) in the `default` namespace. Workflows are named after the workflow function (`processFlow`, `processSingleNode`, `processBatch`, `runScheduledFlow`, `deliverRunOutputs`) and you can search by `workflowId`:

- `run-<runId>` for a full run on the workflow route (`processFlow`).
- `node-process-<nodeId>-<execId>` for one node (`processSingleNode`), whether a child of `processFlow` or started by the back directly.
- `batch-process-<batchFileId>` for a CSV batch (`processBatch`).

Clicking a workflow opens its event timeline; each activity and its retries are visible there.

## Reading `node_executions`

Connect to the local `app_db` database (host `localhost`, port `5434`, user `postgres`) and run:

```sql
SELECT "execId", "runId", "nodeId", "type", "isError", "input", "outputData", "output", "cancelledAt", "createdAt"
FROM node_executions
WHERE "execId" = '<execId>'
ORDER BY "createdAt";
```

How to read a row:

- `isError = false` and `outputData` populated — the activity finished successfully and the next node can read from it.
- `isError = false` and `outputData` null/empty — the activity returned, but no payload was written. See [When a node silently did nothing](#when-a-node-silently-did-nothing) below.
- `isError = true` — the activity threw; see the [Error taxonomy](/worker/error-taxonomy) page for which subclass.
- `cancelledAt` is set — the run was cancelled from the API before the activity completed.

The entity is defined in `back/src/entities/node_execution.entity.ts`. Note that the table name is snake_case (`node_executions`) but the columns are camelCase and must be quoted in SQL — the TypeORM naming strategy on this project does not translate property names.

## Reading worker logs

Worker logs are printed to the `worker` container's stdout. Follow them with `docker logs -f fluxprompt-worker-local` (the container name set in the compose file). To isolate a single run, pipe through grep by `execId` or `runId`: `docker logs fluxprompt-worker-local 2>&1 | grep '<execId>'`. The worker logs with `console.log` and `console.error`; `src/main.ts` only boots the Nest application context and starts the Temporal worker. Flow-level lines from `processFlow` carry a `[B4]` prefix.

## When a node silently did nothing

If the row has `isError = false` but `outputData` is empty (or missing a field you expected), check in this order:

1. Does the workflow dispatch your type? Open `worker/src/modules/temporal/workflows/process-single-node.workflow.ts` and search for `NodeType.<YOUR_TYPE>`; most types have no explicit `case` and are resolved from `UNIFORM_NODE_ACTIVITIES` in `workflows/node-activities.ts`.
2. Did the activity run? Look at the Temporal event timeline for `<node>Activity`. If there is no `node-process-<nodeId>-<execId>` workflow at all, the back never dispatched the node; if the activity failed as not registered, step 5 of [How to add a node type](/worker/how-to-add-a-node-type) was skipped.
3. Did `persistNodeSuccess` write? It does not log, so check the row itself: `outputData.executionStatus` is `"COMPLETED"` after a success write, and `updatedAt` moves. A row with `cancelledAt` set is never overwritten by a success write.

A node that never ran at all in a full run usually has no `node.type === '<type>'` branch in the legacy loop of `FluxService.apiV2` (layer 7 of [How to add a node type](/worker/how-to-add-a-node-type)): that loop has no generic dispatch and skips the type without an error. A missing binding in `worker.service.ts` is louder: the activity task fails in the Temporal timeline because the activity is not registered on the worker.
