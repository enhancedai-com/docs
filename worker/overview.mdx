## What is the Worker?

The Worker is a microservice responsible for executing workflow operations in the FluxPrompt system. It processes node and agent executions from Temporal queues, handles AI model interactions, and manages resource-intensive operations.

The Worker runs as a separate service to isolate processing workloads from the main API, ensuring scalability and reliability for workflow execution.

## How it works

The Worker operates as a Temporal worker that:

- Connects to the Temporal server to receive workflow execution tasks
- Executes workflows defined in the codebase
- Runs activities that perform actual operations (database queries, AI model calls, file generation)
- Reports execution results back to Temporal
- Handles retries and error recovery through Temporal's built-in mechanisms

## Temporal integration

The Worker integrates with Temporal using the Temporal SDK for Node.js. Temporal provides:

- **Workflow orchestration**: Defines the execution flow and coordinates activities
- **State management**: Maintains workflow state across executions and failures
- **Queue management**: Manages task queues for node and agent processing
- **Reliability**: Ensures workflows complete even if the worker restarts
- **History**: Tracks all workflow and activity executions for debugging

### Connection

The Worker connects to Temporal using a `NativeConnection`:

```typescript
this.connection = await NativeConnection.connect({
  address: process.env.TEMPORAL_ADDRESS || "localhost:7233",
});
```

### Task queue

All workflows are processed through an environment-specific task queue (configured via `TEMPORAL_TASK_QUEUE`), which allows multiple workers to process tasks in parallel. Each environment must use a unique task queue name to prevent cross-environment routing. See [Worker service](/worker/workflows/worker-service) for details.

## Workflows and activities

### Workflows

Workflows define the execution logic and orchestrate activities. They are deterministic functions that:

- Cannot make direct external calls (database, HTTP, etc.)
- Must use activities for any non-deterministic operations
- Can handle retries and error scenarios
- Maintain state throughout execution

**Registered workflows** (exported from `src/modules/temporal/workflows/index.ts`):

- [`processSingleNode`](/worker/workflows/process-single-node) - Executes a single node in a workflow
- [`processFlow`](/worker/workflows/process-single-node#related-documentation) - Runs a full flow: dispatches a `processSingleNode` child workflow per node, in topological order
- [`processBatch`](/worker/workflows/process-batch) - Runs a registered CSV batch as a durable workflow: one child `processFlow` per row, five rows in flight, `continueAsNew` every 100 rows, `stopAfterFailures` cap
- `runScheduledFlow` - Runs one fire of a flow schedule: resolves the schedule, then runs the flow as a child `processFlow`
- `deliverRunOutputs` - Delivers a finished run's outputs by email or callback (see [`deliverEmailActivity` and friends](/worker/activities/deliver-run-outputs))
- `completionWorkflow` - Wraps `completionActivity` for the completions API

[`processAgent`](/worker/workflows/process-agent) still exists in `process-agent.workflow.ts`, but `index.ts` does not export it, so the worker does not register it.

### Activities

Activities are the actual operations performed by workflows. They can:

- Make database queries
- Call external APIs
- Generate files
- Send notifications
- Perform any non-deterministic operation

**Available activities:**

The worker registers 64 activities in total (`worker.service.ts:39-215`): one per node type it can execute, the per-type validation and charging activities, the run, batch and schedule bookkeeping activities, and four delivery activities from `DeliveryActivities`. The full table lives on [Worker service](/worker/workflows/worker-service#registered-activities); the ones most worth knowing up front:

- [`notifyStatusActivity`](/worker/activities/notify-status) - Sends status updates to users
- [`getNodeInfoActivity`](/worker/activities/get-info-database) - Fetches node type/flow_id/data before dispatch (`getInfoInDatabaseActivity` is also registered but is dead code: nothing calls it)
- [`validateModelAccessActivity`](/worker/activities/validate-model-access) - Validates user access to AI models
- [`textGeneratorActivity`](/worker/node/text-generator) - Runs the AI Text Generator node (LLM call, persistence, token usage)
- [`chargeTokensActivity`](/worker/activities/charge-tokens) - Records token usage for billing
- [`generateExecutionLogsActivity`](/worker/activities/generate-execution-logs) - Creates execution logs (and updates node state on error)
- [`scriptingActivity`](/worker/node/scripting) - Runs user JavaScript or Python via Lambda
- [`nodeExecutionErrorActivity`](/worker/activities/node-execution-error) - Called on node error; currently a no-op
- [`generateFileActivity`](/worker/activities/generate-file) - Generates output files; registered but not called from any live workflow
- [`deliverEmailActivity`, `deliverCallbackActivity`](/worker/activities/deliver-run-outputs) - Deliver a run's outputs for `deliverRunOutputs`
- The other node-execution activities (`mathFunctionActivity`, `counterActivity`, [`imageGeneratorActivity`](/worker/node/image-generator), `imageReaderActivity`, `webCrawlingActivity`, `largeMemoryActivity`, `webSearchActivity`, `webAmazonActivity`, `voiceGeneratorActivity`, `mcpActivity`, `thirdPartyIntegrationActivity`, `apiCallerActivity`, `sqlQuerierActivity`, `displayBoxActivity`, `dataOutputActivity`, `pullDataActivity`, `pushDataActivity`, `fileSaveActivity`, `reportBuilderActivity`, `aiVideoGeneratorActivity`, `secApiNodeActivity`, `usCensusNodeActivity`, `audioTranscriberActivity`) and the rest; see [Worker service](/worker/workflows/worker-service#registered-activities) for the complete list

## Execution flow

When a workflow is triggered:

1. **Workflow starts**: Temporal receives a workflow execution request
2. **Worker picks up task**: An available worker picks up the task from the queue
3. **Workflow executes**: The workflow function runs and orchestrates activities
4. **Activities execute**: Each activity performs its operation (database query, API call, etc.)
5. **Results returned**: Activity results are returned to the workflow
6. **Workflow completes**: The workflow finishes and reports completion status
7. **Status notification**: Users are notified of the execution status

## Error handling

The Worker implements comprehensive error handling:

- **Activity retries**: Activities can be retried on failure (configured per activity)
- **Workflow error handling**: Workflows catch errors and execute error activities
- **Status updates**: Users are notified of failures through status notifications
- **Execution logs**: All errors are logged with stack traces for debugging

## Configuration

The Worker requires the following environment variables:

- `TEMPORAL_ADDRESS` - Temporal server address (default: `localhost:7233`)
- `TEMPORAL_TASK_QUEUE` - Task queue name (default: `enhanced-ai-queue`; set a unique value per environment)
- `URL_MAIN_API` - Main API URL for internal API calls
- `INTERNAL_API_KEY` - API key for authenticating with the main API
- Database connection variables `TYPEORM_*` (for direct database access) and `REDIS_HOST`/`REDIS_PORT`

The full, validated list is the Zod schema in `src/env.ts`; see [Environment variables](/worker/environment-variables).

See the [development guide](/worker/development) for complete setup details.
